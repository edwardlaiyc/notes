## 1. From Program File to Process in Memory

### 1.1 The process image
To run a program, the OS creates a **process image** and loads it into memory. Lecture 2 showed its four parts:

![The process image (Lecture 7, slide 7.2)](7-artifacts/process-image.png)

| Part | Holds | Position |
|---|---|---|
| Text | The program code | Low addresses |
| Data | Global variables | Above the text |
| Heap | Memory allocated while the program runs, for example `new int[10]` | Grows up |
| Stack | Function parameters and local variables | High addresses, grows down |

### 1.2 Compile, link, load
Three tools turn source code into a process in memory:

![Compiler, linker and loader (Lecture 7, slide 7.3)](7-artifacts/compile-link-load.png)

1. The **compiler** translates source code into an **object module**.
2. The **linker** joins object modules and library code, and resolves the references between them. The result is a **load module** on the disk.
3. The **loader** creates the process image, allocates memory, and copies the image into that memory.

### 1.3 The question: which address does an instruction use?
An instruction such as `LOAD X` or `JUMP Y` contains an address. The CPU uses that address to fetch data or the next instruction. But the program does not know in advance **where in memory** the OS will put it. So someone must turn the addresses in the code into real memory addresses. This is **address binding**.

## 2. Address Binding: Three Choices of Time
Binding can occur at three different times. The example: the program is 800 bytes long, and the OS loads it at memory address 1024.

### 2.1 Compile-time binding
The compiler already knows where the program will be in memory. It writes **absolute addresses** into the code: `LOAD 1824`, `JUMP 1424`.

![Compile-time binding (Lecture 7, slide 7.6)](7-artifacts/compile-time-binding.png)

* The loader copies the code as it is.
* **Problem:** if the start address changes, you must **compile again**.

### 2.2 Load-time binding
The compiler writes **relocatable addresses**, counted from 0: `LOAD 800`, `JUMP 400`. The **loader** adds the start address when it loads the program. In memory, the code says `LOAD 1824` and `JUMP 1424`.

![Load-time binding (Lecture 7, slide 7.7)](7-artifacts/load-time-binding.png)

* The program can go anywhere when it is loaded.
* **Problem:** once loaded, the program cannot move, because its memory now holds absolute addresses.

### 2.3 Execution-time binding
The code in memory **keeps** its relative addresses: `LOAD 800`, `JUMP 400`. The hardware adds the start address **on every memory access**, while the program runs.

![Execution-time binding (Lecture 7, slide 7.8)](7-artifacts/execution-time-binding.png)

The hardware unit that does this is the **memory-management unit (MMU)**. It holds the start address in a **relocation register** (the base register):

![The MMU adds the relocation register (Lecture 7, slide 7.9)](7-artifacts/mmu-relocation.png)

The CPU generates address 800. The MMU adds 1024. Memory receives address 1824.

* The OS can **move** the program while it runs: it copies the program and changes the relocation register.

### 2.4 The protection check differs
Lecture 1 introduced base and limit registers. The check depends on the binding type:

| Binding | Addresses in the code | Legal if | Physical address |
|---|---|---|---|
| Compile time or load time | Absolute | base ≤ address < base + limit | = the address |
| Execution time | Relative (from 0) | address < limit | = address + base |

If the check fails, the CPU traps to the OS.

### 2.5 Logical and physical addresses
* The **logical address** is the address in the code, which the CPU generates when it runs an instruction.
* The **physical address** is the address that the memory unit receives.
* The **address space** of a process is all the addresses that it can use.

With execution-time binding, the logical address space always **starts from 0**, and it is one continuous sequence of bytes, from 0 to limit − 1.

## 3. Contiguous Allocation
How does the OS share memory among processes? The first approach gives each process **one continuous block** of physical memory.

### 3.1 Fixed partitioning
The OS divides memory into **regions with fixed boundaries**. Each process goes into one region.

* **Problem: internal fragmentation.** A process smaller than its region leaves the rest of the region unused. No other process can use that space.

### 3.2 Dynamic partitioning
The OS gives each process **exactly** the memory it asks for. Free blocks of memory are called **holes**. Holes of many sizes are spread through memory. When a process arrives, the OS gives it memory from a hole that is large enough. The OS keeps a list of allocated blocks and free holes.

![Dynamic partitioning over time (Lecture 7, slide 7.18)](7-artifacts/dynamic-partitioning.png)

The slide shows a 2560K memory with the OS in the lowest 400K. Processes arrive and leave. After some time, the free memory is in several small holes.

### 3.3 Which hole to use
To satisfy a request of size n from the list of holes:

| Rule | Which hole | Effect |
|---|---|---|
| **First-fit** | The **first** hole that is large enough | Fast: stops searching early |
| **Best-fit** | The **smallest** hole that is large enough | Must search the whole list (unless sorted by size). Leaves the **smallest** leftover hole |
| **Worst-fit** | The **largest** hole | Must search the whole list. Leaves the **largest** leftover hole |

### 3.4 Two kinds of fragmentation
* **External fragmentation:** there is enough free memory **in total**, but it is not in one continuous block. The waste is **outside** the partitions. Dynamic partitioning has this problem.
* **Internal fragmentation:** a process gets a little **more** memory than it asked for. The unused part is **inside** its partition. Fixed partitioning has this problem.

### 3.5 Compaction
**Compaction** reduces external fragmentation. The OS moves the processes in memory so that all the free memory forms one large block.

![Compaction joins the holes (Lecture 7, slide 7.22)](7-artifacts/compaction.png)

**Compaction needs execution-time binding.** To move a process, the OS must change where its addresses point. With execution-time binding, the OS only changes the base register. With absolute addresses in the code (compile-time or load-time binding), every address inside the process would be wrong after the move.

## 4. Paging

### 4.1 The idea
Contiguous allocation needs one large free block. **Paging** removes that need. A process can use memory **anywhere** that a free block exists:

* Divide **physical memory** into fixed-size blocks, called **frames**. The size is a power of 2, between 512 and 8192 bytes.
* Divide **logical memory** into blocks of the same size, called **pages**.
* To run a program of n pages, find **any** n free frames, and load the pages into them.
* Keep a **page table** for each process. It says which frame holds each page.

The OS keeps track of all free frames.

* **No external fragmentation.** Any free frame is usable.
* **Internal fragmentation is still possible.** The last page of a process is usually not full.

![A paging example (Lecture 7, slide 7.25)](7-artifacts/paging-example.png)

In the slide, the page size is 4 bytes. The logical memory has 4 pages (16 bytes). The physical memory has 8 frames (32 bytes). The page table maps page 0 → frame 5, page 1 → frame 6, page 2 → frame 1, page 3 → frame 2.

### 4.2 Splitting an address
A logical address has two parts:

* **Page number p:** an index into the page table. The page-table entry gives the frame number.
* **Page offset d:** the position inside the page. It stays the same in the frame.

If the page size is $2^n$ bytes and the logical address space is $2^m$ bytes:

* The **low n bits** are the offset d.
* The **high m − n bits** are the page number p.
* The number of pages is $2^{m-n}$.

![Address translation with a page table (Lecture 7, slide 7.27)](7-artifacts/address-translation-scheme.png)

**To translate a logical address to a physical address:**

1. Split the address: p = the high bits, d = the low n bits.
2. Look up p in the page table to get the frame number f.
3. The physical address is f followed by d. As a number: f × page size + d.

![Translating logical address 0111 (Lecture 7, slide 7.28)](7-artifacts/address-translation-example.png)

In the slide, the address is 4 bits and the page size is 4 bytes (n = 2). Logical address `0111` has p = `01` = 1 and d = `11` = 3. The page table maps page 1 to frame 6 = `110`. So the physical address is `110` followed by `11` = `11011` = 27. Check: 6 × 4 + 3 = 27.

**The frame number has its own size.** The number of bits in the frame number depends on the size of **physical** memory, not logical memory. With $2^k$ frames, the frame number has k bits, and the physical address has k + n bits.

### 4.3 Where the page table lives
* The page table is kept in **main memory**.
* The **page-table base register (PTBR)** points to the page table of the current process.
* The **page-table length register (PTLR)** gives the size of the page table.

**Problem: every access now needs two memory accesses.** One to read the page-table entry, and one to read the data or instruction. If one memory access takes μ, a paged access takes 2μ.

### 4.4 The TLB: a cache for the page table
The **translation look-aside buffer (TLB)** is a small, fast hardware cache. It holds recent (page number → frame number) pairs. Another name is **associative registers**.

![Paging with a TLB (Lecture 7, slide 7.30)](7-artifacts/paging-with-tlb.png)

On each access:

* **TLB hit:** the page number is in the TLB. The frame number comes from the TLB. One memory access, for the data.
* **TLB miss:** read the page table in memory (one access), then the data (one more access). The pair also goes into the TLB.

### 4.5 Effective access time with a TLB
Let:

* ε = the time for one TLB lookup,
* μ = the time for one memory access,
* α = the **hit ratio**: the fraction of accesses that find the page number in the TLB.

$$\text{EAT} = (\mu + \varepsilon)\,\alpha + (2\mu + \varepsilon)(1 - \alpha) = (2 - \alpha)\,\mu + \varepsilon$$

Where the two terms come from:

* A hit costs one TLB lookup and one memory access: μ + ε.
* A miss costs one TLB lookup, one page-table access and one data access: 2μ + ε.

A TLB does not always help. If the hit ratio is very low, the EAT with a TLB can be **worse** than 2μ without it, because each access also pays ε.

### 4.6 Shared pages
Two processes can share code: their page tables point to the **same frames**. For example, three users run the same editor. The editor code is in physical memory only once. Each user has private data pages.

![Shared pages (Lecture 7, slide 7.32)](7-artifacts/shared-pages.png)

Shared code must not change while it runs (it must be **read-only**), so that one process cannot break it for the others.

### 4.7 Two-level page tables
**The problem.** Take a 32-bit logical address and 4 KB ($2^{12}$-byte) pages:

* The offset needs 12 bits. The page number needs 32 − 12 = 20 bits.
* The page table has $2^{20}$ entries. With 4 bytes for each entry, it is 4 MB **for each process**. And it must be contiguous in memory.

**The solution: page the page table.** Split the 4 MB page table into pages too.

![The sizes in a two-level page table (Lecture 7, slide 7.34)](7-artifacts/two-level-sizes.png)

* The 4 MB page table fills 4 MB / 4 KB = $2^{10}$ pages. So an **outer page table** needs $2^{10}$ entries, one for each page of the inner table. That needs **10 bits: p1**.
* Each page of the inner table holds 4 KB / 4 bytes = $2^{10}$ entries. That needs **10 bits: p2**.

The logical address is now:

| p1 (outer index) | p2 (inner index) | d (offset) |
|---|---|---|
| 10 bits | 10 bits | 12 bits |

![Two-level address translation (Lecture 7, slide 7.36)](7-artifacts/two-level-page-table.png)

To translate:

1. The PTBR points to the outer page table. Use p1 to find the frame F#1 of one page of the inner table.
2. In that page, use p2 to find the frame F#2 of the data.
3. The physical address is F#2 followed by d.

Each extra level costs one more memory access on a TLB miss, which is a small increase in access time. In return, the OS needs only the pages of the inner table that are in use, and each of them fits in one frame.

**A general rule for the number of levels.** One page of a page table holds (page size ÷ entry size) entries. Keep adding levels until the outermost table fits in **one** page.

### 4.8 Inverted page tables
**The problem.** Each process has its own page table, and its size grows with the **logical** address space. With many processes, the page tables use a lot of memory.

**The solution.** Use **one table for the whole system**, with **one entry for each physical frame**. Entry i says which ⟨process ID, page number⟩ is in frame i.

![Address translation with an inverted page table (Lecture 7, slide 7.38)](7-artifacts/inverted-page-table.png)

* The logical address is ⟨process ID, page number, offset⟩.
* To translate, **search** the table for the pair ⟨process ID, page number⟩.
* If the match is at entry i, the physical address is ⟨i, offset⟩. The entry's **position** is the frame number.

* **Advantage:** the table size grows with the size of **physical** memory, and there is only one table.
* **Disadvantage: slow search.** The table is ordered by frame number, but the lookup uses the page number. In the worst case, the OS searches the whole table.

| | Normal page table | Inverted page table |
|---|---|---|
| How many | One for each process | One for the whole system |
| Number of entries | One for each **page** of the process | One for each **frame** of physical memory |
| Lookup | Index by page number (direct) | Search for ⟨pid, page⟩ |

## 5. Segmentation

### 5.1 The idea
A programmer does not think of a program as pages of equal size. They think of **logical parts**: the main program, functions, the stack, a symbol table, arrays. **Segmentation** divides the program into these parts, the **segments**.

![A program as segments (Lecture 7, slide 7.39)](7-artifacts/segmentation-example.png)

* Segments can have **different sizes**.
* Each segment is placed separately in memory. The segments of one process do **not** need to be next to each other.

### 5.2 Translating a segment address
A logical address is ⟨segment number s, offset d⟩. The **segment table** has one entry for each segment:

* **base:** the physical start address of the segment.
* **limit:** the length of the segment.

The **segment-table base register (STBR)** points to the segment table. The **segment-table length register (STLR)** gives the number of segments that the program uses.

![Segment address translation (Lecture 7, slide 7.42)](7-artifacts/segmentation-translation.png)

To translate ⟨s, d⟩:

1. Look up entry s in the segment table.
2. Check d < limit. If not, trap to the OS (addressing error).
3. The physical address is base + d.

**Example (slide 7.43).** Translate ⟨3, 128⟩. Segment 3 has base 3200 and limit 1100. 128 < 1100, so the address is legal. The physical address is 3200 + 128 = 3328.

Note the difference from paging: paging **joins** the frame number and the offset as bits, while segmentation **adds** the base and the offset as numbers.

### 5.3 Segmentation has external fragmentation
Segments have variable sizes. So placing them is the same problem as dynamic partitioning (section 3.2): the OS uses best-fit or first-fit. When a process leaves, its segments become **holes of different sizes**. So segmentation suffers from **external fragmentation**. It has no internal fragmentation, because each segment gets exactly its size.

### 5.4 Paging and segmentation side by side

| | Paging | Segmentation |
|---|---|---|
| Block size | Fixed (pages) | Variable (segments) |
| Based on | The hardware's page size | The logical parts of the program |
| External fragmentation | No | Yes |
| Internal fragmentation | Yes (in the last page) | No |
| Translation | Frame number joined with offset | Base + offset, after the check d < limit |
| Sharing code | Through shared pages; the code in a page must not change | Natural: share a whole segment, such as a function |

## 6. Summary of the Allocation Schemes

| Scheme | Contiguous? | Internal fragmentation | External fragmentation |
|---|---|---|---|
| Fixed partitioning | Yes | Yes | No |
| Dynamic partitioning | Yes | No | Yes |
| Paging | No | Yes | No |
| Segmentation | No | No | Yes |

## What You Know Now (Lecture 7)

* Binding can occur at compile time (absolute code), load time (the loader relocates) or execution time (the MMU adds the base on every access). Only execution-time binding lets a process move.
* Fixed partitions waste space inside (internal fragmentation). Dynamic partitions leave holes outside (external fragmentation). Compaction fixes holes, but needs execution-time binding.
* First-fit takes the first big-enough hole, best-fit the smallest, worst-fit the largest.
* Paging splits the address into page number and offset. The page table maps pages to frames. Paging has no external fragmentation.
* A TLB caches page-table entries: EAT = (2 − α)μ + ε.
* A two-level page table pages the page table: 32-bit address, 4 KB pages → 10 + 10 + 12 bits.
* An inverted page table has one entry for each frame and must be searched.
* Segmentation uses variable-size logical segments, checks d < limit, and adds base + d. It has external fragmentation.
