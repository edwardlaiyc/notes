I/O devices vary in many dimensions, and most are extremely slow compared with the CPU and memory. I/O design has two objectives:

  • Efficiency: I/O is often the bottleneck. Disk I/O has received the most attention.
  • Generality: handle all devices in a uniform way, both in how processes see devices and in how the OS manages them.

1. I/O System Architecture

Peripherals vary across data transfer modes (character vs. block streams), access semantics (sequential vs. random), synchronization behaviors (synchronous vs. asynchronous), and sharing constraints (dedicated vs. shared).

Layered Structure

  1. Kernel I/O Subsystem: Provides shared, device-independent abstractions: scheduling request queues, buffering, caching, spooling, device reservation, and error handling.
  2. Device Drivers: Device-specific kernel modules that translate standard abstract I/O commands (read, write, seek) into low-level device controller registers and instructions.
  3. Device Controllers: Hardware interfaces on the system bus containing command/status registers and internal data buffers that manage the physical device.
  4. Physical Devices: Mechanical or electronic hardware (magnetic platters, optical media, flash chips, keyboards).

2. Kernel I/O Subsystem Services

I/O scheduling rearranges the order in which I/O requests are served (e.g. disk scheduling, §6) to improve efficiency. The other services (lecture wording):

Mechanism Lecture definition Data in memory Example
Buffering Store data in memory while transferring between devices, to cope with device speed mismatch and transfer-size mismatch Data in transit (may be the only copy) Networking: packets assembled into disk blocks
Caching Fast memory holding a copy of data, to improve I/O efficiency for files that are being written and re-read rapidly A duplicate of data stored elsewhere Keeping a file’s blocks in memory
Spooling Hold output for a device that can serve only one request at a time Whole output jobs queued Printing

The I/O subsystem also provides error handling, device reservation and device-name translation. The device-driver layer hides the differences among device controllers from the I/O subsystem. I/O system calls are costly in CPU time because of the many software layers between the application and the device.

AY17/18 S2 Q4a(iii): Appropriate usage of buffering vs. caching
  • (1) Downloading a file from the Internet and saving to hard disk →\to Buffering: The network operates on unpredictable packet arrival rates with small MTU transfer sizes, while the disk transfers fixed multi-kilobyte blocks. Buffering accommodates transfer size mismatches and decouples transmission speed differences.
  • (2) Reading a file block repeatedly from the hard disk →\to Caching: Because the exact same block is referenced repeatedly, keeping a high-speed copy resident in main memory eliminates repeated mechanical disk access latency.
AY16/17 S1 Q4a(iii) & AY18/19 S1 Q4a(iv): Buffer vs. cache definitions
  • AY16/17 S1 Q4a(iii): “Caching is used to store data temporarily in memory when they are transferred between devices with different transfer sizes.” — False. Bridging transfer size and speed mismatches during transit is the role of buffering. Caching stores copies of data to accelerate subsequent re-access.
  • AY18/19 S1 Q4a(iv): “Buffer holds a copy of the data that resides elsewhere.” — False. A buffer holds data in transit and frequently holds the sole active copy of data before it is persisted. A cache holds a replica of data residing elsewhere.
Tutorial 12 Q1 (Q1a = AY15/16 S2 Q4a(vi)): Buffering, non-blocking I/O, drivers

Question: Indicate whether the following statements are true or false. Justify your answer. (a) Buffering can be used to improve I/O efficiency for files that are being written and re-read rapidly. (b) Process will be in waiting state after performing an I/O system call if non-blocking I/O is used. (c) Device drivers are part of the kernel I/O subsystem.

Answer (my working; Tutorial 12 solutions are not out yet):

  • (a) False. The lecture defines exactly this use as caching: a fast copy of data that is written and re-read rapidly. Buffering holds data in transit between devices. (The AY15/16 posted student solution says True; the lecture slide supports False.)
  • (b) False. A non-blocking call returns at once, so the process stays Running (or Ready).
  • (c) False, by the lecture’s wording: “the device-driver layer hides the differences among device controllers from the I/O subsystem of the kernel”. Drivers are part of the kernel, but they form their own layer below the kernel I/O subsystem (see the layer figure). Say this distinction explicitly in the answer, since the statement is easy to read the other way.

3. Synchronous, Asynchronous, and Non-blocking I/O

Blocking (synchronous) I/O Asynchronous I/O
1. The process makes an I/O request; it is sent to the device. 1. The process makes an I/O request; it is sent to the device.
2. The process is in the waiting state while the device processes it. 2. The system call returns once the request is queued at the device.
3. The process goes back to the ready queue when the I/O completes. 3. The process keeps executing while the device works.
4. When the I/O completes, the process is signaled.

Non-blocking I/O (in past papers, not in the lecture slides): the call returns at once with whatever data is ready, so the process never enters the waiting state.

I/O is a major factor in system performance: the CPU executes device-driver code, interrupts cause context switches, and data is copied between controllers and memory. Asynchronous I/O plus a double buffer improves performance: while the process works on one buffer, the device fills the other.

AY15/16 S2 Q4a(iv) & AY18/19 S1 Q4a(iii): Process states under non-blocking I/O
  • AY15/16 S2 Q4a(iv): “A process will be in either running or ready state after performing an I/O system call if non-blocking I/O is used.” — True. Non-blocking calls return immediately without suspending execution, keeping the thread in the Running or Ready state.
  • AY18/19 S1 Q4a(iii): “A process will be in waiting state after performing an I/O system call if non-blocking I/O is used.” — False. Only blocking system calls place a process into the Waiting state.
AY16/17 S1 Q4a(v): Asynchronous I/O in Graphical User Interfaces (GUIs)

True. GUI frameworks rely on asynchronous I/O (or worker threads) to handle background disk and network transfers so the primary event-dispatch thread remains responsive to user mouse clicks, keystrokes, and window redraws without freezing.

Double buffering timing (not in the lecture)

Sequential block processing under a single buffer serializes read latency RR and CPU compute time PP:

Single Buffer Time=n(R+P)\text{Single Buffer Time} = n(R + P)

With double buffering, the device controller transfers data into buffer 2 via DMA while the CPU simultaneously processes data in buffer 1:

Double Buffer Time=R+(n−1)⋅max⁡(R,P)+P\text{Double Buffer Time} = R + (n - 1) \cdot \max(R, P) + P

Double buffering achieves pipeline concurrency: per-block throughput is constrained by the bottleneck phase max⁡(R,P)\max(R, P) rather than their sum.

Tutorial 12 Q2: Speeding up a synchronous read loop

Question: In a multiprogramming system, a process reads blocks of a file one at a time into a buffer using synchronous I/O, then processes the data: while (not end of file) { buffer <- read a block using synchronous I/O; process data in buffer; }. (a) Discuss how the performance of this process can be improved. (b) For a system running mainly this type of process, which file allocation scheme is best for I/O performance?

Answer (my working):

  • (a) The process waits for every read and the disk idles while it computes. Use asynchronous I/O with double buffering: start reading block i+1i+1 into the second buffer while processing block ii, so reading and processing overlap (time per block → max⁡(R,P)\max(R, P) instead of R+PR + P). Reading ahead several blocks, or reading larger blocks, also cuts the number of waits.
  • (b) Contiguous allocation. The file is read sequentially, so its blocks sit next to each other: minimal seeks, and no pointer or index blocks to read.

4. Life Cycle of an I/O Request

Servicing a storage read traverses ten discrete stages across user, kernel, and hardware layers:

[User Process]           1. Issues read() system call
       │
[Kernel I/O Subsystem]   2. Checks cache/buffer. (HIT -> copies to user space, returns immediately!)
       │                 3. MISS: Allocates buffer, enqueues request, transitions process to Waiting state
       │
[Device Driver]          4. Converts request into device commands; programs controller registers
       │
[Device Controller]      5. Issues commands to drive hardware; transfers data into controller buffer
       │                 6. Data transfer complete: Asserts hardware INTERRUPT line
       │
[Interrupt Handler]      7. Identifies interrupt source; copies controller data into driver buffer
       │                 8. Signals device driver that transfer has concluded
       │
[Kernel I/O Subsystem]   9. Transfers data from kernel buffer to process address space;
                            transitions process from Waiting -> Ready queue
       │
[User Process]          10. Process scheduled: read() call returns; user execution resumes

5. Hard Disk Geometry and Latency Model

A hard disk drive (HDD) consists of stacked rigid platters spinning on a central spindle, read/written by heads mounted on a shared actuator arm.

  • Track: Concentric circular ring on a platter surface.
  • Sector: Fixed-size arc of a track (standard: 512 bytes or 4096 bytes).
  • Cylinder: The collection of identical circular tracks across all platter surfaces located at a given actuator radial distance. Switching heads within the same cylinder requires no mechanical arm movement.

The disk is addressed as a large 1-dimensional array of logical blocks; a block is the smallest unit of transfer (usually 512 bytes). The array is mapped onto the disk’s sectors sequentially.

Access time

To read a sector, the drive positions the head, then transfers the data:

time for N sectors=seek time+rotational latency⏟positioning time+Nsectors per track×full rotation time⏟transfer time\text{time for } N \text{ sectors} = \underbrace{\text{seek time} + \text{rotational latency}}_{\text{positioning time}} + \underbrace{\frac{N}{\text{sectors per track}} \times \text{full rotation time}}_{\text{transfer time}}

  • Seek time: move the heads to the track (5–25 ms). Disk scheduling minimizes this.
  • Rotational latency: rotate the sector under the head; on average half a rotation.

Lecture example: seek 10 ms, full rotation 8 ms (so latency 4 ms), 512-byte sectors, 1K (1024) sectors per track.

Request Random (each sector positioned separately) Sequential (one positioning per track)
1 sector 10+4+11024×8≈10 + 4 + \frac{1}{1024} \times 8 \approx 14 ms
4 KB = 8 sectors 8×14=8 \times 14 = 112 ms 14+81024×8=14+0.0625≈14 + \frac{8}{1024} \times 8 = 14 + 0.0625 \approx 14 ms
128 KB = 256 sectors 256×14≈256 \times 14 \approx 3.5 s still one track: 14+2561024×8=14+2=14 + \frac{256}{1024} \times 8 = 14 + 2 = 16 ms
1 MB = 2048 sectors 2048×14≈2048 \times 14 \approx 28 s 2 tracks at best: each 14+8=2214 + 8 = 22 ms → 44 ms (3 tracks at worst)

Random I/O pays positioning on every sector; sequential I/O pays it once per track.

With RPM instead of rotation time (not in the lecture): full rotation =60/RPM= 60 / \text{RPM} s, so 7200 RPM → 8.33 ms per rotation, 4.17 ms average latency.

6. Disk Scheduling Algorithms

The OS should use the disk efficiently: fast access time and high disk bandwidth (total bytes transferred divided by the time from the first request to the end of the last transfer). Access time is mostly seek time, and seek time ≈ seek distance, so the algorithms minimize total head movement ∑|cyli+1−cyli|\sum |\text{cyl}_{i+1} - \text{cyl}_i|. The requests come from processes running concurrently.

Consider a 200-cylinder drive (0–1990\text{–}199), head starting at cylinder 53, pending queue: 98, 183, 37, 122, 14, 124, 65, 67.

First-Come, First-Served (FCFS)

Processes requests strictly by arrival order. Intrinsically fair with zero starvation risk, but suffers severe arm thrashing across wide cylinder spans.

Path: 53→98→183→37→122→14→124→65→67\text{Path: } 53 \to 98 \to 183 \to 37 \to 122 \to 14 \to 124 \to 65 \to 67 Total Movement=45+85+146+85+108+110+59+2=𝟔𝟒𝟎 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = \mathbf{640\text{ cylinders}}

Shortest Seek Time First (SSTF)

Always selects the pending request with the minimum seek distance from the current head position (analogous to SJF scheduling).

Path: 53→65→67→37→14→98→122→124→183\text{Path: } 53 \to 65 \to 67 \to 37 \to 14 \to 98 \to 122 \to 124 \to 183 Total Movement=12+2+30+23+84+24+2+59=𝟐𝟑𝟔 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = 12 + 2 + 30 + 23 + 84 + 24 + 2 + 59 = \mathbf{236\text{ cylinders}}

  • Limitation: Susceptible to starvation. Continuous arrivals of requests clustered near the current head position will permanently postpone distant requests.

SCAN (Elevator Algorithm)

The arm starts at one end and moves toward the other end, servicing requests on the way, until it reaches the end of the disk; then it reverses and keeps servicing. Starvation is unlikely, but a request may be delayed. The lecture example has the head moving toward 0.

Path (moving inward toward 0): 53→37→14→𝟎→65→67→98→122→124→183\text{Path (moving inward toward 0): } 53 \to 37 \to 14 \to \mathbf{0} \to 65 \to 67 \to 98 \to 122 \to 124 \to 183 Total Movement=(53−0)+(183−0)=53+183=𝟐𝟑𝟔 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = (53 - 0) + (183 - 0) = 53 + 183 = \mathbf{236\text{ cylinders}}

C-SCAN (Circular SCAN)

Sweeps in a single direction servicing requests until reaching the physical boundary (199199). It then immediately returns to cylinder 0 without servicing requests, and resumes sweeping forward. Provides uniform waiting time distribution.

Path (moving outward): 53→65→67→98→122→124→183→𝟏𝟗𝟗→𝟎→14→37\text{Path (moving outward): } 53 \to 65 \to 67 \to 98 \to 122 \to 124 \to 183 \to \mathbf{199} \to \mathbf{0} \to 14 \to 37 Total Movement=(199−53)+(199−0)+(37−0)=146+199+37=𝟑𝟖𝟐 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = (199 - 53) + (199 - 0) + (37 - 0) = 146 + 199 + 37 = \mathbf{382\text{ cylinders}} (Note: By course convention, the return boundary jump 199→0199 \to 0 is included in total movement).

C-LOOK (and LOOK)

C-LOOK is a version of C-SCAN: the head moves from low to high servicing requests, but when it reaches the last request it returns immediately to the lowest-numbered request (not to cylinder 0), and services upward again. LOOK does the same for SCAN (reverse at the last request instead of the disk edge); the lecture names it only on the selection slide, but past papers use it.

  • C-LOOK Path: 53→65→67→98→122→124→183→𝟏𝟒→3753 \to 65 \to 67 \to 98 \to 122 \to 124 \to 183 \to \mathbf{14} \to 37 Total Movement=(183−53)+(183−14)+(37−14)=130+169+23=𝟑𝟐𝟐 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = (183 - 53) + (183 - 14) + (37 - 14) = 130 + 169 + 23 = \mathbf{322\text{ cylinders}}
  • LOOK Path (inward first): 53→37→𝟏𝟒→65→67→98→122→124→18353 \to 37 \to \mathbf{14} \to 65 \to 67 \to 98 \to 122 \to 124 \to 183 Total Movement=(53−14)+(183−14)=39+169=𝟐𝟎𝟖 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = (53 - 14) + (183 - 14) = 39 + 169 = \mathbf{208\text{ cylinders}}

The lecture asks whether SCAN, C-SCAN and C-LOOK really solve starvation. They make it unlikely (every request is reached within a sweep), but a request can still wait up to a full sweep, and with C-SCAN about two.

Selecting an algorithm

  • SSTF is common and has a natural appeal.
  • SCAN and C-SCAN (or LOOK and C-LOOK) perform better under heavy disk load, since starvation is unlikely.
  • Performance depends on the number and types of requests.
  • The file-allocation method shapes the requests: reading a contiguous file gives requests close together; a linked or indexed file may give requests far apart (more head movement).
Tutorial 12 Q3: Why SCAN looked no better than FCFS

Question: (a) A salesman says his company’s UNIX disk driver uses SCAN and also queues multiple requests within a cylinder in sector order. You wrote a program that randomly reads 10,000 blocks spread across the disk, and measured the same performance as FCFS. Was the salesman lying? (b) Under what circumstances could a disk scheduling discipline not improve, or even degrade, performance?

Answer (my working):

  • (a) Not necessarily. The program issues one synchronous read at a time: it waits for each block before asking for the next. The disk queue therefore never holds more than one request, so SCAN has nothing to reorder and serves requests in arrival order, exactly like FCFS.
  • (b) When the queue is short (light load, one request at a time, synchronous I/O), every algorithm reduces to FCFS. Scheduling can even hurt: computing the order adds overhead; SSTF and SCAN can starve or delay far requests; reordering can work against the file system’s own layout (e.g. contiguous files read in order) or against what the drive’s controller already does internally.

7. Disk Management & RAID Systems

Disk preparation requires three progressive operations:

  1. Low-level (Physical) Formatting: Writes sector headers, trailers, and Error Correcting Codes (ECC) onto blank magnetic tracks.
  2. Partitioning: Segments disk platters into contiguous groups of cylinders treated by the OS as distinct logical volumes.
  3. Logical Formatting: Allocates OS filesystem data structures (inodes, superblock, root directory, free allocation tables).

Disk Striping & Mirroring

  • Data Striping: Distributes consecutive blocks across an array of nn independent drives. Drive for block i=(imod⁡n)+1\text{Drive for block } i = (i \bmod n) + 1 Permits simultaneous parallel I/O streaming, drastically improving throughput.
  • Disk Mirroring: Writes duplicate copies of all data blocks to a shadow drive, ensuring fault tolerance at the cost of double drive hardware.

RAID Architecture Levels

RAID (Redundant Array of Independent Disks) improves performance and reliability by storing redundant data.

  • RAID 0 (Striping): non-redundant striping. Maximum throughput, zero fault tolerance (a single drive failure destroys the entire array).
  • RAID 1 (Mirroring): Full drive duplication. 100% capacity redundancy overhead.
  • RAID 0+1 (Mirror of Stripes): Disks are divided into two striped sets (RAID 0), and one set is mirrored onto the other.
    • Failure mode: If one disk fails, its entire stripe set becomes unavailable; the system degrades to a single striped set. A second disk failure in the surviving set causes catastrophic data loss.
  • RAID 1+0 (Stripe of Mirrors): Disks are paired into mirrored sets (RAID 1), and data is striped across the mirrored pairs.
    • Failure mode: If one disk fails, only its individual mirror partner is degraded. The array remains operational and can tolerate multiple concurrent drive failures, provided no two failed drives share the same mirrored pair. RAID 1+0 provides vastly superior reliability over RAID 0+1.
AY18/19 S2 Q4a(iv): Storage capacity under RAID 1+0

Four 200 GB hard disks configured under RAID 1+0 form two mirrored pairs of 200 GB each, striped together. Because half the total storage is dedicated to mirror replicas: Usable Capacity=4×200 GB2=𝟒𝟎𝟎 𝐆𝐁\text{Usable Capacity} = \frac{4 \times 200\text{ GB}}{2} = \mathbf{400\text{ GB}}

AY16/17 S1 Q4a(vi): Reliability comparison between RAID 0+1 and RAID 1+0

“Mirror of stripes (RAID 0+1) has better reliability than stripes of mirrors (RAID 1+0).” — False. RAID 1+0 provides superior fault tolerance. In RAID 1+0, an isolated disk failure only impacts its paired mirror partner, allowing the array to survive additional disk failures across other mirrored pairs. In RAID 0+1, a single failure invalidates an entire striped half, leaving the array completely vulnerable to any subsequent disk crash.

AY15/16 S2 Q4a(v): RAID level 1 refers to non-redundant striping. False. That is RAID 0; RAID 1 is mirroring.

(i) Total Head Movement:

  • SCAN: Path: 100→102→105→150→𝟏𝟗𝟗→89→85→63\text{Path: } 100 \to 102 \to 105 \to 150 \to \mathbf{199} \to 89 \to 85 \to 63 Movement=(199−100)+(199−63)=99+136=𝟐𝟑𝟓 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Movement} = (199 - 100) + (199 - 63) = 99 + 136 = \mathbf{235\text{ cylinders}}
  • C-SCAN: Path: 100→102→105→150→𝟏𝟗𝟗→𝟎→63→85→89\text{Path: } 100 \to 102 \to 105 \to 150 \to \mathbf{199} \to \mathbf{0} \to 63 \to 85 \to 89 Movement=(199−100)+(199−0)+(89−0)=99+199+89=𝟑𝟖𝟕 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Movement} = (199 - 100) + (199 - 0) + (89 - 0) = 99 + 199 + 89 = \mathbf{387\text{ cylinders}}

(ii) Advantage of C-SCAN over SCAN: C-SCAN provides more uniform waiting times. Under bidirectional SCAN, cylinders near the center are visited twice per complete cycle, whereas boundary cylinders are visited only once per cycle. C-SCAN sweeps in one direction only, ensuring all cylinder requests experience equalized maximum wait bounds.

AY18/19 S1 Q4c: SSTF servicing order and starvation mitigation

Given: Head at 100. Pending queue: 150, 110, 80, 160, 5, 190. (i) Servicing Order:

  • From 100: nearest is 110 (dist: 10)
  • From 110: nearest is 80 (dist: 30 vs. 40 to 150)
  • From 80: nearest is 150 (dist: 70 vs. 75 to 5)
  • From 150: nearest is 160 (dist: 10)
  • From 160: nearest is 190 (dist: 30)
  • From 190: nearest is 5 (dist: 185) Servicing Order: 110, 80, 150, 160, 190, 5.

(ii) Starvation Cause & Solutions:

  • Cause: SSTF greedily prioritizes local requests. Under heavy incoming load, if new requests continuously arrive near current head locations, requests at distant cylinders (such as cylinder 5) may be starved indefinitely.
  • Solutions: Implement aging (incrementing request priorities based on wait duration) or replace SSTF with SCAN / LOOK / C-SCAN which enforce directional bounded service intervals.
AY18/19 S2 Q4d: Equivalence of SSTF and LOOK execution sequences

Given: Head at 90 (previous cylinder was 85 ⟹\implies moving outward). Queue: 20, 100, 40, 60, 75, 120, 160. Result: SSTF and LOOK yield the IDENTICAL servicing sequence:

  • LOOK: Continues outward servicing all higher cylinders: 100, 120, 160. At 160 (the outward limit), reverses inward servicing remaining requests in decreasing order: 75, 60, 40, 20.
  • SSTF:
    • At 90: nearest is 100 (dist 10 vs. 15 to 75).
    • At 100: nearest is 120 (dist 20 vs. 25 to 75).
    • At 120: nearest is 160 (dist 40 vs. 45 to 75).
    • At 160: nearest remaining is 75, then sequentially down through 60, 40, 20. Both algorithms execute the sequence: 100, 120, 160, 75, 60, 40, 20.
AY19/20 S1 Q4c: SSTF vs. FCFS total movement and fairness evaluation

Given: Head at 100. Arrival queue: 45, 134, 88, 110, 74, 150. (i) SSTF Order & Head Movement:

  • From 100 →\to 110 (10) →\to 88 (22) →\to 74 (14) →\to 45 (29) →\to 134 (89) →\to 150 (16). Total Movement=10+22+14+29+89+16=𝟏𝟖𝟎 𝐜𝐲𝐥𝐢𝐧𝐝𝐞𝐫𝐬\text{Total Movement} = 10 + 22 + 14 + 29 + 89 + 16 = \mathbf{180\text{ cylinders}}
