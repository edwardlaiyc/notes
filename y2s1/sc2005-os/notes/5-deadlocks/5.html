In a multiprogramming environment, concurrent processes compete for a finite set of shared system resources (printers, memory blocks, database locks, semaphore permits). If processes request resources held by other waiting processes, execution can grind to a halt.

A deadlock occurs when a set of concurrent processes are permanently blocked because each process holds resources while waiting for other resources held by other processes in the set.

1. Deadlock Definition and The Bridge Analogy

A set of processes is deadlocked when every process in the set is waiting for an event that only another process in the same set can cause:

  • The Bridge Analogy: Traffic moves in both directions across a narrow, single-lane bridge. If two vehicles drive onto the bridge from opposite ends, neither can advance. Deadlock can be resolved only if one car preempts its claim, backs up (rolls back), and releases the contested road segment.
  • Deadlock vs. Starvation:
    • In a deadlock, every process in the set is waiting for another blocked process; zero progress occurs system-wide.
    • In starvation, a low-priority process waits indefinitely while other processes successfully execute and progress.
  • Minimum Size: A deadlock requires a minimum of two processes and two non-preemptible resource instances.

2. The Four Necessary Conditions for Deadlock

Deadlock can arise if and only if all four Coffman conditions hold simultaneously in the system:

Condition Formal Meaning Physical Real-World Interpretation
1. Mutual Exclusion At least one resource must be held in a non-shareable mode. Only one process at a time can use the resource. If another process requests it, that process must wait.
2. Hold and Wait A process must be holding at least one resource and actively waiting to acquire additional resources held by others. Processes do not release currently held allocations while queued for pending ones.
3. No Preemption Resources cannot be forcibly taken away from a process. A resource can be released only voluntarily by the holding process after completing its task.
4. Circular Wait A closed directed chain of waiting processes exists: {P0,P1,…,Pn}\{P_0, P_1, \dots, P_n\} such that P0P_0 waits for a resource held by P1P_1, P1P_1 waits for P2P_2, …\dots, and PnP_n waits for P0P_0. Circular dependency of resource claims.

[!IMPORTANT] Necessary vs. Sufficient:

  • All 4 conditions are strictly necessary for deadlock. If you break even one condition, deadlock is mathematically impossible.
  • However, conditions 1, 2, and 3 alone are not sufficient to guarantee deadlock—deadlock occurs only when a circular wait forms.

3. Resource-Allocation Graphs (RAG)

Deadlocks can be precisely modeled using a directed graph G=(V,E)G = (V, E) consisting of processes (circles) and resource types (boxes containing dots representing instances):

  • Request Edge (Pi→RjP_i \to R_j): Process PiP_i has requested an instance of resource type RjR_j and is currently waiting.
  • Assignment Edge (Rj→PiR_j \to P_i): An instance of resource type RjR_j has been allocated to process PiP_i.

Step-by-Step Method: Cycle Analysis in Resource Graphs

Is there a directed cycle in the graph?
   ├── NO  ──> System is NOT deadlocked.
   └── YES ──> Check instance counts per resource type:
          ├── Exactly 1 instance per resource type ──> DEADLOCK DEFINITELY EXISTS.
          └── Multiple instances per resource type ──> DEADLOCK IS POSSIBLE (Run Graph Reduction).

Graph Reduction Procedure for Multiple Instances

  1. Find a process PiP_i whose pending requests can be completely satisfied by currently available unallocated instances.
  2. If found, assume PiP_i finishes: erase all its edges and return all its held allocations to the free pool.
  3. Repeat iteratively. If all processes can be erased, no deadlock exists. If unallocated resources cannot satisfy any remaining process, the unreduced processes are deadlocked.

4. Handling Deadlocks: Four Paradigms

  1. Deadlock Prevention: Design structural protocols that ensure at least one of the four necessary conditions can never hold.
  2. Deadlock Avoidance: The OS uses a priori knowledge of maximum resource demands to dynamically ensure the system remains in a safe state.
  3. Deadlock Detection and Recovery: Allow deadlocks to occur, periodically execute graph-detection algorithms, and recover via process termination or preemption.
  4. Deadlock Ignorance (The Ostrich Algorithm): Ignore the problem completely and assume deadlocks never occur. Used by Linux, Windows, and macOS because handling overhead outweighs the frequency of deadlocks.

5. Deadlock Prevention

Deadlock prevention invalidates one of the four Coffman conditions:

Target Condition Prevention Mechanism Practical Limitation / Cost
Mutual Exclusion Make all resources shareable (e.g. read-only files). Impossible in practice for inherently dedicated hardware (printers, tape drives, mutex locks).
Hold and Wait Protocol A: A process must request and receive all required resources simultaneously before beginning execution.
Protocol B: A process must release all currently held resources before requesting any new ones.		 Severe resource underutilization: Resources held for long periods are used only briefly. Processes requiring popular resources suffer starvation.
No Preemption If a process holding resources requests an unavailable resource, all its currently held resources are forcibly preempted. Applicable only to resources whose state can be easily saved and restored (CPU registers, RAM pages). Unworkable for disks or locks.
Circular Wait Impose a global total ordering function F:R→ℕF: R \to \mathbb{N} on all resource types. A process can request a resource RjR_j if and only if F(Rj)>F(Ri)F(R_j) > F(R_i) for all currently held resources RiR_i. Most practical prevention technique. (Used in OS kernels). Forces programmers to write resource requests in strict hierarchical order.
Tutorial 6 Q1 & Q2: Deadlock Conditions and Prevention Rules
  • Tutorial 6 Q1 (Circular Wait via Total Ordering):
    • Question: Why does global resource ordering prevent circular wait?
    • Proof: Suppose a circular wait exists: P0→P1→…→Pn→P0P_0 \to P_1 \to \dots \to P_n \to P_0, where each process PkP_k holds Rh(k)R_{h(k)} and waits for Rw(k)R_{w(k)}. By the ordering rule, PkP_k can only request Rw(k)R_{w(k)} if F(Rw(k))>F(Rh(k))F(R_{w(k)}) > F(R_{h(k)}). Summing these inequalities around the cycle yields F(R0)<F(R1)<…<F(Rn)<F(R0)F(R_0) < F(R_1) < \dots < F(R_n) < F(R_0), which is a logical contradiction (F(R0)<F(R0)F(R_0) < F(R_0)). Thus, no cycle can form.
  • Tutorial 6 Q2 (Hold and Wait Protocols):
    • Requiring processes to hold all resources at once guarantees safety, but severely degrades throughput because idle resources cannot be borrowed by other ready processes.

6. Deadlock Avoidance: Safe States and The Banker’s Algorithm

Instead of imposing rigid structural restrictions, deadlock avoidance dynamically inspects every resource request. If granting the request could lead to a deadlock, the request is deferred.

Safe States

A state is safe if there exists at least one safe sequence ⟨P1,P2,…,Pn⟩\langle P_1, P_2, \dots, P_n \rangle of processes such that for each PiP_i, the maximum remaining resources PiP_i can still request can be satisfied by: 𝐂𝐮𝐫𝐫𝐞𝐧𝐭𝐥𝐲 𝐀𝐯𝐚𝐢𝐥𝐚𝐛𝐥𝐞 𝐑𝐞𝐬𝐨𝐮𝐫𝐜𝐞𝐬+∑j<iResources Allocated to Pj\mathbf{\text{Currently Available Resources}} + \sum_{j < i} \text{Resources Allocated to } P_j

  • Safe State ⟹\implies NO DEADLOCK.
  • Unsafe State ⟹\implies Deadlock is POSSIBLE. (An unsafe state is not automatically a deadlock; it simply means the OS can no longer prevent processes from deadlocking if they all suddenly demand their maximum claims).
  • Avoidance Rule: Never grant a request if doing so transitions the system from a Safe State to an Unsafe State.

The Banker’s Algorithm Data Structures

For nn processes and mm resource types:

  • Available[m]\text{Available}[m]: Vector of length mm. Available[j]=k\text{Available}[j] = k means kk instances of resource type RjR_j are free.
  • Max[n][m]\text{Max}[n][m]: Matrix n×mn \times m. Max[i][j]=k\text{Max}[i][j] = k means process PiP_i may request at most kk instances of RjR_j.
  • Allocation[n][m]\text{Allocation}[n][m]: Matrix n×mn \times m. Allocation[i][j]=k\text{Allocation}[i][j] = k means PiP_i currently holds kk instances of RjR_j.
  • Need[n][m]\text{Need}[n][m]: Matrix n×mn \times m. Remaining claim of each process: 𝐍𝐞𝐞𝐝[𝒊][𝒋]=𝐌𝐚𝐱[𝒊][𝒋]−𝐀𝐥𝐥𝐨𝐜𝐚𝐭𝐢𝐨𝐧[𝒊][𝒋]\mathbf{\text{Need}[i][j] = \text{Max}[i][j] - \text{Allocation}[i][j]}

Step-by-Step Method 1: The Safety Algorithm

To test if a state is safe and find a safe sequence:

  1. Initialize: Work=Available,Finish[i]=false for i=0,1,…,n−1\text{Work} = \text{Available}, \quad \text{Finish}[i] = \text{false for } i = 0, 1, \dots, n-1
  2. Find an index ii such that: Finish[i]==falseandNeedi≤Work\text{Finish}[i] == \text{false} \quad \text{and} \quad \text{Need}_i \le \text{Work} (If no such ii exists, skip to Step 4).
  3. Process PiP_i can safely finish: Work=Work+Allocationi,Finish[i]=true\text{Work} = \text{Work} + \text{Allocation}_i, \quad \text{Finish}[i] = \text{true} Record PiP_i in the safe sequence. Return to Step 2.
  4. Verdict:
    • If Finish[i]==true\text{Finish}[i] == \text{true} for all i⟹i \implies The system is in a SAFE STATE. The list of recorded processes is a valid safe sequence.
    • If any Finish[i]==false⟹\text{Finish}[i] == \text{false} \implies The system is in an UNSAFE STATE.

Step-by-Step Method 2: Handling a Resource Request (RequestAlgorithm)

When process PiP_i requests vector Requesti\text{Request}_i:

  1. Sanity Check: If Requesti≤Needi\text{Request}_i \le \text{Need}_i, proceed to Step 2. Otherwise, raise error (process exceeded maximum declared claim).
  2. Availability Check: If Requesti≤Available\text{Request}_i \le \text{Available}, proceed to Step 3. Otherwise, PiP_i must wait (insufficient resources).
  3. Pretend to Allocate (Tentative State): Available=Available−RequestiAllocationi=Allocationi+RequestiNeedi=Needi−Requesti\begin{aligned} \text{Available} &= \text{Available} - \text{Request}_i \\ \text{Allocation}_i &= \text{Allocation}_i + \text{Request}_i \\ \text{Need}_i &= \text{Need}_i - \text{Request}_i \end{aligned}
  4. Run the Safety Algorithm on the tentative state:
    • If Safe: Formally grant the request ⟹Pi\implies P_i receives resources.
    • If Unsafe: Deny the request ⟹\implies Roll back to original values; PiP_i must wait.

Step-by-Step Method 3: Finding the Minimum Available Vector for Safety

When an exam asks: “What is the minimum value of Available\text{Available} for the state to be safe?”

  1. For at least one process PkP_k to complete first, the initial Available\text{Available} must satisfy: Available≥Needk\text{Available} \ge \text{Need}_k
  2. To minimize Available\text{Available}, pick the process with the smallest Need\text{Need} vector across all components.
  3. Set Available=Needk\text{Available} = \text{Need}_k (component-wise).
  4. Run the Safety Algorithm with this candidate vector to confirm that all subsequent processes can cascade to completion. If a downstream process gets stuck, increase Available\text{Available} component-wise by the deficit.
