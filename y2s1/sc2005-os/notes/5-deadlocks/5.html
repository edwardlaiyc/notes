Processes compete for a finite set of resources. When each process in a group holds something another one needs, and none will let go, the whole group stops. This chapter defines that state, gives the four conditions it needs, and covers the two ways the course handles it: prevention (break a condition) and avoidance (the Banker’s algorithm). Deadlock detection is in the lecture but marked not examinable.

1. The Deadlock Problem

A deadlock is a set of blocked processes, each holding a resource and waiting for a resource held by another process in the set.

  • Tape drives: the system has two tape drives; P1P_1 and P2P_2 each need both. Each holds one and waits for the other.
  • Semaphores A=B=1A = B = 1: P0P_0 runs wait(A); wait(B); and P1P_1 runs wait(B); wait(A);. A context switch after each first wait deadlocks them.

Bridge crossing: only one car fits on the bridge, so the bridge is a shared resource. A deadlock is resolved if one car backs up (releases the resource and rolls back); several cars may have to back up.

A deadlock needs at least two processes: one process alone cannot hold-and-wait against itself.

System model

  • Resource types R1,…,RmR_1, \dots, R_m (memory space, I/O devices, semaphores). Type RiR_i has WiW_i identical instances.
  • Each process uses a resource in three steps: request a number of instances, use them, release them.

2. Resource-Allocation Graph (RAG)

The vertices are the processes P={P1,…,Pn}P = \{P_1, \dots, P_n\} (circles) and the resource types R={R1,…,Rm}R = \{R_1, \dots, R_m\} (boxes, one dot per instance). There are two kinds of directed edge:

Edge Meaning Removed when
Request Pi→RjP_i \to R_j PiP_i waits for an instance of RjR_j the request is granted
Assignment Rj→PiR_j \to P_i PiP_i holds an instance of RjR_j the resource is released
Graph Verdict
No cycle → no deadlock. Run order P3→P2→P1P_3 \to P_2 \to P_1 meets every request.
Cycle, and the processes on it are stuck → deadlock.
Cycle, but other instances exist → no deadlock. Order P2→P4→P3→P1P_2 \to P_4 \to P_3 \to P_1.

Basic facts:

  • No cycle → no deadlock.
  • Cycle, and one instance per resource type → deadlock.
  • Cycle, and several instances per type → deadlock possible, not certain.

Method for a multi-instance RAG: find a process whose outstanding requests the free instances can satisfy; let it finish, return everything it holds, and erase its edges. Repeat. Processes that can never be erased are deadlocked.

AY19/20 S1 Q2b: Build a RAG from a request sequence

Question: Construct the resource-allocation graph for the following sequence of requests. Assume there is only one instance of each resource type. Is the system deadlocked? Justify. P1 requests R; P2 requests S; P3 requests T; P1 requests S; P3 requests R.

Solution:

  • Granted: R→P1R \to P_1, S→P2S \to P_2, T→P3T \to P_3. Waiting: P1→SP_1 \to S (held by P2P_2), P3→RP_3 \to R (held by P1P_1).
  • Path: P3→R→P1→S→P2P_3 \to R \to P_1 \to S \to P_2. P2P_2 requests nothing more, so there is no cycle → no deadlock.
  • P2P_2 finishes and releases SS → P1P_1 gets SS, finishes, releases RR and SS → P3P_3 gets RR and finishes.
Tutorial 6 Q1: True/false on deadlock basics

Question: Indicate whether the following statements are true or false. Justify your answers. (a) In the dining-philosopher problem with five philosophers, if we allow at most four of them to be hungry simultaneously, deadlock may still occur. (b) It is impossible to have a deadlock involving only one single process. (c) If a resource allocation graph contains a cycle, then a deadlock has occurred.

Answer:

  • (a) False. With at most four hungry philosophers and five chopsticks, at least one of them gets both chopsticks.
  • (b) True. The hold-and-wait condition can never be satisfied with a single process.
  • (c) False. It depends on the number of instances per resource type.
Past-paper T/F: Graphs and conditions
  • AY16/17 S1 Q1a(iv): Deadlocks can occur even if the resource allocation graph does not have a cycle. False. No cycle means no deadlock.
  • AY17/18 S1 Q1a(ii): (RAG with a cycle where R1 has two instances) The system is deadlocked. False. The second instance of R1 lets P1 continue and break the cycle.
  • AY17/18 S2 Q2a(iii): Desktop operating systems like Windows never have deadlock issues. False. Windows ignores deadlocks (pretends they never occur), because prevention or detection costs constant overhead.

3. The Four Deadlock Conditions

Deadlock may arise if all four hold at the same time. They are necessary but not sufficient: all four can hold without a deadlock (for example, a cycle through multi-instance resources).

Condition Meaning
1. Mutual exclusion Only one process at a time can use a resource instance.
2. Hold and wait A process holding at least one resource waits for more resources held by other processes.
3. No preemption A resource is released only voluntarily, by the process holding it, after it finishes its task.
4. Circular wait Waiting processes {P0,…,Pn}\{P_0, \dots, P_n\} exist where P0P_0 waits for P1P_1, P1P_1 for P2P_2, …, PnP_n for P0P_0.

4. Handling Deadlocks

The lecture gives three methods:

  1. Ensure the system never enters a deadlock state: prevention (§5) or avoidance (§6).
  2. Allow deadlock, then detect and recover (detection is not examinable).
  3. Ignore the problem and pretend deadlocks never occur. Used by most operating systems, including UNIX (and Windows).

5. Deadlock Prevention

Prevent at least one of the four conditions. The lecture illustrates each with the dining philosophers (chapter 4): each chopstick is a binary semaphore, and philosopher ii runs wait(chopstick[i]); wait(chopstick[(i+1)%5]); eat; signal(...); signal(...); think.

Condition How to break it (general) Dining philosophers
Mutual exclusion Make the resource shareable. Often impossible. Chopsticks cannot be shared at the same time, so this condition cannot be eliminated.
Hold and wait Whenever a process requests a resource, it must hold no other resource. Pick up chopsticks only if both are available.
No preemption If a request cannot be granted, the process releases what it holds. If a philosopher cannot get the second chopstick, it releases the first.
Circular wait Impose an order on resources; request only in increasing order. (1) At most four philosophers hungry at once. (2) Odd–even: odd philosophers take left then right, even ones right then left. (3) Acquire chopsticks only in order (figure).

With ordered chopsticks A < B < C < D < E, the philosopher between E and A must take A first. A cycle would need every philosopher to hold a lower chopstick while waiting for a higher one, which is impossible around a closed ring.

6. Deadlock Avoidance

The avoidance algorithm examines the resource-allocation state each time a process requests an available resource. If immediate allocation leaves the system safe, grant it; otherwise the process waits. The system never enters an unsafe state.

Safe state

A completion sequence ⟨P1,P2,…,Pn⟩\langle P_1, P_2, \dots, P_n \rangle is safe if, for each PiP_i, the resources PiP_i may still request can be satisfied by the currently available resources plus the resources held by all PjP_j with j<ij < i. Then PiP_i waits for the earlier processes to finish, takes what it needs, runs, returns everything, and so on down the list.

The system is in a safe state if at least one safe sequence exists.

Lecture example: Available = 1.

P1P_1 P2P_2 P3P_3
Hold 1 1 1
Request 1 2 3
  • ⟨P1,P2,P3⟩\langle P_1, P_2, P_3 \rangle: 1≤11 \le 1; 2≤1+12 \le 1 + 1; 3≤1+1+13 \le 1 + 1 + 1 → safe.
  • ⟨P3,P2,P1⟩\langle P_3, P_2, P_1 \rangle: 3>13 > 1 → not safe.
  • Is the system safe? Yes: one safe sequence exists. Other unsafe orderings do not matter.
  • Safe → no deadlock.
  • Unsafe → deadlock is possible, not certain: if a process releases resources well before it completes, deadlock may not occur.
  • Deadlock → unsafe.

Banker’s algorithm

Checks whether granting a request could lead to an unsafe state, for multiple instances of each resource type. Assumptions: each process declares in advance the maximum instances of each type it may need, and a process that gets all its resources returns them in finite time.

nn processes, mm resource types:

Structure Size Meaning
Available mm Available[j] = k: kk instances of RjR_j are free
Max n×mn \times m Max[i,j] = k: PiP_i may request at most kk of RjR_j
Allocation n×mn \times m Allocation[i,j] = k: PiP_i holds kk of RjR_j
Need n×mn \times m Need[i,j] = k: PiP_i may need kk more of RjR_j

Need=Max−Allocation\text{Need} = \text{Max} - \text{Allocation}

V1≤V2V_1 \le V_2 means V1[j]≤V2[j]V_1[j] \le V_2[j] for every jj.

Part 1: safety algorithm

  1. Work = Available; Finish[i] = false for all ii.
  2. Find ii with Finish[i] == false and Need[i] ≤ Work. If none, go to step 4. (If several fit, any choice works.)
  3. Work = Work + Allocation[i]; Finish[i] = true; go to step 2. (Work is Available plus everything held by the finished processes.)
  4. If Finish[i] == true for all ii, the state is safe; the order found is a safe sequence. Otherwise it is unsafe.

Part 2: resource-request algorithm for request vector Requesti\text{Request}_i:

  1. If Requesti≤Needi\text{Request}_i \le \text{Need}_i, go on; otherwise error (the process exceeded its maximum claim).
  2. If Requesti≤Available\text{Request}_i \le \text{Available}, go on; otherwise PiP_i waits (resources not available).
  3. Pretend to allocate: Available -= Request_i; Allocation_i += Request_i; Need_i -= Request_i.
  4. Run the safety algorithm. Safe → allocate. Unsafe → PiP_i waits and the old state is restored.

Tutorial 6 Q3: Minimum unknowns in Available

Question: Five processes P0–P4 and four resource types A–D. Available = (0, x, y, 1). Process P3 requests (A=0, B=0, C=0, D=1) next. Compute the minimum values of x and y so that this request can be granted and the resulting state is safe. Show the safety steps.

Allocation ABCD Need ABCD
P0 2 2 0 0 1 4 0 0
P1 3 1 0 0 0 1 0 0
P2 1 1 0 0 1 0 0 0
P3 0 0 1 1 0 0 1 1
P4 0 0 1 1 0 0 3 2

Solution:

  1. The request fits Need₃ (0011) and Available (D = 1). Pretend: Available = (0,x,y,0)(0, x, y, 0), Alloc₃ = 0012, Need₃ = 0010.
  2. Split the problem: A and B are used only by P0–P2; C and D only by P3 and P4.
  3. x: P1 and P2 can run with x=1x = 1 and return B = 1 + 1. P0 needs B = 4, so x+2≥4x + 2 \ge 4 → x≥2x \ge 2.
  4. y: P3 can run with y=1y = 1 and return C = 1. P4 needs C = 3, so y+1≥3y + 1 \ge 3 → y≥2y \ge 2. (D: P4 needs 2; P3 returns 2.)
  5. Minimum x = 2, y = 2. Check from (0,2,2,0):
Work Run Need ≤ Work Work after
0220 P1 0100 3320
3320 P2 1000 4420
4420 P3 0010 4432
4432 P0 1400 6632
6632 P4 0032 6643

Safe sequence ⟨P1,P2,P3,P0,P4⟩\langle P_1, P_2, P_3, P_0, P_4 \rangle.

Additional Practice Q3 (also AY16/17 S1 Q2b): Minimum x for a safe state

Question: Four processes P0–P3 and three resource types A, B, C. Available = (0, 1, x). Compute the minimum value for x so that this system state is safe.

Allocation ABC Need ABC
P0 2 1 1 0 1 0
P1 1 1 0 2 1 2
P2 1 1 1 2 0 1
P3 1 1 1 4 1 0

Solution: Look for an order that never needs C from Available.

  1. P0 (Need 010 ≤ 01x) → Work = (2,2,x+1)(2, 2, x+1).
  2. P2 (Need 201): needs C = 1 ≤ x+1x + 1, true for x=0x = 0 → Work = (3,3,x+2)(3, 3, x+2).
  3. P1 (Need 212): needs C = 2 ≤ x+2x + 2 → Work = (4,4,x+2)(4, 4, x+2).
  4. P3 (Need 410) → Work = (5,5,x+3)(5, 5, x+3).

Every step holds with x=0x = 0, so the minimum is x = 0, sequence ⟨P0,P2,P1,P3⟩\langle P_0, P_2, P_1, P_3 \rangle.

AY18/19 S1 Q2b: Totals, safety, minimum Available, request

Question: Five processes P1–P5 and two resource types A, B. Available = (4, 3).

Allocation AB Max AB
P1 0 1 3 3
P2 1 0 4 5
P3 0 1 5 4
P4 1 0 3 3
P5 0 0 5 5

(i) What are the total numbers of instances of A and B? (ii) Is the state safe? (iii) What are the minimum values required in Available to ensure the system is safe? (iv) P2 requests 3 instances each of A and B. Is it safe to grant?

Solution:

  • (i) Total = Available + all Allocation: A = 4 + 2 = 6, B = 3 + 2 = 5.
  • (ii) Need: P1 32, P2 35, P3 53, P4 23, P5 55. Work 43 → P1 → 44 → P4 → 54 → P3 → 55 → P2 → 65 → P5 → 65. Safe, ⟨P1,P4,P3,P2,P5⟩\langle P_1, P_4, P_3, P_2, P_5 \rangle.
  • (iii) Try smaller vectors:
    • (3,3): P1 → 34 → P4 → 44; P3 needs A = 5, P2 needs B = 5 → stuck. Unsafe.
    • (3,4): P1 → 35 → P4 → 45 → P2 → 55 → P3 → 56 → P5. Safe.
    • (4,3): the given state, safe. (4,2) and (2,4) are unsafe.
    • Minimum: (3,4) or (4,3).
  • (iv) (3,3) ≤ Need₂ (3,5) and ≤ Available (4,3). Pretend: Available = (1,0), Need₂ = (0,2). No Need ≤ (1,0). Unsafe → do not grant.

Q2a(v): A system is not safe if there is at least one unsafe sequence of process executions. False. It is safe if at least one safe sequence exists, whatever the other orders do.

AY18/19 S2 Q2a(iii): Avoidance and requests

Deadlock avoidance allows processes to request for resources at will. True. Processes may request at any time (within their declared maximum); the avoidance algorithm only grants a request if the resulting state is safe.

7. Deadlock Detection (not examinable)

The system allows deadlock, runs a detection algorithm, then recovers. For multiple instances the detection algorithm looks like the safety algorithm, but uses the current Request matrix instead of Need, and starts with Finish[i] = true for processes holding nothing. Any process left with Finish[i] == false is deadlocked. The lecture marks this part and its examples not examinable.
