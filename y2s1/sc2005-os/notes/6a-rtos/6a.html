General-purpose operating systems optimize for average throughput and interactive responsiveness. However, in safety-critical, embedded, and cyber-physical systems, timing is a strict correctness criterion.

In a Real-Time Operating System (RTOS), a late result is equivalent to an incorrect result. This chapter examines the characteristics of real-time workloads, formal task parameters, and the two foundational real-time CPU scheduling algorithms: Rate Monotonic (RM) and Earliest Deadline First (EDF).

1. What Defines a Real-Time System?

Timeliness and Worst-Case Predictability

A real-time system is correct if and only if:

  1. It delivers the logically correct output.
  2. It delivers the output before its specified deadline.

[!IMPORTANT] “Real-Time” Does NOT Mean “Fast”: Real-time computing is defined by worst-case determinism and predictability, not raw processing speed. A blazing-fast general-purpose processor that completes 99.9% of computations in 1 ms but occasionally delays a task by 100 ms due to cache misses or page faults is unacceptable for real-time control (such as deploying an automotive airbag).

The Cyber-Physical Feedback Loop

Real-time embedded systems repeatedly execute three sequential phases: 𝐒𝐞𝐧𝐬𝐞→𝐃𝐞𝐜𝐢𝐝𝐞→𝐀𝐜𝐭\mathbf{\text{Sense}} \quad \longrightarrow \quad \mathbf{\text{Decide}} \quad \longrightarrow \quad \mathbf{\text{Act}}

  1. Sense: Sample analog sensors (accelerometers, radar, temperature probes).
  2. Decide: Compute a mathematical control law on the sampled input.
  3. Act: Issue commands to physical actuators (brakes, thrusters, steering motors) within a bounded time window.

Why Desktop OSs (Windows/Linux) Are NOT Real-Time

General-purpose desktop operating systems are time-sharing systems designed to maximize fairness and average-case throughput for human users. They use virtual memory paging, background kernel daemons, and dynamic priority boosts—features that introduce non-deterministic latencies incompatible with strict deadlines.

2. Characterizing Real-Time Workloads

Single Process Specification: ⟨R,C,D⟩\langle R, C, D \rangle

An individual real-time task is defined by a 3-tuple:

  • Release Time (RR): The physical time instant at which the task becomes ready for execution.
  • Computation Time (CC): The worst-case CPU execution time required by the task.
  • Relative Deadline (DD): The allowable time interval after release within which the task must complete.

𝐀𝐛𝐬𝐨𝐥𝐮𝐭𝐞 𝐃𝐞𝐚𝐝𝐥𝐢𝐧𝐞=R+D\mathbf{\text{Absolute Deadline}} = R + D

Periodic Process Specification: ⟨T,C,D⟩\langle T, C, D \rangle

Most real-time tasks repeat cyclically:

  • Period (TT): The constant time interval between consecutive task releases.
  • Computation Time (CC): CPU time needed per instance.
  • Relative Deadline (DD): Allowable time from release to completion (often D=TD = T).

Instance kk (k=0,1,2,…k = 0, 1, 2, \dots) is released at: Rk=k⋅Tand must complete by absolute deadline dk=k⋅T+DR_k = k \cdot T \quad \text{and must complete by absolute deadline } \quad d_k = k \cdot T + D

[!WARNING] Parameter Trap: In ⟨R,C,D⟩\langle R, C, D \rangle, the first value is a one-time release timestamp. In ⟨T,C,D⟩\langle T, C, D \rangle, the first value is a recurring period.

3. Why General-Purpose Schedulers Fail

Standard scheduling algorithms (FCFS, SJF, Round Robin) completely ignore deadlines:

  • FCFS: A long non-urgent job that arrives first monopolizes the CPU, causing pending urgent tasks to blow past their deadlines.
  • SJF / Round Robin: A short task with a distant deadline is prioritized ahead of a longer task whose deadline is imminent.

4. Real-Time Scheduling Algorithms

Real-time scheduling relies on preemptive scheduling: when an urgent real-time instance is released, it must immediately preempt lower-priority tasks.

1. Rate Monotonic (RM) Scheduling

Rate Monotonic is a static (fixed) priority preemptive scheduler:

  • The Priority Rule: Shorter period T⟹T \implies Higher priority.
  • Priority is assigned to the process at design time and remains constant for all instances.
  • Failure Mode: RM considers only period TT, ignoring relative deadline DD. If a task has a long period but a very tight relative deadline (D≪TD \ll T), RM assigns it low priority, causing it to miss its deadline.

2. Earliest Deadline First (EDF) Scheduling

Earliest Deadline First is a dynamic priority preemptive scheduler:

  • The Priority Rule: Earliest absolute deadline (Rk+DR_k + D) ⟹\implies Highest priority.
  • Priority belongs to the individual instance, dynamically reassessed at every release or completion event.
  • Optimality: EDF is theoretically optimal on a uniprocessor: if a set of periodic real-time tasks can be scheduled by any algorithm without missing a deadline, EDF is guaranteed to schedule it successfully.

Comparison: Rate Monotonic vs. Earliest Deadline First

Feature Rate Monotonic (RM) Earliest Deadline First (EDF)
Priority Assignment Static (Fixed): One priority per process based on period TT. Dynamic: Priority changes per instance based on absolute deadline R+DR + D.
Scheduler Complexity Simple: managed via static fixed-priority queues. Higher: ready queue must be re-sorted by absolute deadline on every release.
Processor Utilization Sub-optimal: theoretically bound by U≤n(21/n−1)U \le n(2^{1/n}-1), which approaches ln⁡2≈69.3%\ln 2 \approx 69.3\% for large nn. Can miss deadlines that EDF meets. Optimal (100% utilization): Can achieve up to 100% CPU utilization without missing deadlines (U≤1U \le 1).
Behavior Under Overload Predictable: High-priority tasks (short periods) continue meeting deadlines; only low-priority tasks fail. Unpredictable: Under heavy load, a cascade of missed deadlines can cause arbitrary tasks to fail catastrophically.

Step-by-Step Method: Drawing an RM or EDF Schedule

  1. Calculate Timelines: For each process, list the release time Rk=k⋅TR_k = k \cdot T and absolute deadline dk=k⋅T+Dd_k = k \cdot T + D for every instance in the window.
  2. Assign Priorities:
    • For RM: Rank processes statically: T1<T2<T3…T_1 < T_2 < T_3 \dots
    • For EDF: At each scheduling instant, evaluate active, unfinished instances by earliest absolute deadline dkd_k.
  3. Trace Execution:
    • Dispatch the highest-priority available instance.
    • If a new instance is released with higher priority (shorter period in RM, or earlier absolute deadline in EDF), preempt immediately.
  4. Audit Deadlines: Verify that every instance completes before its absolute deadline dkd_k.
Concept & Exam Checks: RTOS Principles
  • AY15/16 S2 Q1a(ii): Real-time operating systems usually use preemptive job scheduling. ⟹\implies True. An urgent task with an immediate deadline must preempt a running task with a later deadline; nonpreemptive scheduling would cause urgent tasks to miss deadlines.
  • True/False: In real-time systems, average response time of user programs should be minimized. ⟹\implies False. Real-time systems require guaranteed satisfaction of deterministic deadlines in the worst case; average response time is irrelevant.
  • True/False: In EDF scheduling, priority is assigned by comparing the relative deadline parameter DD. ⟹\implies False. Priority is assigned dynamically by evaluating the absolute deadline (R+DR + D). An older instance with large DD can have an earlier absolute deadline than a newly released instance with small DD.
