In a real-time system, when a result arrives is part of whether it is correct. This chapter defines real-time processes with three numbers, shows why the schedulers of chapter 3 fail on them, and covers the two real-time schedulers in the course: Rate Monotonic (RM) and Earliest Deadline First (EDF).

1. What Real-Time Means

Cyber-physical systems (CPS) are physical or engineered systems whose operation is monitored, coordinated and controlled by a reliable computing and communication core: cars (autonomous driving, parking assist, airbags), avionics, manufacturing robots, medical devices. They all repeat the same loop:

  1. Collect data from sensors.
  2. Execute control laws to decide the response.
  3. Send actuator commands in a reasonable amount of time.

What is “reasonable” depends on:

  • The function: collision avoidance needs milliseconds; a pacemaker up to a second; robotic surgery varies with the target.
  • The environment: available computing and communication resources; timing of sensors, actuators and operations.
  • Failure mitigation: time to detect and recover from failures (for example, replicated execution for redundancy).

Real-time ≠ fast. Real-time = predictable, even in the worst case. The lecture’s example: “Man drowned in a river with average depth 20 cm.” An average says nothing about the worst point.

A real-time system is one whose correctness depends on its temporal behaviour as well as its logical result: the application has deadlines that must be met. A real-time OS (RTOS), such as FreeRTOS or MicriumOS, provides OS services to such systems. Its key measure is timeliness: how predictably it meets deadlines. The worst case matters more than the average case, and deadlines come from the application’s requirements.

General-purpose OSes (Windows, Linux) are time-sharing systems tuned for fast average response, not real-time systems.

2. Real-Time Processes

One-shot process: ⟨R,C,D⟩\langle R, C, D \rangle

  • RR: release time, when the process becomes ready.
  • CC: execution requirement (in this course, the length of its single CPU burst).
  • DD: relative deadline.

The process needs CC units of CPU inside the window [R,R+D)[R, R + D). Its absolute deadline is R+DR + D.

Recurrent and periodic processes

Real-time functions repeat (airbag control, flight control, collision avoidance, pacemakers). A recurrent process runs some function again and again; each run is one real-time process ⟨R,C,D⟩\langle R, C, D \rangle.

A periodic process repeats at a fixed rate, typically because it is time-triggered (a sensor sends data periodically). It is written ⟨T,C,D⟩\langle T, C, D \rangle:

  • TT: period. Instances are released at R=0,T,2T,…R = 0, T, 2T, \dots
  • Instance kk must finish by kT+DkT + D.

Watch the first number: in ⟨R,C,D⟩\langle R, C, D \rangle it is a one-time release instant; in ⟨T,C,D⟩\langle T, C, D \rangle it is a recurring period.

FCFS, SJF and RR do not prioritize deadlines, so they miss them. The real-time scheduling problem: given periodic (or sporadic) real-time processes, find a uniprocessor scheduler that meets all deadlines. Real-time schedulers are preemptive: an urgent instance must be able to take the CPU at once.

Running example: P1⟨10,6,10⟩P_1\langle 10,6,10 \rangle, P2⟨19,4,19⟩P_2\langle 19,4,19 \rangle, P3⟨20,2,20⟩P_3\langle 20,2,20 \rangle.

4. Rate Monotonic (RM): Fixed Priority

In fixed-priority scheduling, each recurrent process has one priority that every instance keeps. If P1P_1’s instance released at 0 outranks P2P_2’s instance released at 0, then P1P_1’s instance at 10 also outranks P2P_2’s instance at 0, and so on.

RM assigns priority by period TT (the minimum release separation): shorter period = higher priority. Ties are broken arbitrarily.

RM is very popular in industry: it is simple to implement, and high-priority processes stay predictable even under high load.

5. Earliest Deadline First (EDF): Dynamic Priority

EDF gives each instance a priority from its absolute deadline: the earlier the deadline, the higher the priority. Ties are broken arbitrarily. Priority depends on the instance’s deadline (R+DR + D), not on the parameter DD.

EDF is a dynamic-priority scheduler, so it is more powerful than RM.

RM EDF
Priority Fixed per process (period TT) Dynamic per instance (absolute deadline)
Implementation Simpler: a separate queue for each recurrent process Harder: the queue must be sorted online by instance deadlines
Under high load Predictable for high-priority processes Can be unpredictable

Method: drawing an RM or EDF schedule

  1. List every release (kTkT) and absolute deadline (kT+DkT + D) in the window (up to the least common multiple of the periods).
  2. At every release and every completion, run the highest-priority ready instance: shortest period (RM) or earliest absolute deadline (EDF). Preempt if a new release outranks the running instance.
  3. Where two instances tie, either may run: each choice gives a different valid schedule.
  4. Check every instance finishes by its absolute deadline.

Utilization tests (not in the lecture)

The lecture judges schedulability by drawing the schedule. Two standard tests give a quick check; utilization U=∑Ci/TiU = \sum C_i / T_i:

  • EDF (D=TD = T): schedulable if and only if U≤1U \le 1.
  • RM (D=TD = T): schedulable if U≤n(21/n−1)U \le n(2^{1/n} - 1) (0.828 for n=2n = 2, 0.780 for n=3n = 3, → 0.693). Above the bound, RM may still work; draw the schedule.

Question: Consider the periodic real-time processes P1<5, 2, 5>, P2<10, 3, 10>, P3<20, 5, 20>. Construct all possible schedules for this process set under EDF. Is the process set schedulable under EDF?

Solution (my working; Tutorial 7 solutions are not out yet):

  • Releases and deadlines in [0,20)[0, 20): P1 at 0, 5, 10, 15 (deadlines 5, 10, 15, 20); P2 at 0, 10 (deadlines 10, 20); P3 at 0 (deadline 20).
  • The schedule is forced up to time 12:

Runs P1 (d5) P2 (d10) P1 (d10) P3 (d20), 3 of 5 P1 (d15)
  • At 12, P2 (d20, needs 3) and P3 (d20, needs 2) tie. At 15, P1 is released with d20, which ties again. The four schedules:
12–15 15–17 17–19 19–20
A1 P2 P1 P3 idle
A2 P2 P3 P1 idle
B1 P3 (12–14), P2 (14–15) P1 P2 idle

Tutorial 7 Q1(a) and past papers: Real-time T/F
  • Tutorial 7 Q1(a): Real-time CPS applications usually require a response within a very short time. False (my working). Real-time means the response is predictable and meets its deadline, which may be long (a pacemaker allows up to a second). Real-time ≠ fast.
  • AY15/16 S2 Q1a(ii): Real-time operating systems usually use preemptive job scheduling. True. An urgent instance must be able to take the CPU from a less urgent one.
  • Sample concept quiz: In real-time systems, average response time of user programs should be minimized. False. Real-time systems need guaranteed deadlines, whatever the average.
  • Tutorial 1 Q2(c): Windows and Linux are real-time systems. False. They are time-sharing systems.
