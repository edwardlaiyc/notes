To run, a program’s code and data must be in physical memory. This chapter covers how program addresses are bound to memory addresses, how memory is shared among processes (contiguous allocation, paging, segmentation), and how the hardware speeds up paging (TLB, multi-level and inverted page tables).

1. Binding Code and Data to Memory

To run a program, the OS creates a process image (text, data, heap, stack; chapter 2) and loads it into memory.

  • Compiler: source code → object module.
  • Linker: combines object modules and library code, resolving references → load module.
  • Loader: creates the process image, allocates memory, and loads the image into it.

An instruction such as LOAD X or JUMP Y names an address. Address binding decides which physical address that becomes. It can happen at three stages:

Stage How Address format in the image Check per access
Compile time Memory location known in advance; compiler emits absolute code. Must recompile if the start changes. Absolute Trap if address < base or ≥ base + limit; else use the address as is
Load time Compiler emits relocatable code; the loader binds it once. Absolute (after loading) Same as above
Execution time Binding is delayed until run time, so the process can move during execution. Relative (starts at 0) Trap if address ≥ limit; else physical = address + base

Lecture example (execution time): base = 1024, limit = 1000 (base + limit = 2024). The image holds LOAD 800: 800<1000800 < 1000, so physical address =800+1024=1824= 800 + 1024 = 1824. With compile- or load-time binding the image would already hold LOAD 1824.

Logical vs. physical address

  • Address space: all addresses a process can access.
  • Logical address: the address used in the code, generated by the CPU when it executes an instruction.
  • Physical address: the address the memory unit sees.
  • The logical address space is a linear, contiguous sequence of bytes. With execution-time binding it always starts at 0 (0 to limit − 1).
  • With compile- and load-time binding, logical and physical addresses are identical; with execution-time binding they differ.

2. Contiguous Allocation

Two approaches to sharing memory: contiguous allocation (each process’s logical address space stays in one piece of physical memory) and non-contiguous allocation (paging, segmentation).

  • Fixed partitioning: memory is divided into regions with fixed boundaries.
  • Dynamic partitioning: a hole is a block of free memory; holes of various sizes are scattered through memory. An arriving process gets memory from a hole large enough for it. The OS tracks allocated partitions and holes.

Choosing a hole

Rule Picks Notes
First-fit The first hole big enough Fastest
Best-fit The smallest hole big enough Must search the whole list unless sorted by size; leaves the smallest leftover hole
Worst-fit The largest hole Must search the whole list; leaves the largest leftover hole

Fragmentation

  • External fragmentation: enough total memory exists for a request, but it is not contiguous. It lies outside partitions.
  • Internal fragmentation: the allocated block is slightly larger than the request; the difference lies unused inside the partition.
Scheme Internal External
Fixed partitions Yes No
Dynamic partitions No Yes
Paging Yes (last page only) No
Segmentation No Yes

Compaction shuffles memory contents to gather free memory into one large block, reducing external fragmentation. It is possible only if the process image uses relocatable addresses and binding is done at execution time: moving a process with absolute addresses breaks every address inside it.

AY15/16 S2 Q3a: First, best and worst fit

Question: A system uses dynamic partitioning. Memory has holes, in physical address order, of 4 KB, 8 KB, 20 KB, 9 KB, 14 KB, 10 KB and 40 KB. Given a request of 12 KB, identify the hole allocated under first fit, best fit and worst fit.

Solution: Holes big enough for 12 KB: 20, 14, 40.

  • First fit: the first big-enough hole in address order → 20 KB.
  • Best fit: the smallest big-enough hole → 14 KB (leaves 2 KB).
  • Worst fit: the largest hole → 40 KB (leaves 28 KB).

Question: A system provides 4800 words of user memory, with multiple-partition multiprogramming. Four processes occupy memory (start, length): (1000, 1200), (3100, 700), (4000, 400), (4400, 200). For a new request: Step 1, use best fit; do Step 2 only if no hole fits. Step 2, compact by moving occupied partitions toward lower addresses, stopping as soon as a hole is large enough; if still not enough, block the process. (c) Which yields lower overhead in total relocation of occupied partitions?

Solution (my working; Tutorial 8 solutions are not out yet):

Occupied: A 1000–2199, B 3100–3799, C 4000–4399, D 4400–4599. Holes: 0–999 (1000), 2200–3099 (900), 3800–3999 (200), 4600–4799 (200).

(a) Best fit

  1. 600 → smallest hole ≥ 600 is 900 → 2200–2799. Hole left: 2800–3099 (300).
  2. 250 → smallest hole ≥ 250 is 300 → 2800–3049. Hole left: 3050–3099 (50).
  3. 1050 → holes are 1000, 50, 200, 200: none fits. Compact from address 0 upward:
    • move A to 0–1199 (free 1200–2199, 1000: not enough);
    • move the 600-block to 1200–1799 (free 1800–2799, still 1000);
    • move the 250-block to 1800–2049 → free 2050–3099 = 1050. Stop. Allocate 2050–3099.
  4. Relocated 3 partitions (1200 + 600 + 250 = 2050 words).

(b) First fit

  1. 600 → first hole ≥ 600 is 0–999 → 0–599. Hole left: 600–999 (400).
  2. 250 → 600–849. Hole left: 850–999 (150).
  3. 1050 → holes 150, 900, 200, 200: none fits. Compact: the two new blocks already sit at the bottom; move A to 850–2049 → free 2050–3099 = 1050. Allocate it.
  4. Relocated 1 partition (1200 words).

(c) First fit gives lower relocation overhead here (1 partition, 1200 words vs. 3 partitions, 2050 words). In both cases B, C, D stay put and 3800–3999 and 4600–4799 remain free.

Tutorial 8 Q2: Internal fragmentation; compaction with absolute addresses

Question: (a) Identify memory allocation schemes that suffer from internal fragmentation. (b) Explain why memory compaction cannot be performed if absolute address format is used in the code.

Answer (my working):

  • (a) Fixed partitioning (a process smaller than its partition wastes the rest) and paging (the last page of a process is rarely full; on average half a page is wasted).
  • (b) With absolute addresses (compile- or load-time binding), every address in the code is a physical address. Moving the process would leave all those addresses pointing at the old location, and nothing adds an offset at run time. Compaction needs relocatable addresses with execution-time binding, so that only the base register changes.

3. Paging

Paging lets a process’s memory be non-contiguous: a process gets physical memory wherever it is free.

  • Frames: physical memory divided into fixed-size blocks; the size is a power of 2, between 512 bytes and 8192 bytes.
  • Pages: logical memory divided into blocks of the same size.
  • The OS keeps track of all free frames. To run a program of nn pages, it finds nn free frames and loads the program.
  • A page table translates logical to physical addresses.
  • No external fragmentation. Internal fragmentation is still possible: the last page may not fill its frame.

Address translation

Page size 2n2^n bytes, logical address space 2m2^m bytes, so 2m−n2^{m-n} pages:

p⏟m−n bits|d⏟n bits\underbrace{p}_{m-n \text{ bits}} \;\Big|\; \underbrace{d}_{n \text{ bits}}

  • Page number pp: index into the page table; the entry holds the frame number ff.
  • Offset dd: combined with ff to form the physical address.

physical address=f×2n+d(i.e. f bits followed by d bits)\text{physical address} = f \times 2^n + d \qquad (\text{i.e. } f \text{ bits followed by } d \text{ bits})

Page-table implementation

  • The page table is kept in main memory.
  • The page-table base register (PTBR) points to the page table of the current process.
  • The page-table length register (PTLR) gives its size.
  • So every data or instruction access needs two memory accesses: one for the page-table entry and one for the data. EAT =2τ= 2\tau for memory cycle time τ\tau.

TLB

A translation look-aside buffer (TLB) (associative registers) is a small, fast hardware cache of page-table entries.

TLB lookup time ε\varepsilon, memory cycle time τ\tau, hit ratio α\alpha (fraction of lookups found in the TLB):

EAT=(τ+ε)α+(2τ+ε)(1−α)=(2−α)τ+ε\text{EAT} = (\tau + \varepsilon)\,\alpha + (2\tau + \varepsilon)(1 - \alpha) = (2 - \alpha)\,\tau + \varepsilon

A hit costs one memory access; a miss costs two. The TLB helps only if EAT <2τ< 2\tau, that is, α>ε/τ\alpha > \varepsilon / \tau. A TLB does not always improve EAT: with a very low hit ratio, the lookup time is pure overhead.

Shared pages

Several processes can share code by mapping their pages to the same frames. The shared code must be reentrant (read-only), so no process can change it.

4. Multi-Level and Inverted Page Tables

Two-level paging

A 32-bit machine with 4 KB pages has a 20-bit page number and a 12-bit offset: 2202^{20} page-table entries. At 4 bytes each, every page table occupies 4 MB, which is hard to allocate contiguously. So the page table itself is paged (divided into pages), at the cost of a small increase in access time.

  • One page of the inner table holds 4 KB/4=2104\text{ KB} / 4 = 2^{10} entries → p2p_2 = 10 bits.
  • The inner table occupies 4×220/4 K=2104 \times 2^{20} / 4\text{ K} = 2^{10} pages, so the outer table has 2102^{10} entries → p1p_1 = 10 bits.

p1⏟10|p2⏟10|d⏟12\underbrace{p_1}_{10} \;\Big|\; \underbrace{p_2}_{10} \;\Big|\; \underbrace{d}_{12}

Translation: PTBR → outer table entry p1p_1 gives the frame of an inner-table page (F#1) → entry p2p_2 in that page gives the data frame (F#2) → physical address = F#2 followed by dd. Without a TLB, a kk-level table costs k+1k + 1 memory accesses per reference.

Method (multi-level sizing):

  1. Offset bits d=log⁡2(page size)d = \log_2(\text{page size}); page-number bits =m−d= m - d.
  2. Entries per page =page size/PTE size= \text{page size} / \text{PTE size}; each inner level uses log⁡2\log_2 of that many bits.
  3. The outer level gets the remaining bits. Add levels until the outer table fits in one page.

Inverted page table

Normally each process has its own page table, whose size grows with the logical address space, so many page tables use a lot of memory. An inverted page table is a single table with one entry per physical frame, holding ⟨process-id,page-no⟩\langle \text{process-id}, \text{page-no} \rangle.

  • Logical address: ⟨process-id,page-no,offset⟩\langle \text{process-id}, \text{page-no}, \text{offset} \rangle.
  • The pair ⟨process-id,page-no⟩\langle \text{process-id}, \text{page-no} \rangle is searched for in the table. If it matches entry ii, the physical address is ⟨i,offset⟩\langle i, \text{offset} \rangle.
  • Saves memory, but increases search time: the table is sorted by physical address while lookups use the logical address.

One page holds 2y/4=2y−22^y / 4 = 2^{y-2} entries, so the inner index has y−2y - 2 bits. Format: [x−y+2∣y−2∣y][\,x - y + 2 \mid y - 2 \mid y\,].

5. Segmentation

Segmentation breaks a program into its logical segments (main program, subroutines, stack, symbol table) and allocates each separately. Unlike pages, segments vary in size; like pages, a process’s segments need not be contiguous.

  • Logical address: ⟨segment-no s,offset d⟩\langle \text{segment-no } s, \text{offset } d \rangle.
  • Segment table entry: base (starting physical address) and limit (segment length).
  • Segment-table base register (STBR) points to the table; segment-table length register (STLR) gives the number of segments the program uses.

Translation: (1) look up entry ss; (2) check d<limitd < \text{limit}, otherwise trap; (3) physical address =base+d= \text{base} + d.

Lecture example: translate ⟨3,128⟩\langle 3, 128 \rangle. Entry 3: base 3200, limit 1100. 128<1100128 < 1100, so the address is 3200+128=𝟑𝟑𝟐𝟖3200 + 128 = \mathbf{3328}.

Because segments vary in length, allocating them is a dynamic storage-allocation problem (usually best-fit or first-fit). When a process leaves, its segments become holes of varying sizes: external fragmentation, but no internal fragmentation.

Past-paper T/F: Binding, allocation, translation
  • AY17/18 S2 Q3a(i): With execution-time binding, addresses generated by the CPU directly access physical memory. False. The CPU’s logical address goes through the relocation register in the MMU.
  • AY18/19 S2 Q3a(i): With load-time binding, logical and physical addresses are identical. True. The loader writes absolute addresses.
  • AY19/20 S1 Q3a(ii): If address binding is performed during load time, the compiler must generate re-locatable code. True. The loader then binds it to absolute addresses.
  • AY16/17 S1 Q3a(iii): With demand paging, address binding must be performed during load time. False. Pages move between disk and any frame, so binding must be at execution time.
  • AY19/20 S1 Q3a(iii): Worst-fit results in the smallest leftover hole in memory. False. It leaves the largest; best-fit leaves the smallest.
  • AY16/17 S1 Q3a(i): Segmentation suffers from internal fragmentation. False. It suffers from external fragmentation.
  • AY16/17 S1 Q3a(ii): The TLB is used to reduce page faults. False. It reduces effective memory access time.
  • AY18/19 S1 Q3a(i): Using a TLB always improves the effective memory access time. False. With a very low hit ratio, the TLB lookup only adds time.
  • AY19/20 S1 Q3a(iv): An inverted page table increases the time needed for address translation. True. The table must be searched for the ⟨\langlepid, page⟩\rangle pair.
