A physical disk is a one-dimensional array of fixed-size blocks (typically 512 B or 4 KB) addressed by integer index. It has no built-in notion of filenames, directories, or permissions.

The file system provides this abstraction: it maps human-readable names and directory hierarchies to raw disk blocks, manages free space, and enforces access permissions.

1. Layered File System Architecture

Operating systems structure file systems in hierarchical layers, where each layer depends only on the one directly below it:

Layer Primary Role What It Does
Application Programs API Calls Issues open, read, write, close.
Logical File System Names & Metadata Resolves pathnames, manages directory hierarchies, enforces permissions, and maintains File Control Blocks (FCBs) / inodes.
File-Organisation Module Address Translation Translates logical block addresses (e.g. file block 2) into physical disk block addresses (e.g. disk block 4182). Tracks free blocks.
Basic File System Buffering & Block I/O Issues generic read/write block commands to disk drivers; manages in-memory block caches.
I/O Control Hardware Driver Interface Device drivers and interrupt handlers transferring data between disk controllers and main memory.

Important

Key Exam Split:

  • Logical File System: Handles names, directories, protection, and metadata (FCBs/inodes).
  • File-Organisation Module: Handles block translation (logical →\to physical) and space allocation.

2. Files, File Operations, and Open-File Tables

File attributes, types and structure

Attribute Meaning
Name The only information kept in human-readable form
Type Needed by systems that support different file types
Location Pointer to the file’s location on the device
Size Current file size
Protection Who can read, write, execute
Time, date, user ID For protection, security, usage monitoring

This information is kept in the directory structure on disk.

A file has a contiguous logical address space and can hold many types of information, usually shown by the extension: executable (exe, bin), object (obj, o), source (c, asm), batch (bat, sh), text (txt, doc), library (lib, a), print/view (ps, gif), archive (zip, tar).

A file is a collection of records. Structuring the records is usually left to applications (an OS supporting several structures would need code for each). UNIX and MS-DOS treat a file as unstructured: a sequence of bytes, each addressable from the start of the file. The rest of this chapter assumes that.

Access methods and operations

  • Sequential access: bytes are processed in order from the beginning, one after another.
  • Direct access: bytes can be read in any order, by byte number.
Operation What it does
Create Allocate disk space; create a directory entry with the file’s attributes
Delete Delete the directory entry; free the disk space
Open Search the directory structure for the entry; move its contents into memory (the open-file table)
Close Copy the in-memory directory entry back to the directory structure on disk
Read / Write Find the file’s location through the open-file table; read or write at the current position pointer
Seek (not in the lecture table) Move the current position pointer: an in-memory change, 0 disk reads

For each open file the OS keeps the current position pointer, the file open count, and the disk location.

Why open() Exists & The Two-Table Architecture

Traversing directories on disk to find a file’s metadata for every single read() or write() is prohibitively slow. open() performs this directory search once, caches the file’s metadata in memory, and returns a lightweight integer file descriptor (fd).

To allow multiple processes to access the same file concurrently with independent read positions, the kernel separates state into two tables:

Process A                      System-Wide Open-File Table
[fd: 3] ──> [Offset: 500  ] ──┐
                              ├──> [ Inode / FCB copy ]
Process B                     │    [ Open Count: 2    ]
[fd: 4] ──> [Offset: 12000] ──┘
Table Scope Stored Information Purpose
Per-Process Open-File Table One per process Current file position pointer, access mode (read/write), pointer to system-wide entry. Tracks independent read/write offsets for each process.
System-Wide Open-File Table One for entire OS Cached copy of the FCB (inode), open count (number of active opens). Coordinates shared metadata and tracks when a file can be removed from memory.
AY19/20 S1 Q4a: Why both open-file tables are required, and how open() modifies them

Question: Explain why both per-process open file table and system-wide open file table are required and describe how they are modified in open() operation.

Answer:

  • Why both are required:
    • The per-process table maintains independent, process-specific state (most importantly, the current file position pointer and process access rights).
    • The system-wide table maintains shared state across all processes (a single cached copy of the FCB/inode and an open count), avoiding duplicate memory allocation and synchronizing file size/metadata changes.
  • Modifications during open():
    1. The kernel traverses directories on disk to locate the FCB.
    2. If the file is already in the system-wide table, the kernel increments its open count; otherwise, it allocates a new entry, copies the FCB from disk, and sets open count = 1.
    3. The kernel verifies process access permissions against the FCB.
    4. It creates a new entry in the calling process’s per-process table with offset = 0, records the access mode, and links it to the system-wide entry.
    5. It returns the index of this per-process entry as the file descriptor (fd).

3. Directories, Path Names, and File Sharing

A directory contains entries, one per file; both the directory and the files are on disk. An entry holds either:

  • (a) the file name and its other attributes, or
  • (b) the file name and a pointer to another structure holding the attributes: the file control block (FCB). UNIX does this: each entry holds a file name and an inode number.

Implementing a directory:

Linear list Hash table
How Entries in a linear list Linear list plus a hash table for look-up
Pro Simple to implement Shorter search time
Con Slow: linear search to find an entry Collisions (two names hash to the same slot); fix: each hash entry holds a list of directory entries
  • Absolute path: from the root down to the file, e.g. /spell/mail/prt/first.
  • Relative path: from the current directory. If the current directory is /spell/mail, the same file is prt/first.
  • A tree gives efficient searching (locate a file by path), naming (the same name can exist in different directories) and grouping (files grouped logically by property).

Directory operations:

Operation Notes
Create In UNIX, . (this directory) and .. (parent) are added automatically
Delete Only an empty directory (only . and ..) can be deleted
List List the files and their entries
Search Find the entry for a file
Traverse Visit every directory and file in the structure

File Sharing: Hard Links vs. Symbolic Links

To allow files to be shared across directories without duplicating data, file systems use an Acyclic Graph Directory:

Feature Hard Link Symbolic Link (Soft Link)
Lecture definition Duplicate all information about the file in several directories. In UNIX: another directory entry with the same inode number. A directory entry that holds the absolute or relative path name of the file; the link is resolved by following that path.
Lookup Speed Fast (direct inode reference). Slower (must resolve the path).
Cross-Device (not in the lecture) Cannot span file systems. Can span file systems.
On Deletion of Target UNIX keeps a link count in the inode and frees the blocks only when it reaches 0. The link becomes dangling.

Problems with file sharing:

  1. Traversal may visit a shared file more than once. Fix: ignore link entries when traversing.
  2. Deleting a shared file may leave dangling pointers to it. Fixes: (a) search for dangling links and remove them; (b) leave them, and delete each one when it is next used; (c) preserve the file until all references to it are deleted.
Tutorial 11 Q1(a): Hazards and solutions when deleting shared files

Question: Consider a file system where a file can be deleted and its disk space reclaimed while links to that file still exist. What problems may occur if a new file is created in the same storage area or with the same absolute path name? How can these problems be avoided?

Answer (my working; Tutorial 11 solutions are not out yet):

  • Problems: the old links become dangling. If a new file reuses the storage area, a hard link (or any pointer to the old blocks) now reaches the new file’s data. If a new file is created with the same path name, a symbolic link silently resolves to the new file. Either way a user reaches the wrong file, which is also a security hole (another user’s private data).
  • Avoiding them (the three fixes from the lecture):
    1. Search for dangling links and remove them when the file is deleted.
    2. Leave them, and delete each link when it is next used and found invalid.
    3. Preserve the file until all references to it are deleted (UNIX keeps a link count in the inode for hard links).
Tutorial 11 Q1(b): Single shared copy vs. multiple individual copies

Question: Some systems provide file sharing by maintaining a single copy of a file; other systems maintain several copies, one for each of the users sharing the file. Discuss the relative merits of each approach.

Comparison (my working):

  • Single Shared Copy: Updates are immediately visible to all users; minimal disk space. However, requires file locking/synchronization, and accidental corruption affects everyone.
  • Multiple Copies (One per user): Users work independently without lock contention; damage is isolated. However, wastes disk space, and copies diverge, making synchronization difficult.

4. File Protection in UNIX

UNIX uses 9 permission bits divided into three classes: Owner (u), Group (g), and Public/Other (o). Each class has three rights: Read (r = 4), Write (w = 2), and Execute (x = 1): Mode 751⟹r w x⏟Owner (7)r - x⏟Group (5)- - x⏟Public (1)\text{Mode } 751 \implies \underbrace{\text{r w x}}_{\text{Owner (7)}} \quad \underbrace{\text{r - x}}_{\text{Group (5)}} \quad \underbrace{\text{- - x}}_{\text{Public (1)}}

File vs. Directory Permissions

Permission Regular File Directory
Read (r) Read file content. List filenames inside the directory (ls).
Write (w) Modify file content. Create, rename, or delete files inside the directory.
Execute (x) Execute program/script. Traverse/Enter the directory (cd, accessing inodes inside).

Warning

  • Directory x is mandatory: Lacking x on a directory prevents accessing any file inside it, even if the file itself has permissions 777 (rwxrwxrwx).
  • File deletion depends on directory w: Deleting a file modifies the enclosing directory’s list. It requires w on the directory, not on the file itself!

5. File Space Allocation Methods

To locate byte offset nn in a file with block payload BdataB_{data}: n=Q×Bdata+R⟹Q=⌊n/Bdata⌋ (Logical Block),R=n(mod⁡Bdata) (Offset in Block)n = Q \times B_{data} + R \implies Q = \lfloor n / B_{data} \rfloor \text{ (Logical Block)}, \quad R = n \pmod{B_{data}} \text{ (Offset in Block)}

The Three Allocation Schemes

The lecture’s examples all use 512-byte blocks and logical byte address 2333.

  1. Contiguous allocation: each file occupies a set of contiguous blocks.
    • Simple: only the starting block and length are needed. Supports random access.
    • Problems: wasted space (like dynamic partitioning of memory); finding a big-enough hole with first-fit (faster) or best-fit causes external fragmentation; the file is limited by the size of its hole and may later have to move to a bigger one; overestimating the space needed causes internal fragmentation.
    • Mapping: logical address =Q×512+R= Q \times 512 + R; block == start +Q+ Q; displacement =R= R. Example: 2333=4×512+2852333 = 4 \times 512 + 285 → byte 285 of block start + 4.
  2. Linked allocation: each file is a linked list of blocks scattered anywhere on the disk.
    • Simple (only the starting address is needed); no wasted space; no limit on file size (blocks are allocated as needed). Problem: no random access.
    • Mapping with a 4-byte pointer at the start of each block: logical address =Q×508+R= Q \times 508 + R; access the (Q+1)(Q+1)th block in the chain; displacement =R+4= R + 4. Example: 2333=4×508+3012333 = 4 \times 508 + 301 → the 5th block in the chain (block 25 in the lecture figure), displacement 301+4=305301 + 4 = 305.
    • FAT (a table of the links kept in memory) is the variant named in the lecture outline.
  3. Indexed allocation: each file has an index block holding pointers to all its blocks; the directory entry holds the index block’s number.
    • Supports random access; dynamic allocation without external fragmentation (like paging). Problem: overhead of index blocks and mapping.
    • Mapping: logical address =Q×512+R= Q \times 512 + R; QQ = displacement into the index table, RR = displacement into the block. Example: 2333=4×512+2852333 = 4 \times 512 + 285 → entry 4 of the index points to block 25 → byte 285 of block 25.
    • Why 2 index blocks for a 128 KB maximum file? 128 KB/512=256128\text{ KB} / 512 = 256 blocks, 256×4 B=1024256 \times 4\text{ B} = 1024 B of pointers =2= 2 blocks of 512 B.

Metric Contiguous Linked Indexed
Directory Stores Start block & length First block pointer Index block pointer
Direct / Random Access 1 read Q+1Q + 1 reads 2 reads (Index + Data)
External Fragmentation Yes No No
File Growth Difficult Easy Easy (up to index size)

Step-by-Step Method: Calculating Disk Reads for File Access

To find disk I/Os required to read LL bytes starting at byte offset AA:

  1. Find byte range: [A,A+L−1][A, \; A + L - 1].
  2. Determine usable block size BdataB_{data}: BB for Contiguous/Indexed; B−pB - p for Linked.
  3. Compute logical block indices: Qstart=⌊A/Bdata⌋Q_{start} = \lfloor A / B_{data} \rfloor, Qend=⌊(A+L−1)/Bdata⌋Q_{end} = \lfloor (A + L - 1) / B_{data} \rfloor.
  4. Compute Disk Reads (assuming directory is cached in memory):
    • Contiguous: Qend−Qstart+1Q_{end} - Q_{start} + 1 reads.
    • Linked: Must traverse from block 0 to Qend⟹𝑸𝒆𝒏𝒅+𝟏Q_{end} \implies \mathbf{Q_{end} + 1} reads.
    • Indexed: 1 (fetch index block)+(Qend−Qstart+1)1 \text{ (fetch index block)} + (Q_{end} - Q_{start} + 1) reads. (If index block is already cached, count is just Qend−Qstart+1Q_{end} - Q_{start} + 1).

6. The UNIX Multi-Level Inode Architecture

UNIX uses an inode (an index block) for each file or directory. It holds the file attributes and:

  • 12 direct pointers to data blocks;
  • 3 indirect pointers to index blocks: single, double, triple indirect.

Lecture sizing (4-byte pointers, 4 KB blocks, so K=1024K = 1024 pointers per block):

  • direct: 12×4 KB=4812 \times 4\text{ KB} = 48 KB;
    • single indirect: 48 KB+1024×4 KB=48 KB+22248\text{ KB} + 1024 \times 4\text{ KB} = 48\text{ KB} + 2^{22} B;
    • double indirect: 48 KB+222+23248\text{ KB} + 2^{22} + 2^{32} B, more than 4 GB.

Each UNIX directory entry holds an inode number and a file name, and each inode has a fixed location on disk, so finding a file’s inode is a straightforward path walk.

Disk Reads to Access Logical Block QQ (after open(), inode in RAM)

  • Direct (0≤Q<D0 \le Q < D): 1 read (data block).
  • Single Indirect (D≤Q<D+PD \le Q < D + P): 2 reads (index block + data block).
  • Double Indirect (D+P≤Q<D+P+P2D + P \le Q < D + P + P^2): 3 reads (double index + single index + data block). (Note: An indirect index block fetched once during a read request is cached for subsequent blocks under it).

Path Resolution (open()) Disk Reads

For a path with kk components below the cached starting directory (e.g. /usr/ast/mbox with root cached has k=3k = 3): 𝐃𝐢𝐬𝐤 𝐑𝐞𝐚𝐝𝐬 𝐟𝐨𝐫 𝐨𝐩𝐞𝐧()=2(k−1)+1\mathbf{\text{Disk Reads for open()}} = 2(k - 1) + 1 (Each intermediate directory costs 2 reads: its inode + its data block. The target file costs 1 read: its inode).

7. Block Size Trade-offs and Free-Space Management

Block Size Trade-Off

Choosing disk block size balances throughput against space utilization:

  • Big blocks: a file fits in few blocks → fast to find and transfer, but space is wasted when the file does not fill its last block.
  • Small blocks: a file needs many blocks → slow data rate, but little waste.
  • Time and space utilization must be traded off.
Tutorial 11 Q4: Two block sizes

Question: Some file systems use two block sizes, e.g. 4 KB and 512 B. A 6 KB file can then be allocated one 4 KB block and four 512 B blocks. Discuss the advantage over a single block size.

Answer (my working): it gets both sides of the trade-off. The body of the file sits in large blocks, so it is fast to find and transfer (high data rate). Only the tail uses small blocks, so at most part of one 512 B block is wasted instead of most of a 4 KB block (here, 0 B wasted instead of 2 KB with 4 KB blocks only).

Free-Space Management

Keeping track of free blocks is like tracking free memory under variable partitions. Two methods:

Bit map (bit vector): one bit per block, 0 = free, 1 = allocated.

  • Needs extra space. Lecture example: block 292^9 B, disk 2342^{34} B (16 GB) → 2252^{25} blocks → bitmap =225/8=222= 2^{25} / 8 = 2^{22} B (4 MB).
  • Kept in a fixed place on disk; may be brought into memory for speed, but must be written back occasionally for consistency and security.
  • Easy to locate free blocks, but inefficient unless the whole map is in memory.

Linked list: link all free blocks together; keep a pointer to the first free block in a special location on disk and cache it in memory.

  • No extra space, but not efficient (blocks must be visited one by one).
AY Past-Paper Checks: Free Space & Sizing
  • AY18/19 S2 Q4c (Compare Bitmap vs Linked List): Linked list uses zero extra storage but is inefficient due to disk traversal. Bitmap requires dedicated memory (1 bit/block) but is extremely fast and efficiently finds contiguous runs.
  • AY18/19 S1 Q4a(ii): Large block size results in high data rate and high disk utilization. ⟹\implies False (data rate is high, but space utilization is low).
  • Additional Practice Q7: (a) With protection bits r-x r-x --x, only the owner can read the file. False: the group can read too. (b) The open-file table temporarily caches data blocks of a file. False: it caches the FCB (inode), position pointer and open count, not data. (c) Linked allocation may result in external fragmentation. False: any free block can be linked in.
AY15/16 S2 Q4b: Problems of contiguous allocation; how indexing fixes them

Question: Describe the problems of the contiguous file allocation method and discuss how the index file allocation method overcomes these problems.

Answer:

  • Contiguous problems: wasted space, as in dynamic partitioning; finding a big-enough hole (first-fit or best-fit) leaves external fragmentation; a file is limited by its hole and may have to move to a bigger one; overestimating its size causes internal fragmentation.
  • Indexed fix: each file has an index block holding pointers to its blocks, and the directory entry holds the index block’s number. Any free block can be used (no external fragmentation, as with paging), the file can grow block by block, and random access is still supported through the index.
