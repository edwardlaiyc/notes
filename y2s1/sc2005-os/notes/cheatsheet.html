1. Operating System Overview & Protection

Key Contrasts & Invariants

Concept Mode / Mechanism A Mode / Mechanism B Core Distinction
CPU Execution Modes User Mode (mode bit = 1) Kernel Mode (mode bit = 0) Hardware prevents user applications from executing privileged instructions (I/O, halt, base/limit registers).
Control Transitions Trap (Software Interrupt) Interrupt (Hardware) Traps are synchronous (system calls, exceptions like divide-by-zero, page faults). Interrupts are asynchronous (timer, disk, network).
Context Switching Mode Switch Context Switch Mode switch switches execution privilege (User ↔\leftrightarrow Kernel) for the same process. Context switch saves state of Process A and loads Process B (high CPU overhead).
Kernel Structure Monolithic Kernel Microkernel Monolithic runs all OS services (VFS, IPC, drivers) in kernel space (fast, but fault-intolerant). Microkernel keeps only minimal primitives in kernel space; OS services run as user processes (robust, but IPC message-passing overhead).

High-Yield MCQ “Watch Out” Checks

  • Privileged Instructions: Direct I/O instructions, loading base/limit registers, modifying the mode bit, disabling hardware interrupts, and HALT are strictly privileged.
  • Non-Privileged Instructions: Reading the time-of-day clock, generating a trap (INT 0x80, syscall), and arithmetic calculations can execute safely in User Mode.
  • Timer Interrupt: The timer is a hardware mechanism that periodically forces control back to the OS scheduler, preventing a runaway user process from monopolizing the CPU.
  • Base/Limit Check: A reference is legal iff base≤addr≤base+limit−1\text{base} \le \text{addr} \le \text{base} + \text{limit} - 1. With base 0x1000 and limit 0x1000, 0x1FFF is legal (no trap); 0x2000 traps (T1 Q2b).
  • System Call: Always switches User →\to Kernel through a trap (T1 Q2d: True). An API is only the library function that wraps the system call, so not every API call enters the kernel.
  • PC OSes (Windows, Linux): Time-sharing, not real-time. Time-sharing aims at fast average response; real-time aims at guaranteed deadlines.

Hardware I/O and System Types

Contrast Mechanism A Mechanism B Trap
I/O Transfer Interrupt-driven: CPU copies each unit out of the controller buffer; one interrupt per unit. Suits mouse and keyboard. DMA: Controller moves a whole block to RAM; one interrupt per block. Suits disk and network. DMA still interrupts, at the end of the block. In both, the requesting process goes Running →\to Waiting; DMA frees the CPU for other processes.
Polling vs Interrupt Polling: CPU busy-waits on a status register. Interrupt: device signals completion. An OS with no interrupts would idle forever; that is why it is called interrupt-driven.
Multiprogramming Several processes resident in RAM; CPU switches when one waits for I/O. Works on one core. Multiprocessing: Two or more cores run instructions in true parallel (higher throughput, fault tolerance). A multiprocessor is normally also multiprogrammed. Multi-threading is a third idea: several streams inside one process.
Time-sharing (multitasking) Multiprogramming plus a timer-driven switch, so interactive users see fast response. Real-time: provable deadlines. All time-sharing ≠\ne real-time.

Process States & Transitions

  • New →\to Ready: Long-term scheduler admits process to ready queue in RAM.
  • Ready →\to Running: Short-term CPU scheduler dispatches process.
  • Running →\to Ready: Time-slice expires (timer interrupt) or preemption by higher-priority job.
  • Running →\to Waiting (Blocked): Process requests synchronous I/O or waits for child/event (wait()).
  • Waiting →\to Ready: I/O transfer completes (hardware interrupt asserted). A blocked process NEVER transitions directly to Running.

High-Yield MCQ “Watch Out” Checks

  • User-Level Threads (ULT) vs. Kernel-Level Threads (KLT):
    • ULT: Thread management handled by user-space runtime library without kernel awareness. Extremely fast context switching (no mode switch), but if one ULT performs a blocking system call, the entire process and all sibling ULTs are blocked.
    • KLT: Managed directly by OS kernel. Individual threads can block without stalling sibling threads, and true multi-core parallel execution is supported.
  • Process Creation (fork()):
    • Child receives an exact duplicate copy of parent address space (separate address space!).
    • In parent, fork() returns the child’s PID (>0> 0). In child, fork() returns 0. On failure, returns -1.
  • wait() / exit() / abort(): The parent calls wait() (also called join()) to block until a child ends; a child never uses wait() to wait for the parent (T2 Q1c: False). A process ends itself with exit(); a parent kills a child with abort().
  • Interrupts and states: When a hardware interrupt (not a trap) arrives, the running process goes Running →\to Ready so the ISR can run; afterwards the OS may resume it or pick another (T2 Q1b: True; some kernels skip the state change if the same process will resume).
  • Data vs Stack region: The data region has a fixed size and holds globals; the stack grows and shrinks and holds locals and call frames (T2 Q2).

3. CPU Scheduling

Scheduling Criteria & Trade-offs

  • CPU Utilization: Percentage of time CPU is actively executing instructions (40%–90%40\%\text{–}90\%).
  • Throughput: Number of processes completed per unit time.
  • Turnaround Time (TturnT_{\text{turn}}): Tcompletion−TarrivalT_{\text{completion}} - T_{\text{arrival}} (entire lifetime).

4. Process Synchronization

The Critical Section Problem

To prevent race conditions, any valid synchronization solution must satisfy all 3 criteria:

  1. Mutual Exclusion: If process PiP_i is executing in its critical section, no other processes can be executing in their critical sections.
  2. Progress: If no process is executing in its critical section and some processes wish to enter, only those processes not in their remainder sections can participate in deciding who enters next, and selection cannot be postponed indefinitely.
  3. Bounded Waiting: There exists a bound on the number of times other processes are allowed to enter their critical sections after a process has made a request to enter and before that request is granted (prevents starvation).

Semaphore Primitives (Atomic)

  • wait(S) / P(S): Decrements SS. If S<0S < 0, the calling process blocks: wait(S):S←S−1;if S<0⟹block();\text{wait}(S): \quad S \leftarrow S - 1; \quad \text{if } S < 0 \implies \text{block();}
  • signal(S) / V(S): Increments SS. If S≤0S \le 0, wakes up one blocked process: signal(S):S←S+1;if S≤0⟹wakeup();\text{signal}(S): \quad S \leftarrow S + 1; \quad \text{if } S \le 0 \implies \text{wakeup();}
  • Invariant Meaning of SS:
    • S>0S > 0: Represents the number of available resources.
    • S≤0S \le 0: Absolute value |S||S| represents the exact number of processes currently blocked in the semaphore queue.

  • Atomic read-modify-write: Making each read and each write atomic is not enough; counter++ is three instructions, so the whole sequence needs mutual exclusion.

5. Deadlocks

The Four Necessary Conditions (Coffman)

Deadlock can occur if and only if all four conditions hold simultaneously:

  1. Mutual Exclusion: At least one resource is held in a non-shareable mode.
  2. Hold and Wait: A process holding at least one resource is actively waiting to acquire additional resources held by other processes.
  3. No Preemption: Resources cannot be forcibly preempted; they can only be released voluntarily by the holding process.
  4. Circular Wait: A closed chain of processes {P0,P1,…,Pn}\{P_0, P_1, \dots, P_n\} exists such that P0P_0 waits for a resource held by P1P_1, and PnP_n waits for a resource held by P0P_0.

Cardinal Rule: An Unsafe State is NOT inherently a deadlock; it is merely a vulnerable state that has the potential to deteriorate into a deadlock if all processes demand their maximum claims simultaneously.

Handling Deadlocks: Four Paradigms

Paradigm Idea Cost
Prevention Make one Coffman condition impossible. Low utilization.
Avoidance Grant a request only if the state stays safe (Banker’s, needs maximum claims in advance). Run-time check on every request.
Detection and recovery Allow deadlock, find it (RAG reduction), then kill or preempt processes. Lost work.
Ignore (ostrich) Assume it never happens; Linux and Windows do this. None until it happens.
Condition attacked Prevention rule Limitation
Mutual exclusion Make resources shareable. Printers, locks cannot be shared.
Hold and wait Request everything at once, or release all before asking again. Idle resources; starvation.
No preemption Take back all held resources when a request fails. Only for savable state (registers, pages).
Circular wait Number resource types; request only in increasing order. Most practical; used in kernels.
  • Safe ⇒\Rightarrow no deadlock; unsafe ⇒\Rightarrow deadlock possible; deadlock ⇒\Rightarrow unsafe.
  • A deadlock needs at least two processes: one process cannot satisfy hold-and-wait against itself (T6 Q1b: True).
  • A RAG cycle means deadlock only when every resource type has a single instance (T6 Q1c: False).

6. Real-Time OS & Virtualization

RTOS Scheduling

  • Hard Real-Time: Missing a deadline results in total system failure (flight control, pacemakers).
  • Soft Real-Time: Missing a deadline degrades quality of service but does not cause catastrophic system failure (multimedia streaming).
  • Rate Monotonic (RM): Static-priority assignment based on task period. Shorter period Ti⟹T_i \implies Higher priority.
    • Schedulability bound (Liu & Layland): ∑CiTi≤n(21/n−1)\sum \frac{C_i}{T_i} \le n(2^{1/n} - 1) (n=2⟹82.8%n=2 \implies 82.8\%, n→∞⟹69.3%n \to \infty \implies 69.3\%).
  • Earliest Deadline First (EDF): Dynamic-priority assignment based on absolute deadline. Closer deadline ⟹\implies Higher priority.
    • Provably optimal: Guaranteed schedulable if and only if ∑CiTi≤1.0\sum \frac{C_i}{T_i} \le 1.0 (100%100\%).

Virtualization Models

  • Type 1 Hypervisor (Bare-Metal): Runs directly on host hardware without an underlying OS (VMware ESXi, Xen).
  • Type 2 Hypervisor (Hosted): Runs as an application inside a host operating system (VirtualBox, VMware Workstation).
  • Trap-and-Emulate: Sensitive guest kernel instructions trap to hypervisor, which emulates behavior.
  • Binary Translation: Rewrites sensitive unprivileged instructions on-the-fly when hardware lacks virtualization extensions.
  • Full vs Para-virtualization: Full: the guest OS runs unmodified and does not know it is virtual. Para: the guest OS is modified to call the hypervisor through hypercalls (virtual call API), which is faster.
  • Three mechanisms: Multiplexing (1 →\to many: vCPUs, virtual memory), Aggregation (many →\to 1: RAID), Emulation (one kind →\to another: JVM, RAM disk).
  • Limited Direct Execution: Unprivileged guest instructions run directly on the CPU; sensitive instructions trap to the hypervisor (VM exit in hardware-assisted VT-x / AMD-V), which emulates them.
  • Who does what (T7 Q1, from the lecture): The hypervisor abstracts the hardware and gives each VM an interface; the guest OS manages the applications inside its own VM. A Type 2 hypervisor lets normal host applications run beside the VMs; Type 1 does not.
  • Real-time ≠\ne fast: A real-time system must meet its deadlines predictably; a very short response time is typical of cyber-physical systems but is not the definition.
  • CPU overcommitment: The hypervisor may assign more vCPUs than physical cores because VMs rarely use 100% together.

7. Physical Memory Organization

Contiguous Allocation & Fragmentation

8. Virtual Memory & Demand Paging

Valid-Invalid Bit & Page Fault Handling Sequence

  • Valid (v): Page resides in physical RAM.
  • Invalid (i): Page resides on backing store (disk). Triggers a Page Fault Trap.
  • Dirty (Modify) Bit: Set on memory writes. Clean victim ⟹\implies discard without I/O; Dirty victim ⟹\implies write back to disk (page-out before page-in).
  • Reference Bit: Set on read/write. Used by Clock to approximate LRU.
  • Belady’s Anomaly: Increasing physical frames causes an increase in page faults.
    • Stack Algorithms (OPT, LRU): Satisfy inclusion property (St(n)⊆St(n+1)S_t(n) \subseteq S_t(n+1)). Immune to Belady’s anomaly.
    • FIFO and Clock: Violate inclusion property. Can suffer Belady’s anomaly.
  • Frame Allocation Rules: Fixed allocation requires local replacement. Variable allocation can use either local or global replacement.
  • Thrashing: Processes spend virtually all time paging rather than computing.
    • Symptom: Low CPU utilization combined with high multiprogramming and saturated paging disks.
    • Remedy: Reduce degree of multiprogramming (swap out processes) or add physical RAM. (Faster CPU does NOT help).
    • T10 Q3 (CPU 20%, paging disk 97.7%): Helps: fewer processes, more RAM, a faster or additional paging disk. Does not help: faster CPU, more processes, a merely bigger paging disk.
  • Page Fault Frequency (PFF): Per-process fault-rate feedback. Rate above the upper threshold: give the process a frame (or swap another process out). Rate below the lower threshold: take a frame away.
  • Working-set window Δ\Delta: Too small gives high fault rate and too much multiprogramming. Too large wastes frames and lowers multiprogramming.
  • Locality: C stores arrays in row-major order. Row-by-row loops touch one page for many accesses; column-by-column loops on a page-per-row array fault on almost every access. Arrays have good spatial locality; linked lists do not.
  • FIFO and LRU fault bounds: With NN distinct pages and length LL, any algorithm faults at least NN times (compulsory) and at most LL times. If M≥NM \ge N frames, FIFO and LRU both fault exactly NN times.

Symbolic link Small file holding a path; can cross file systems; becomes dangling if the target is deleted. A new file at the same path is silently reached through the old link (T11 Q1a).
Shared copy vs private copies One copy: no disk waste and updates visible to all, but needs locking. Private copies: isolated, but wasteful and they diverge.
UNIX permissions rwx for owner / group / other (r=4, w=2, x=1). r-x r-x --x: group can also read (additional Q7a: False). Directory: r list, w create or delete entries, x traverse. No x on a directory means no access to anything inside.
Linked allocation No external fragmentation (additional Q7c: False); random access walks the chain.
Block size Large: high data rate, low space use. Small: high space use, low data rate. Two block sizes (large body + small tail pieces) get both (T11 Q4).
Free space Bitmap (1 bit per block): fast, easy to find contiguous runs, needs blocks/8\text{blocks}/8 bytes. Linked free list: no extra space but slow to traverse.

RAID Architecture Levels

  • RAID 0 (Striping): High throughput, zero fault tolerance (1/MTTF1/MTTF multiplies).
  • RAID 1 (Mirroring): 100% capacity redundancy overhead, high fault tolerance.
  • RAID 0+1 (Mirror of Stripes): Striped sets mirrored. Single failure invalidates an entire striped half.
  • RAID 1+0 (Stripe of Mirrors): Mirrored pairs striped together. Survives multiple disk crashes across separate pairs. RAID 1+0 is vastly more reliable than RAID 0+1.
  • RAID 5 (Distributed Parity): Data and XOR parity blocks striped across n≥3n \ge 3 disks; survives one failure; capacity (n−1)×C(n-1) \times C.

Recipe 17: Synchronization Traces (Protocol Checker, Semaphore Values, Semaphore from TestAndSet)

Protocol Checker (Tutorial 4 Q1, Q3; Tutorial 5 Q2)

  1. Mutual exclusion: Run one process up to its critical section (CS), switch, and try to run the other into its CS. Start from the stated initial values.
  2. Progress: Look for a state where the CS is empty, a process wants in, and it can never get in because a shared variable holds the wrong value.
  3. Bounded waiting: Count how many times the other process can enter after the waiter has asked.

T4 Q1 (P0P_0: flag=true; while(turn==1); … turn=1. P1P_1: turn=0; while(flag and turn==0); … flag=false. Initial flag=false, turn=0):

  • Mutual exclusion fails. P1P_1 sets turn=0, sees flag=false and enters. Switch. P0P_0 sets flag=true, sees turn=0 (not 1) and enters. Both are inside.
  • Progress fails. P0P_0 leaves with turn=1. If P0P_0 asks again while P1P_1 stays in its remainder section, while(turn==1) spins forever and the CS is empty.
  • Bounded waiting holds. P0P_0 waiting enters as soon as P1P_1 runs turn=0, so P1P_1 enters 0 times. P1P_1 waiting enters when P0P_0 runs turn=1 after its CS, so P0P_0 enters at most once.

T4 Q3 (TestAndSet sets *target = false and returns the old value; lock starts true; entry while(TestAndSet(&lock)==false);; exit lock=false):

  • Mutual exclusion holds. The first process gets true and leaves the loop, and lock becomes false, so the other gets false and loops.
  • Progress fails. Nothing ever sets lock back to true. After the first CS the lock is false for ever, so every later TestAndSet returns false and the CS stays empty.

T5 Q2 (Wait: S--; if (S < -1) block();, Signal: S++; if (S <= 0) wakeup();, SS starts at 0):

  • Mutual exclusion holds. First Wait: S=−1S=-1, no block, enters. Second Wait: S=−2S=-2, blocks. Every Wait is paired with a later Signal, so S≤0S \le 0 always.
  • Progress holds. No process is blocked while S=0S = 0. The one oddity: Signal from −1-1 to 00 calls wakeup() with nobody waiting.

Use S=I−#Wait+#SignalS = I - \#\text{Wait} + \#\text{Signal}. While S<0S < 0, |S||S| processes are blocked.

  • 2 processes hold SS and 4 are blocked ⟹\implies S=−𝟒S = \mathbf{-4} (the holders are not blocked).
  • If 5 Signals and 2 Waits end at S=−1S = -1, then the start was S0=−1−5+2=−4S_0 = -1 - 5 + 2 = -4.

Deadlock-Free Semaphore Code (T5 Q1, Alice, 1 apple + 2 oranges)

Never hold two semaphores at once, so no circular wait can form:

  1. Wait(A)  (take 1 apple)
  2. Signal(A); Wait(O)  (release apples, then check oranges)
  3. Signal(O)  (2 oranges found: take them, release)
  4. Signal(O); Wait(A)  (not enough: release oranges, then reopen the apple basket)
  5. Signal(A)  (drop the apple back, release)

Semaphore Built From TestAndSet (T5 Q3)

Shared boolean lock = false guards only S.value and the queue S.L; do not hold it while sleeping.

Wait(S):   while (TestAndSet(&lock));
           S.value--;
           if (S.value < 0) { add this process to S.L; lock = false; block(); }
           else lock = false;

           S.value++;
