Labs 3 and 4 Quiz

Test yourself on the xv6 labs: Lab 3 (spinlocks, sleep/wakeup, semaphores, bounded buffer) and Lab 4 (Sv39 page tables, traps, lazy allocation). Answer each question on paper first, then open the drawer.

  • Fact questions check one idea from the lab. Apply questions need a trace or a calculation.
  • Lecture link questions tie the lab code back to Lectures 4, 5, 7 and 8.
  • Beyond the guide marks a point the lab guide leaves out but the code needs. The lab manual itself lists some of these as out of scope.

Part A. Lab 3: Synchronization and Semaphores

A1. Why kernel memory (Fact + Apply)

A parent declares a global int x = 0;, forks, and then both processes run for (i = 0; i < 1000; i++) x++;. The parent waits for the child, then prints x. What does it print, and why does this program not show the Lab 3 race?

A1: Answer

It prints 1000. fork() copies the parent’s user pages, so the child increments its own private copy of x. The parent never sees those increments. Nothing is shared, so nothing races.

Lab 3 puts ucnt[] and ubuf in kernel memory. All processes reach the same physical variables through system calls. Only then do parent and child really conflict.

A2. Atomic test-and-set (Apply)

acquire() is written naively as if (lk->locked == 0) lk->locked = 1;. Both CPU 0 and CPU 1 call it on a free lock. Show an interleaving where both enter. Then say what __sync_lock_test_and_set(&lk->locked, 1) returns to each CPU when they race.

A2: Answer

Bad interleaving:

Step CPU 0 CPU 1
1 reads locked == 0
2 reads locked == 0
3 writes locked = 1, enters
4 writes locked = 1, enters

Both are in the critical section. The check and the write are two separate steps, and the other CPU slips between them.

With the atomic swap, the hardware (amoswap) writes 1 and returns the old value in one indivisible step. The memory system orders the two swaps. The first one returns 0 and wins. The second returns 1, so it keeps spinning. The lock is acquired only by the CPU that sees the old value 0.

A3. push_off / pop_off nesting (Apply)

Interrupts are on. A CPU runs acquire(A); acquire(B); release(A); release(B);. Give noff and the interrupt state after each call. Then say what happens if interrupts were off before the first acquire.

A3: Answer
After noff Interrupts
acquire(A) 1 off
acquire(B) 2 off
release(A) 1 still off
release(B) 0 on

Releases need not be in reverse order. Only the counter matters. Interrupts return when noff hits 0.

If interrupts were already off at the start, push_off remembers that (the per-CPU intena flag). After the final pop_off, they stay off. This is the nesting that makes a lock safe to take inside code that already disabled interrupts. (intena is Beyond the guide.)

A4. What disabling interrupts does and does not do (Fact)

A teammate says: “push_off() already stops other CPUs, so the amoswap is redundant.” Refute this. Then explain what push_off is for.

A4: Answer

Disabling interrupts is local to one CPU. CPU 1 and CPU 2 keep running. Only the atomic amoswap gives mutual exclusion across the 3 cores.

push_off handles a same-core problem. A thread holds lock LL and an interrupt fires on that same CPU. If the handler tries to take LL, it spins forever, because the holder cannot run until the handler returns. That is a self-deadlock. With interrupts off while LL is held, the handler cannot start.

Two different jobs: amoswap = exclusion between CPUs. push_off = no re-entry on one CPU.

A5. Spin or sleep? (Apply)

Take the lab’s rough numbers: a context switch costs about 100 cycles. Choose spin or sleep for each wait, and say why.

  1. Waiting for a lock that is held for about 20 cycles by a thread running on another CPU.
  2. Waiting for a disk read that takes about 1,000,000 cycles.
  3. Waiting for a lock whose holder is on the same CPU and is not running.
A5: Answer
  1. Spin. 20 cycles of waiting is cheaper than the ~100-cycle switch.
  2. Sleep. Spinning wastes about a million cycles of a core. Sleeping lets another process use them.
  3. Sleep (or yield). Spinning cannot help. The holder cannot release the lock until it gets the CPU back, and the spinner is using it.

The lab manual says these numbers are assumptions, not measured xv6 cutoffs. State the assumption when you answer.

A6. The lost wakeup (Apply)

In sleep(chan, lk), xv6 takes p->lock before release(lk). Suppose a buggy version releases lk first and takes p->lock afterwards. Walk through a schedule that loses a wakeup. Then explain exactly which rule in the correct version blocks it.

A6: Answer

Bug schedule (consumer C sleeps, producer P wakes):

  1. C holds lk, sees the buffer is empty, calls sleep.
  2. Buggy sleep calls release(lk).
  3. P takes lk, adds data, calls wakeup(chan). C is not SLEEPING yet, so the loop finds nobody.
  4. C now takes p->lock, sets SLEEPING, and switches away.
  5. Nobody will call wakeup again. C sleeps forever.

Correct version. wakeup must take p->lock before it reads p->state or p->chan. sleep holds p->lock from before release(lk) until the process is really SLEEPING and inside sched(). P can take lk at step 3, but its wakeup blocks on C’s p->lock. It only proceeds after C is fully asleep. Then it sees SLEEPING and the right chan, and wakes C.

The handover has no gap where C holds neither lock.

A7. Why while, not if (Apply)

Three processes A, B and C are asleep in sem_wait on a semaphore whose value is 0. One process calls sem_signal once. Trace the value and each process’s state. Then say what goes wrong if sem_wait used if (sem->value == 0) sleep(...) instead of while.

A7: Answer

sem_signal: value becomes 1, and wakeup(sem) marks all three RUNNABLE. wakeup is a broadcast.

Say they run in the order A, B, C. Each returns from sleep holding sem->lock:

Process Sees value Does value after
A 1 value--, proceeds 0
B 0 goes back to sleep 0
C 0 goes back to sleep 0

With if: B and C skip the re-check. They decrement, giving value = -2. Three processes pass on one signal. That breaks the lab’s rule that the value never goes negative. It also breaks the guarantee the semaphore gives.

Waking only means “the condition may hold now”. Another process can take the resource first. Always re-check.

A8. Textbook semaphore vs the lab semaphore (Apply + Lecture link)

A semaphore starts at 0. Three threads call wait. Then two other threads call signal. After everything settles, what is the semaphore value, and how many threads are still blocked, under (a) the textbook definition from Lecture 4 and (b) the lab’s sem_wait?

A8: Answer
After 3 waits After 2 signals (settled) Blocked
(a) Textbook −3-3 −1-1 1
(b) Lab 0 0 1
  • Textbook: wait always does S←S−1S \leftarrow S-1, then blocks if S<0S<0. |S||S| counts the blocked threads. Each signal adds 1 and unblocks one thread.
  • Lab: wait blocks while S==0S == 0 and decrements only when S>0S>0. The value never goes negative, so it does not show how many are waiting. Both signals are consumed by two waiters, which leaves 0 and one sleeper.

Both versions let exactly two threads through. Only the value differs. Do not mix the two meanings in an exam answer.

A9. Protect the counter (Apply)

Parent and child each do N = 1000 rounds of val = ucnt_get(0); ucnt_set(0, val+1);. For each variant, say whether the final count is always 2000, and why.

  1. No semaphore.
  2. sem_wait/sem_signal around ucnt_get alone, and again around ucnt_set alone.
  3. One semaphore around both calls, created with sem_init(1) before fork().
  4. Same as 3, but parent and child each call sem_init(1) after fork().
  5. Same as 3, but sem_init(0).
  6. Same as 3, but sem_init(2).
A9: Answer
  1. No. Lost update: both read XX, both write X+1X+1. The result is at most 2000, and usually less. (In theory it can drop as low as 2.)
  2. No. The race sits between the read and the write. Each call is protected alone, but another process can still run between them. The whole read-modify-write must be one critical section.
  3. Yes. Initial value 1 gives mutual exclusion. The semaphore lives in the kernel table, and the child’s copied semid names the same kernel entry.
  4. No. Each process allocates its own semaphore. They get different ids, and nothing excludes the other process.
  5. No, and worse: deadlock. Both block on sem_wait forever. The test hangs and never prints a count.
  6. No. Two processes can both pass wait, so there is no exclusion.

One run that prints 2000 does not prove the code is race-free. The manual says this.

A10. Count the semaphores (Apply)

The buffer has 16 slots. empty, full and mutex start at 16, 0 and 1. The producers write 10 characters in total and the consumer reads 4. With everyone idle, what are the three values? What does a producer do on its 17th write if there has been no read at all, and which semaphore does it block on?

A10: Answer

Net characters in the buffer: 10−4=610 - 4 = 6.

full =6= 6, empty =16−6=10= 16 - 6 = 10, mutex =1= 1. Check: empty + full = 16. That sum holds only while nobody is between a wait and its matching signal.

17th write with no reads: after 16 writes, empty = 0 and full = 16. The 17th producer blocks in sem_wait(empty) while holding nothing. A consumer read will signal empty and free it.

A11. Do you need the mutex? (Apply)

  1. Why do two producers need mutex even though empty already limits how many can enter? (b) Would one producer and one consumer need it? Use the fact that ubuf_write() uses tail, ubuf_read() uses head, and both call yield() after touching the slot but before moving the index.
A11: Answer

(a) empty only counts free slots. It does not make two producers take turns. Say empty = 5. Producers P1 and P2 both pass sem_wait(empty). P1 writes slot tail, then yield() lets P2 run. P2 sees the same tail, overwrites the slot, and both then advance tail. One character is lost and one slot is skipped. mutex makes each whole ubuf_write atomic. The yield() calls exist to make this bug show up.

(b) With one producer and one consumer, each index is touched by only one side. empty and full already stop the consumer reading an unwritten slot and the producer overwriting an unread one. So the mutex is not strictly needed there. The lab uses it because of the two producers. (This reasoning is Beyond the guide. It holds only if the buffer has no shared count field.)

A12. Deadlock from lock order (Apply + Lecture link)

The producer runs wait(mutex); wait(empty); write; signal(mutex); signal(full). The buffer is full. Trace the deadlock, then name the four Coffman conditions from Lecture 5 as they appear here. Does swapping the two signal calls cause a deadlock?

A12: Answer

Trace: The producer takes mutex, then blocks in wait(empty) because empty = 0. The consumer needs mutex to read, so it blocks in wait(mutex). Only a read can signal empty. Neither can move.

Coffman condition Here
Mutual exclusion mutex is held by one process.
Hold and wait Producer holds mutex while waiting for empty.
No preemption A semaphore cannot be taken away from its holder.
Circular wait Producer waits on the consumer’s signal(empty); consumer waits on the producer’s mutex.

Fix: wait for the counting semaphore first (empty or full), and take mutex only after. The consumer has the mirror problem if it takes mutex before full.

Swapping the signals is safe. A signal never blocks, so no one holds a resource while waiting. Order only changes how soon the other side wakes.

A13. When does the test finish? (Apply)

Two producers send 48 characters each. The consumer is told to read r characters and then exit. For which values of r does the parent’s wait() return? What happens if the producers send 90 total but the consumer waits for 96?

A13: Answer

Total written is 2×48=962 \times 48 = 96. After the consumer stops, at most 16 characters can sit in the buffer. The producers can finish only if 96−r≤1696 - r \le 16, so r≥80r \ge 80.

  • r=96r = 96 (the test): everything drains. The parent’s wait() returns for both producers.
  • r=70r = 70: 26 characters remain. The producers fill the buffer and block on empty forever, so the parent hangs on wait().

If only 90 characters are sent, the consumer’s last 6 sem_wait(full) calls block forever. That is the mirror hang: the producers are done and the consumer is stuck.

Cleanup order matters. Free the semaphores only after the consumer finishes and both producers are reaped.

A14. Channels and cleanup (Fact)

  1. What is a sleep channel? (b) Suppose sem_signal always called wakeup(&semaphores[0]) no matter which semaphore it used. Is the program still correct? (c) What goes wrong if you call sem_free() while a child still sleeps on that semaphore?
A14: Answer

(a) A channel is just an address used as a tag. It is not a queue and holds no data. wakeup(chan) wakes processes whose p->chan equals it. sem_wait and sem_signal both use the address of struct semaphore, so semaphore A’s signal does not wake B’s sleepers.

(b) Still correct, because every waiter re-checks value in its while loop. A false wakeup only makes it go back to sleep. But it is wasteful: every signal on any semaphore wakes sleepers on all of them.

(c) sem_free() only marks the entry unused. It neither waits for nor wakes the sleepers. The orphans wait on a channel that nothing will signal. They can sleep forever, or the slot can be reused by a new sem_init and confuse them.

A15. Spinlock fairness (Lecture link)

Lecture 4’s simple TestAndSet spinlock gives mutual exclusion and progress. Which property does it lack, and does xv6’s acquire() fix it? Describe what could happen to CPU 2 when CPU 0 and CPU 1 repeatedly take and release the same lock.

A15: Answer

It lacks bounded waiting. xv6’s acquire() is the same simple test-and-set loop, so it does not fix this. Nothing orders the waiters.

If CPU 0 and CPU 1 keep winning the swap each time the lock frees, CPU 2 can spin without end (starvation). In practice the critical sections are tiny and starvation is rare. The guarantee is still missing. Lecture 4’s bounded-waiting TestAndSet variant (a waiting[] array and a hand-off scan) is the version that guarantees it.

A16. What the tests do not prove (Fact)

The manual says sem_basic checks the count sequence 1→0→11 \to 0 \to 1, and producer_consumer checks only that each received byte belongs to the set of characters in msg. Name one bug each test would miss.

A16: Answer
  • sem_basic never makes anyone wait on a zero value. A sem_wait that forgets to sleep, or a missing while re-check, still passes. Only a blocked waiter would show it.
  • producer_consumer checks membership only. A buffer that duplicates, drops or reorders characters can still pass, as long as every byte it prints is a legal character. The test does not compare the full stream.

Passing once is evidence, not proof. You need the argument about counts, mutex and call order.

Part B. Lab 4: Page Tables and Lazy Allocation

B1. Sv39 sizes (Fact + Lecture link)

  1. Why does each page-table level use exactly 9 index bits? (b) How big would a flat, single-level table be for a 39-bit space with 4 KB pages? (c) How many page-table pages (4 KB each) does xv6 need to map one page? Then to map two pages at VA 0x0 and 0x1000? At 0x0 and 0x200000? At 0x0 and 0x40000000?
B1: Answer

(a) A table is one 4 KB page. A PTE is 8 bytes. So it holds 4096/8=512=294096/8 = 512 = 2^9 entries, and log⁡2512=9\log_2 512 = 9 index bits per level. Three levels give 2727 bits, plus the 1212-bit offset gives 3939 bits.

(b) A flat table needs 2272^{27} entries ×\times 8 B =230= 2^{30} B == 1 GiB per process. This is why Lecture 7 uses hierarchical tables.

(c) Page-table pages needed (excluding the data page):

Mapped VAs Why Table pages
0x0 root + one L1 + one L0 3
0x0, 0x1000 same L0 table (VPN[0] = 0, 1) 3
0x0, 0x200000 VPN[1] differs: new L0 4
0x0, 0x40000000 VPN[2] differs: new L1 and new L0 5

Page tables grow only where the address space is used.

B2. Decompose an address (Apply)

Split the virtual address 0x80003FFF into VPN[2], VPN[1], VPN[0] and the offset. Which byte of the page is it?

B2: Answer

Offset = low 12 bits = 0xFFF = 4095 (the last byte of the page).

VPN = 0x80003FFF >> 12 = 0x80003 = 524291.

  • VPN[0] = VPN mod 512 = 3.
  • VPN[1] = (VPN >> 9) mod 512 = 1024 mod 512 = 0.
  • VPN[2] = VPN >> 18 = 2.

Check: (2 << 30) + (0 << 21) + (3 << 12) + 0xFFF = 0x80000000 + 0x3000 + 0xFFF = 0x80003FFF. ✓

Walk order: root[2] →\to L1[0] →\to L0[3] →\to frame, then byte 4095.

B3. Decode a PTE (Apply)

A leaf PTE holds 0x20048C17. Give its flags, the physical frame address, and the physical address for byte offset 0x456. What would change if the low byte were 0x01?

B3: Answer

Low byte 0x17 == 0001 0111: V, R, W, U set; X clear. A valid, readable, writable, user data page (not executable).

PPN = PTE >> 10 = 0x80123. Frame base = PPN << 12 = 0x80123000. This is PTE2PA. The reverse, PA2PTE, is (pa >> 12) << 10.

Physical address = 0x80123000 + 0x456 = 0x80123456. The offset is copied unchanged from the virtual address.

With low byte 0x01 only V is set: R, W, X are all 0. That makes it an intermediate pointer to the next-level table at 0x80123000, not a leaf.

B4. What walk() allocates (Apply)

A process page table has only its root page. For one fresh virtual address, what does walk(pt, va, 0) return? What does walk(pt, va, 1) do, and what is the V bit of the PTE it returns? What if the L1 and L0 tables already exist but that leaf PTE is zero?

B4: Answer
  • walk(pt, va, 0): the root entry is invalid and alloc == 0, so it returns 0 (null).
  • walk(pt, va, 1): it calls kalloc() twice, once for the L1 table and once for the L0 table. It zeroes each and links it with PA2PTE(...) | PTE_V. It returns a pointer to the L0 entry. That entry is still 0, so V is clear. The caller (mappages) fills it in.
  • Tables exist but the leaf is zero: walk returns a non-null pointer to an entry with V = 0.

So walk allocates page-table pages, never data pages. And a non-null result does not mean the page is mapped. That is why countpp() checks pte != 0 && (*pte & PTE_V).

B5. walkaddr() refusals (Apply)

List the four cases where walkaddr() returns 0. A user program passes the address TRAPFRAME as the buffer to read(). What happens, and why?

B5: Answer

It returns 0 when: (1) va >= MAXVA, (2) walk returns null (a missing table), (3) the leaf has V = 0, (4) the leaf has U = 0.

TRAPFRAME is mapped in the user page table, so (1) to (3) pass, but it has no PTE_U. Case (4) fires, walkaddr returns 0, and the system call fails with -1. The kernel does not copy into its own private page on a user’s say-so.

The PTE_U check is what stops a user passing a pointer to kernel-only data. (This is the same wall that stops user code touching the trampoline.)

B6. The guard page (Fact + Apply)

  1. What flags does the stack guard page have, and does it have a physical frame? (b) Why would a countpp() built on walkaddr() give the wrong answer, and by how much? (c) A user program recurses without end. What trap occurs, and what happens next in the Lab 4 kernel?
B6: Answer

(a) V is set and U is cleared (exec() calls uvmclear). It has a frame. Kernel-side access works. User-mode access faults.

(b) walkaddr rejects U = 0, so it skips the guard page and undercounts by 1. The manual counts the guard page’s frame. Use walk(..., 0) and test V only.

(c) The stack grows down into the guard page. A user-mode store there faults (scause 15, or 13 for a load). lazy_alloc sees va < p->sz, then finds the PTE already valid and returns -1. The process is killed with setkilled.

That check matters. Without it the handler would call kalloc() and mappages() over a valid PTE. mappages panics with “remap” and brings the whole kernel down. (The panic detail is Beyond the guide.)

B7. countvp and countpp (Apply)

A fresh process has countvp() = countpp() = 6: code, data, guard and stack. It then runs the steps below on the lazy kernel. Give both counts after each step.

  1. sbrk(10 * 4096)
  2. write one byte in heap page 3, then one in heap page 8, then another in heap page 3
  3. read one byte from heap page 10
  4. sbrk(-2 * 4096)
  5. A separate run: from the start, sbrk(100) on a page-aligned break.

How do the answers to 1 to 3 change under eager allocation?

B7: Answer
Step countvp countpp Why
1 16 6 sz grows by 10 pages. No frame yet.
2 16 8 Pages 3 and 8 fault once each. The second write to page 3 hits a mapped page.
3 16 9 A read also faults (cause 13) and gets a zeroed frame.
4 14 8 Heap pages 9 and 10 are released. Page 10 had a frame (freed). Page 9 was a hole (skipped).
5 7 unchanged countvp rounds up: ⌈100/4096⌉\lceil 100/4096 \rceil adds one page. Lazy adds no frame.

Eager: step 1 gives 16 / 16. Steps 2 and 3 change nothing in countpp, because every frame already exists. This matches lazytest: +30 and +30 at once under eager, +30 and +0 under lazy.

Step 4 only works because uvmunmap now skips holes (see B13).

B8. Reading the trap registers (Apply)

For each event, give scause, sepc, and stval. Assume the instruction is at 0x1A4.

  1. ecall for a system call.
  2. lw a0, 0(t0) with t0 = 0x7000, an unmapped heap address.
  3. sw a0, 0(t0) with the same t0.
  4. A jump to an address in a page that has no X permission, say 0x9000.

For (2), how many faults occur for a[0] = a[0] + 1 on a fresh lazy page?

B8: Answer
# scause sepc stval
1 8 0x1A4 (the ecall) not used
2 13 (load page fault) 0x1A4 0x7000
3 15 (store page fault) 0x1A4 0x7000
4 12 (instruction page fault) 0x9000 0x9000

sepc is the instruction. stval is the data address. In (4) the instruction itself is at the bad address, so they match. Cause 14 does not exist (reserved).

a[0] = a[0] + 1 does a load then a store. The load faults once (13). The handler maps the page read and write, so the store finds it mapped. One fault total.

B9. Why epc is not advanced (Apply)

  1. A system call advances epc by 4. A page fault must not. Why? (b) Say lazy_alloc also did epc += 4. What does the program do wrong, and does it crash? (c) What if ecall did not advance epc?
B9: Answer

(a) ecall has already done its job when the kernel runs. The kernel continues after it. The faulting lw or sw never completed. The program needs that instruction to run, so the handler returns to the same instruction, now with a valid PTE.

(b) The load or store would be skipped. A store is lost. A load leaves a stale value in its register. The program then continues with wrong data and no crash: a silent corruption. This is a nasty bug to find.

(c) sret would re-execute the ecall, so the same system call would run forever.

B10. The bound check (Apply)

p->sz = 0x4050. For each fault address, say whether the lab’s lazy_alloc maps a page or kills the process. Assume page 0x4000 has no frame yet, and 0x3000 is an already mapped stack page.

0x4040, 0x4060, 0x5000, 0x3000

B10: Answer
va Result Reason
0x4040 map <sz< sz, page 0x4000 has no valid PTE
0x4060 kill ≥sz\ge sz (beyond the break)
0x5000 kill ≥sz\ge sz
0x3000 kill <sz< sz, but the PTE is already valid: this is a protection fault, not a missing page

Check va < p->sz before rounding. If you round 0x4060 down to 0x4000 first, it passes 0x4000 < 0x4050 and is wrongly accepted.

Beyond the guide: under eager xv6, 0x4060 would not fault. uvmalloc rounds up and maps the whole last page. The lab’s check is stricter than the old behaviour.

B11. Null pointer (Apply)

In xv6, program text is mapped at virtual address 0. What happens for int x = *(int*)0; and for *(int*)0 = 1;?

B11: Answer
  • Load from 0: it succeeds. Address 0 is a valid user page (code), readable. x gets the first bytes of the program. No fault.
  • Store to 0: the text page is mapped read and execute, not writable. The store faults (scause 15). lazy_alloc sees va < sz and a valid PTE, so it returns -1 and the process is killed.

So a null write crashes but a null read does not. (The exact permissions come from exec(); this is Beyond the guide.)

B12. Why the trampoline is shared (Fact + Apply)

  1. At the moment of the trap, which page table is active? (b) Why must TRAMPOLINE be at the same virtual address in user and kernel tables? (c) Why is TRAPFRAME mapped only in the user table? (d) If the kernel table mapped the trampoline elsewhere, which instruction would fail? (e) Neither page has PTE_U, yet trap code runs there. Why is that allowed?
B12: Answer

(a) The user page table. The hardware changes privilege mode but does not touch satp.

(b) uservec must change satp while it is running. The pc keeps counting up. The next fetch after the csrw satp is translated through the kernel table. Only if the trampoline sits at the same VA does that fetch find the same code. Both tables map it to the same physical frame.

(c) Each process has its own trapframe. Mapping it in the user table lets uservec save registers x1 to x31 before satp changes. The kernel reaches it later through p->trapframe.

(d) The instruction right after csrw satp, a1. It would be an instruction page fault with nothing left to handle it.

(e) PTE_U = 0 only blocks user mode. The trap code runs in supervisor mode. This also stops user code reading or jumping into these pages.

B13. Unmapping holes (Apply)

A process calls sbrk(100 * 4096), touches 3 of those pages, then exits. In uvmunmap over the heap, how many kfree calls happen? Why did the original code panic, and what makes walk return 0 inside this loop?

B13: Answer

3 kfree calls. The other 97 pages are holes and are skipped with continue.

The original uvmunmap assumed every page in the range had a frame and panicked on walk == 0 or V == 0. That was right under eager allocation. Lazy allocation leaves unmapped holes, so those panics would crash the kernel on every normal exit().

walk(..., 0) returns 0 when a whole table is missing, for example a 2 MB region where no page was ever touched (no L0 table was created). V == 0 covers a missing leaf in an existing table.

The PTE_FLAGS == PTE_V check (“not a leaf”) stays, because that one is a real bug.

B14. System calls and lazy pages (Beyond the guide)

A process does char *buf = sbrk(4096); read(fd, buf, 100);. It never touched buf. With the lab’s lazy code, can read succeed? Why or why not, and what would fix it?

B14: Answer

No. It fails. Inside read, the kernel copies out through walkaddr, which finds V = 0 for the untouched page and returns 0. The syscall returns -1, even though the address is legal. The lab’s usertrap handler only runs for faults from user mode. This copy happens in kernel code, and it never raises a user page fault.

Fix: make the kernel copy routines (copyout, copyin, or walkaddr) apply the same lazy check: if va < p->sz and the page is absent, allocate it first.

The manual lists fork(), copyin and copyout with untouched pages as outside the core exercise, and says lazytest does not test them. Know it as a limit of the lab.

B16. The cost of a 3-level walk (Lecture link)

Without a TLB, how many memory accesses does one load need under Sv39? With a TLB (lookup 1 ns, memory 100 ns, hit rate 98%), compute the EAT, counting a TLB miss as one lookup, a 3-level walk, then the data access.

B16: Answer

4 accesses without a TLB: 3 page-table reads (L2, L1, L0) plus the data.

  • Hit: 1+100=1011 + 100 = 101 ns.
  • Miss: 1+3×100+100=4011 + 3 \times 100 + 100 = 401 ns.

EAT=0.98×101+0.02×401=98.98+8.02=107 ns\text{EAT} = 0.98 \times 101 + 0.02 \times 401 = 98.98 + 8.02 = 107\text{ ns}

Deeper tables save memory (see B1) but make a miss costlier. The TLB hides that cost.

B17. Lazy or eager? (Apply)

  1. A program reserves 50 MB but really uses only 100 KB. Compare the physical frames used by eager and lazy allocation. (b) Name two ways lazy allocation can be worse.
B17: Answer

(a) Eager: 50×1024/4=12,80050 \times 1024 / 4 = 12{,}800 frames. Lazy: 100/4=25100/4 = 25 frames. The saving is about 99.8%.

(b)

  1. Touch everything: if the program uses all NN pages, lazy pays NN separate traps (save registers, switch tables, walk, return), while eager allocates them in one batch.
  2. Late failure: sbrk() can succeed with no RAM behind it. When RAM runs out, the failure arrives later as a kill at a random store, not as sbrk() returning -1. Code that checks sbrk for failure is no longer enough.

Also: lazytest cannot show the over-commit case, and the manual says to explain its limits.

B18. Why fault dies but lazytest lives (Apply)

fault read calls sbrk(0), then reads the first unallocated page, PGROUNDUP(end). After the Lab 4 changes, it is still killed. lazytest touches reserved pages and continues. What is the difference?

B18: Answer

lazytest first calls sbrk(4096 * 30), so p->sz covers those pages. A first touch has va < sz and no PTE, so the handler maps a frame and the program continues.

fault uses sbrk(0), which does not reserve anything. Its target is at or above p->sz. lazy_alloc returns -1 for va >= sz, and the process is killed. Only the faulting process dies. The kernel and the shell keep running.

Reserve first, then touch is the rule. A fault is only repaired when the address was reserved by sbrk.
