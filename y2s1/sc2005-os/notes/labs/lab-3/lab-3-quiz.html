Lab 3 Quiz: Synchronization and Semaphores

Tap an option to lock in your answer. The page marks it and shows the reason. Every wrong option is a real misconception. The sections follow the Lab 3 Guide.

1. Why the Shared Data Lives in the Kernel

01A parent declares a global int x = 0;, forks, and both processes run x++ 1,000 times. The parent waits for the child, then prints x. What does it print?

C. fork() copies the parent’s user pages. The child changes its own private x, so nothing is shared and nothing races. That is why Lab 3 puts ucnt[] and ubuf in kernel memory, which every process reaches through system calls.

2. Spinlocks and Hardware Atomicity

02A naive acquire() does if (lk->locked == 0) lk->locked = 1;. Why does this fail with CPUS=3?

A. The check and the write are two separate steps, and another CPU can run between them. amoswap (through __sync_lock_test_and_set) writes 1 and returns the old value in one indivisible step.

03Two CPUs call acquire() on a free lock at the same instant. What decides which one gets it?

B. The memory system puts the two atomic swaps in an order. The first returns 0 and wins. The second returns the 1 the first one wrote, so it spins. Interrupts are per CPU and decide nothing between CPUs.

04Someone removes push_off() from acquire() but keeps the atomic swap. What new failure becomes possible?

D. Interrupts off stops a CPU deadlocking with its own interrupt handler: the holder cannot run until the handler returns. Keeping other CPUs out is still the atomic swap’s job.

05Interrupts are on. A CPU runs acquire(A); acquire(B); release(A);. What is the interrupt state now?

D. push_off and pop_off keep a per-CPU counter. Two acquires make it 2; one release makes it 1. The order of the releases does not matter, only the count.

06A CPU calls acquire(lk) on a lock that it already holds. What happens?

B. acquire() checks holding(lk) before it spins. Without that check, the CPU would spin forever on a lock that only it can release.

07Lecture 4’s simple test-and-set spinlock gives mutual exclusion and progress. Which property does it lack, and does xv6’s acquire() fix it?

C. xv6 uses the same simple loop, and nothing orders the waiters. If CPU 0 and CPU 1 keep winning the swap, CPU 2 can spin without end. The critical sections are tiny, so this is rare, but the guarantee is missing.

3. Sleep and Wakeup

08For a wait of 10 cycles, and for a wait of 10,000 cycles, which is cheaper?

C. Spinning costs as long as the wait. Sleeping costs a fixed trip through the scheduler and back, about hundreds to thousands of cycles. These are assumptions, not measured xv6 cutoffs: state them in your answer.

09On a machine with one CPU, a process finds a lock held. Why is spinning a bad choice?

D. Spinning pays off only when the holder is running on another CPU and will release soon. With one CPU, the spinner wastes its whole time slice.

10Which statement about chan in sleep(chan, lk) is correct?

A. A channel is a label. wakeup(chan) wakes every process whose p->chan equals it. It is not a queue and it does not order the sleepers.

11Suppose sleep() called release(lk) first and only then acquire(&p->lock). What goes wrong?

C. That opens a gap where the waiter holds neither lock. wakeup() finds nobody asleep and does nothing; then the waiter sleeps forever. This is the lost wakeup.

12How does the correct order in sleep() prevent the lost wakeup?

D. The waiter takes p->lock before it releases lk, and keeps it until it is SLEEPING and inside sched(). So at every moment one of the two locks covers it, and wakeup() can never see it “about to sleep”.

13wakeup(chan) has just returned. Process P had been sleeping on chan. P is now:

D. wakeup() only changes SLEEPING to RUNNABLE. It reserves nothing, so another process can take the resource first. That is why the waiter re-checks in a while loop.

14Why does wakeup() wake every matching sleeper instead of just one?

D. Waking everyone is safe because of the while re-check: a sleeper that cannot proceed goes back to sleep. “Each sleeper must decrement once” is the if-bug way of thinking.

4. The Kernel Semaphore

15Which function finds a free slot in semaphores[] and returns its index?

C. seminit() sets up the whole array at boot. sem_init() is the user system call. sys_sem_init() is its handler, which only passes the call on to sem_alloc().

16Three processes sleep in sem_wait on one semaphore whose value is 0. One process calls sem_signal once. What happens?

B. wakeup() wakes everyone on the channel. The first to run sees 1 and takes it. The other two see 0 in their while loop and go back to sleep. The value never drops below 0.

17A semaphore’s value is 0 and two processes sleep in sem_wait. A student wrote if instead of while. One sem_signal arrives. What is the worst-case value afterwards?

B. The signal makes the value 1. Both sleepers wake, skip the check and decrement: 1→0→−11 \to 0 \to -1. Two processes pass on one signal.

18A semaphore starts at 0. Three processes call wait, then two others call signal. After everything settles, what are the values under the textbook semaphore (Lecture 4) and the lab’s semaphore?

A. The textbook wait always decrements, so |S||S| counts the blocked: 0→−3→−10 \to -3 \to -1. The lab’s wait sleeps while the value is 0 and never goes negative, so it stays at 0. Both let exactly two processes through.

19In this lab, sem_getvalue() returns 0. What can you conclude about waiting processes?

A. The lab’s value never goes negative, so it does not count the waiters. Only the textbook semaphore uses a negative value to show how many are blocked.

20Why does sem_wait pass &sem->lock into sleep()?

A. If the waiter slept while holding sem->lock, the signaller could never take it to increment the value, and everyone would be stuck. sleep() releases the lock without a gap and takes it back before it returns.

21struct semaphore holds lock, value, in_use in that order. A student’s sem_wait sleeps on sem, but sem_signal calls wakeup(&sem->value). What happens?

A. lock is the first field, so &sem->value is a different address from sem. Channels match only on the exact address. The value still rises, so a later sem_wait passes, but the sleepers stay asleep.

22sem_signal always calls wakeup(&semaphores[0]), whatever semaphore it signals, and every sem_wait sleeps on &semaphores[0] too. Is the program correct?

B. Each woken process re-checks its own semaphore’s value in its while loop. A false wakeup only sends it back to sleep. Correctness holds; the cost is many useless wakeups.

23What does sem_basic actually verify?

B. It never waits on a value of 0, so blocking, sleeping, waking and the re-check are never tested. A sem_wait that forgets to sleep still passes.

24A parent calls sem_free(id) while its child is still asleep in sem_wait(id). What happens to the child?

A. sem_free only clears in_use. It neither wakes sleepers nor waits for users. Rule: allocate before fork(), free only after every user has finished.

5. The Shared Counter

25Parent and child each run val = ucnt_get(0); ucnt_set(0, val + 1); 1,000 times with no semaphore. What is the final count?

A. Both can read the same old value XX and both write X+1X + 1. Two increments become one. Entering the kernel does not make the pair atomic: two calls are two separate trips. One run that prints 2000 proves nothing.

26A student puts sem_wait / sem_signal around ucnt_get alone, and a second pair around ucnt_set alone. The count is sometimes below 2000. Why?

C. The race sits between the read and the write. The other process can read the same old value in that gap. The whole read-modify-write must be one critical section.

27A student calls sem_init(1) inside do_work(), which runs after fork(). What is the final count?

D. Two calls make two different semaphores. Each process excludes only itself. Create the semaphore once, before fork().

28The semaphore is created before fork() with sem_init(0) instead of sem_init(1). What happens?

A. A value of 0 means “none free”. Nobody ever signals first, so both processes sleep forever and no count is printed.

29The same, but with sem_init(2). What is the final count?

C. Value 2 lets two processes pass wait at the same time, so there is no mutual exclusion. Mutual exclusion needs a start value of 1.

30race_test calls sem_init(1) and does not check the result. All 32 slots are still taken by earlier runs that crashed. What happens?

D. sem_init returns −1. Each sem_wait(-1) fails the supplied error check and returns at once, so the increments run unprotected. Slots leak because kernel memory survives between runs until xv6 reboots. Always check for −1.

31Why does the child’s copy of semid reach the parent’s semaphore?

B. fork() copies the variable, but the variable is only an index into semaphores[]. Both processes pass the same number, so both reach the same kernel semaphore.

32When may the parent call sem_free on the counter’s semaphore?

C. The order is: wait(0), then check the count, then sem_free. Freeing earlier can leave the child using a slot that a new sem_init reuses.

6. The Bounded Buffer

33The 16-slot buffer starts empty. What are the starting values of empty, full and mutex?

B. empty counts free slots (all 16), full counts filled slots (none), and mutex = 1 lets one process touch the indices at a time.

34The buffer starts empty. The producers have written 10 characters and the consumer has read 4. Nobody is inside a critical section. What are the values?

D. Six characters are in the buffer: full = 10 − 4 = 6 and empty = 16 − 6 = 10. The mutex is back to 1. empty + full = 16 holds only while nobody is between a wait and its signal.

35Which index does each buffer function use?

A. The comment above struct ubuf reverses the roles. The manual says it is wrong: follow the function bodies.

36Why do ubuf_read() and ubuf_write() call yield() between using a slot and advancing its index?

B. Without the yield(), a bad interleaving is rare and the bug may hide. With it, a missing mutex corrupts the buffer almost every run.

37A student uses only empty (16) and full (0), with no mutex. What can go wrong with two producers?

D. Both pass wait(empty). Producer A writes data[tail] and yields. Producer B writes the same slot. Both advance tail, so one character is lost and one slot is never written. Counts limit how many slots are used, not which index.

38A producer runs wait(mutex); wait(empty); write; signal(mutex); signal(full). When does this deadlock?

A. With the buffer full, the producer sleeps on empty while holding mutex. The consumer needs mutex to read and free a slot. Neither can move. All four Coffman conditions hold: mutual exclusion, hold and wait, no preemption, circular wait.

39The buffer starts empty. The consumer does wait(mutex) before wait(full). What happens?

C. This is the mirror of the producer case. Rule: wait on the counting semaphore first, then take the mutex. Never sleep for space or data while you hold the mutex.

40A producer swaps its two signals: signal(full) before signal(mutex). What happens?

B. signal never blocks, so nobody holds a resource while waiting. The order of signals only changes how soon the other side wakes. The order of waits is what matters.

41One producer and one consumer share the buffer (no second producer). Is the mutex strictly needed?

B. The producer alone moves tail and the consumer alone moves head. full stops the consumer reading an unwritten slot; empty stops the producer overwriting an unread one. The lab needs the mutex because it has two producers. (Not in the lab guide; it holds only if the buffer has no shared count field.)

42Two producers send 48 characters each. The consumer reads r characters and then stops. For which r can both producers finish?

C. 96 characters are sent and at most 16 can wait in the buffer. The producers finish only if 96−r≤1696 - r \le 16, so r≥80r \ge 80. With fewer reads, they block on empty forever and the parent hangs in wait().

43producer_consumer prints PASS. What does that establish?

D. The consumer only checks that each byte is one of c, a, f or e. Order, duplicates and lost bytes are not checked. PASS supports your argument; it does not prove correctness.
