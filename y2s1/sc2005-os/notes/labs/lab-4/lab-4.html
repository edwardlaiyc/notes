Lab 4: Page Tables and Lazy Allocation

Modern operating systems decouple virtual memory addresses referenced by executing software from the underlying physical RAM addresses managed by hardware. This virtualization enables memory protection, process isolation, and dynamic memory growth.

Lab 4 explores the RISC-V Sv39 multi-level paging architecture in xv6:

  1. Sv39 Virtual Memory Translation: Understanding the 3-level page table walk, Page Table Entry (PTE) bits, and page translation software primitives (walk() and walkaddr()).
  2. Virtual vs. Physical Memory Accounting: Implementing countvp() and countpp() system calls to measure virtual page reservations versus allocated physical frames.
  3. Trap Architecture & Page Fault Inspection: Tracing page faults via RISC-V hardware registers (scause, sepc, stval) and the trampoline switching mechanism.
  4. Lazy Heap Allocation: Redesigning sbrk() to lazily defer physical frame allocation until the process touches memory, handling page faults transparently.

1. RISC-V Sv39 Virtual Memory Architecture

RISC-V uses the Sv39 paging scheme: virtual addresses are 39 bits wide, mapping into a 56-bit physical address space.

Address Decomposition

A page is 4 KB=4096 bytes=212 bytes4\text{ KB} = 4096\text{ bytes} = 2^{12}\text{ bytes}. The bottom 12 bits form the page offset, while the upper 27 bits form the Virtual Page Number (VPN):

│    VPN[2]    │    VPN[1]    │    VPN[0]    │       Page Offset       │
│   (9 bits)   │   (9 bits)   │   (9 bits)   │        (12 bits)        │
└──────────────┴──────────────┴──────────────┴─────────────────────────┘
  • PTE Size: In 64-bit RISC-V (Sv39), each Page Table Entry (PTE) occupies 64 bits (8 bytes=23 bytes8\text{ bytes} = 2^3\text{ bytes}).
  • Table Capacity: Each physical page table occupies exactly one 4 KB4\text{ KB} (4096 bytes=212 bytes4096\text{ bytes} = 2^{12}\text{ bytes}) physical frame, accommodating: 4096 bytes per frame8 bytes per PTE=512=29 Page Table Entries\frac{4096\text{ bytes per frame}}{8\text{ bytes per PTE}} = 512 = 2^9\text{ Page Table Entries}
  • Index Width: Because each table holds 512=29512 = 2^9 entries, each translation level requires exactly log⁡2(512)=9 bits\log_2(512) = 9\text{ bits} to index one PTE.
  • Tree Depth: 3 levels of 9-bit indices (VPN[2]\text{VPN}[2], VPN[1]\text{VPN}[1], VPN[0]\text{VPN}[0]) consume 3×9=27 VPN bits3 \times 9 = 27\text{ VPN bits}.   • Root Table: The hardware satp (Supervisor Address Translation and Protection) register holds the physical base frame address of the root (Level-2) page table.

Leaf vs. Intermediate PTEs: A valid PTE with PTE_R, PTE_W, and PTE_X all set to 0 is an intermediate pointer pointing to the physical address of the next-level page table. A PTE with any of R,W,XR, W, X set is a leaf entry pointing to physical RAM data.

2. Kernel Paging Primitives: walk() and walkaddr()

The kernel frequently navigates page tables in software using two foundational primitives in kernel/vm.c:

1. walk(): 3-Level Software Page Table Walk

walk() mimics hardware MMU translation in software, returning a pointer to the Level-0 PTE corresponding to a virtual address:

pte_t *walk(pagetable_t pagetable, uint64 va, int alloc) {
    if (va >= MAXVA)
        panic("walk");

    for (int level = 2; level > 0; level--) {
        pte_t *pte = &pagetable[PX(level, va)];
        if (*pte & PTE_V) {
            pagetable = (pagetable_t)PTE2PA(*pte); // Traverse to next-level table
        } else {
            if (!alloc || (pagetable = (pde_t*)kalloc()) == 0)
                return 0;
            memset(pagetable, 0, PGSIZE);
            *pte = PA2PTE(pagetable) | PTE_V; // Mark intermediate table pointer valid
        }
    }
    return &pagetable[PX(0, va)]; // Returns address of Level-0 Leaf PTE
}

Code Tracing & Key Primitives:

  1. PX(level, va): Macro extracting the 9-bit VPN index for that level:
    • PX(2, va): bits 38–30 (Root Level-2 index).
    • PX(1, va): bits 29–21 (Middle Level-1 index).
    • PX(0, va): bits 20–12 (Leaf Level-0 index).
    • Formula: shift va right by 12+9×level12 + 9 \times \text{level}, then keep the low 9 bits. So level 0 shifts by 12, level 1 by 21, level 2 by 30.
  2. Intermediate Table Traversal (level = 2 down to 1):
    • If *pte & PTE_V is set: the intermediate page table already exists. The macro PTE2PA(*pte) extracts the physical frame address of the child table, and execution advances downward.
    • If *pte & PTE_V is 0: the intermediate page table is absent.
      • If alloc == 0: walk() stops immediately and returns 0 (used for non-destructive inspection).
      • If alloc != 0: walk() allocates a fresh 4 KB4\text{ KB} frame via kalloc(), zeroes it with memset(), sets *pte = PA2PTE(pagetable) | PTE_V, and continues walking.
  3. Leaf Return (level = 0): Returns the memory address of the Level-0 PTE (&pagetable[PX(0, va)]).

2. walkaddr(): User-Virtual to Physical Address Translation

When a user process passes a virtual pointer to a kernel system call (such as a buffer address to read() or write()), the kernel must translate the user virtual address to a physical memory address while enforcing strict access control:

uint64 walkaddr(pagetable_t pagetable, uint64 va) {
    pte_t *pte;
    uint64 pa;

    if (va >= MAXVA)
        return 0;

    pte = walk(pagetable, va, 0);
    if (pte == 0)
        return 0;
    if ((*pte & PTE_V) == 0)
        return 0;
    if ((*pte & PTE_U) == 0)
        return 0;
    pa = PTE2PA(*pte);
    return pa;
}

Step-by-Step Execution Trace:

  1. Boundary Check (va >= MAXVA): Validates that va does not exceed the allowed user virtual address range (2382^{38}).
  2. Read-Only Walk (walk(pagetable, va, 0)): Calls walk() with alloc = 0. If any intermediate page table is missing, walk() returns 0, causing walkaddr() to safely return 0 (translation failed).
  3. Presence Verification (*pte & PTE_V): Ensures the Level-0 leaf PTE is valid and backed by physical RAM.
  4. Security & Permission Check (*pte & PTE_U): Confirms that the page has the User Mode flag (PTE_U) set. This prevents malicious user programs from tricking the kernel into reading or writing kernel-private data or unmapped guard pages via system calls.
  5. Physical Address Extraction (PTE2PA(*pte)): Shifts the 44-bit PPN left by 12 bits to retrieve the physical base address of the frame.

Warning

Why countpp() Must NOT Use walkaddr(): In Part 2, countpp() counts all physical frames allocated to the process address space. In xv6, the stack guard page has a physical frame allocated with PTE_V set, but its PTE_U flag is intentionally cleared to prevent user access. If countpp() invoked walkaddr(), it would fail at (*pte & PTE_U) == 0 and skip the guard page, incorrectly undercounting allocated physical frames by 1. Therefore, countpp() must call walk(p->pagetable, va, 0) directly and inspect only (*pte & PTE_V).

3. Process Memory Layout & Allocation Models

Architectural Context: How an xv6 Process Address Space is Formed

In xv6, memory isolation is enforced using two types of page tables:

  1. Kernel Page Table (kernel_pagetable): A single global page table used whenever the CPU executes in Supervisor Mode running kernel C code. It maps physical RAM directly, memory-mapped I/O devices (e.g. UART, virtio disk, PLIC), and kernel stacks.
  2. User Page Table (p->pagetable): Each running process (struct proc *p) maintains its own private page table. It defines the process’s virtual memory universe from virtual address 0 up to MAXVA. User code and variables reside here; kernel internal data structures are excluded so user code cannot access them.

1. Creation and ELF Loading (exec())

When a program is executed (such as the shell running ls or user/fault), the kernel invokes the exec() system call:

  • Text & Data (Starting at 0): exec() reads the executable ELF binary from disk, allocates physical frames via uvmalloc(), and maps the program’s machine instructions (.text) and static variables (.data) starting at virtual address 0.
  • The Guard Page: Directly above the program data, exec() calls uvmalloc for two pages, then calls uvmclear() on the lower one. uvmclear clears that page’s PTE_U bit. So the guard page has a physical frame (PTE_V set), but its PTE_U flag is 0. If the user stack overflows downward, the CPU attempts to touch this guard page in User Mode; because PTE_U is missing, the MMU immediately triggers a page fault exception, terminating the program before it can silently corrupt program code or variables.
  • The User Stack: Exactly one 4 KB4\text{ KB} page allocated directly above the guard page.
  • The Program Break (p->sz): Tracks the current upper boundary of the user address space. Initially, p->sz points to the top of the user stack.

2. Dynamic Heap Growth via sbrk()

User programs dynamically allocate memory at runtime using library routines like malloc(). In Unix and xv6, malloc() requests memory from the OS kernel via the sbrk(n) system call:

  • When called with n>0n > 0, sbrk() raises the program break p->sz by nn bytes. The heap occupies the dynamic region between the original stack top and p->sz.
  • When called with n<0n < 0, sbrk() contracts p->sz, freeing heap pages back to the kernel.

The path of one sbrk request (eager kernel):

  1. malloc runs out of free space and calls morecore() in user/umalloc.c. morecore asks sbrk() for at least 4,096 header units.
  2. The user stub (generated from user/usys.pl) puts the syscall number in a register and runs ecall. The CPU traps into the kernel.
  3. sys_sbrk() in kernel/sysproc.c saves addr = p->sz, calls growproc(n), and returns addr.
  4. growproc() in kernel/proc.c: if n>0n > 0 it calls uvmalloc(); if n<0n < 0 it calls uvmdealloc(); if n=0n = 0 it changes nothing. Then it sets p->sz.
  5. uvmalloc() in kernel/vm.c does the work, one page at a time:
for (a = PGROUNDUP(oldsz); a < newsz; a += PGSIZE) {
    mem = kalloc();                  // take a free frame (0 if RAM is exhausted)
    memset(mem, 0, PGSIZE);          // clear it
    mappages(pagetable, a, PGSIZE, (uint64)mem, PTE_R | PTE_U | PTE_W);
    // on any failure: kfree this frame, undo the earlier pages, return 0
}
  • The loop starts at PGROUNDUP(oldsz). If the old break is in the middle of a page, that page is already mapped. Example: p->sz = 0x3800, sbrk(0x1000). The new range is 0x3800–0x4800. Page 0x3000 is already mapped, so only page 0x4000 gets a new frame.
  • Why clear the frame: a recycled frame may still hold another process’s data. kalloc() fills a frame with junk bytes, not zeros (kfree fills with 1s and kalloc with 5s, as a debugging aid). Handing it over uncleared would leak data.
  • mappages(pt, va, size, pa, perm) installs leaf entries. It uses walk(..., 1) to create any missing tables. It panics with “remap” if an entry is already valid. It returns -1 if a table cannot be allocated.
Call Effect Returns
sbrk(n), n>0n > 0 grows the heap by nn bytes old break
sbrk(0) nothing current break
sbrk(n), n<0n < 0 shrinks; frees whole pages that fall off the end old break
failure nothing changes -1

sbrk returns the old break because that is the start of the new region (old break to old break + nn). It is the pointer morecore() turns into a free block.

3. High-Memory Fixed Mappings: Trapframe and Trampoline

When a trap (system call, interrupt, or page fault) occurs in user space, the CPU switches privilege mode from User Mode to Supervisor Mode. Crucially, the CPU hardware does NOT switch page tables automatically. It enters Supervisor Mode with satp still pointing to the process’s User Page Table (p->pagetable).

To allow the kernel to execute entry code and switch page tables without crashing, the kernel permanently reserves and maps two pages at the very ceiling of every address space near MAXVA = 2382^{38} (256 GB256\text{ GB}):

  • TRAPFRAME (MAXVA - 2 * PGSIZE): A private page for each process that stores its 31 saved user registers during a mode switch. It is mapped with PTE_R | PTE_W but no PTE_U, meaning User Mode code cannot read or alter it, but kernel entry code can read/write it while satp is still pointing to p->pagetable. (In the kernel, each process’s trapframe is accessed via its direct kernel pointer p->trapframe).
  • TRAMPOLINE (MAXVA - PGSIZE): Contains the mode-switching assembly code (uservec and userret). It is mapped with PTE_R | PTE_X (no PTE_U) at the identical virtual address (MAXVA - PGSIZE) in both the User Page Table and the Kernel Page Table, mapping to the exact same physical RAM frame.
Why Identical Virtual Addresses? (The satp & pc Handover)

Why must TRAMPOLINE share the same virtual address in both tables while other components do not?

Consider what happens inside uservec at the exact instruction that switches the page table:

  1. Before the switch:
    • satp holds: Physical address of p->pagetable (User PT).
    • pc holds: Virtual address inside Trampoline (e.g. MAXVA - PGSIZE + 0x50).
    • The CPU executes instructions in uservec, saving user registers (x1–x31x1\text{--}x31) into TRAPFRAME.
  2. At the switch instruction (csrw satp, a1):
    • The CPU executes the instruction that writes the address of kernel_pagetable into satp.
    • The active translation table instantly switches from User PT to Kernel PT.
  3. Immediately after the switch (the very next instruction fetch):
    • satp now holds: Physical address of kernel_pagetable (Kernel PT).
    • pc advances to: MAXVA - PGSIZE + 0x54 (the next sequential instruction).
    • Because TRAMPOLINE is mapped at the identical virtual address in kernel_pagetable, the MMU translates MAXVA - PGSIZE + 0x54 to the exact same physical code page. The CPU seamlessly fetches the next instruction (jr a0, jumping to C function usertrap()) without missing a beat.
Comparison with Non-Shared Components
Component In User PT (p->pagetable)? In Kernel PT (kernel_pagetable)? Virtual Address Why Different?
User Code, Stack & Heap Yes (with PTE_U) No 0x0 to p->sz Strictly isolated. The kernel does not execute user code directly in its own address space.
Kernel Data & Devices No Yes E.g. 0x10000000 (UART) User processes must never view or write kernel memory or device registers.
TRAPFRAME Yes (no PTE_U) No (accessed via direct PA) MAXVA - 2 * PGSIZE in User PT Each process has its own distinct trapframe; mapping it in User PT gives uservec access before satp changes.
TRAMPOLINE Yes (no PTE_U) Yes (no PTE_U) Identical: MAXVA - PGSIZE Required so pc does not fault when satp switches tables mid-execution.

If TRAMPOLINE were mapped at different virtual addresses between the two tables, then as soon as satp changed, the next instruction fetch at pc + 4 would look up an unmapped virtual address, crashing the machine immediately with an instruction page fault.

  • Why MAXVA = 2^38 instead of 2392^{39}: Sv39 supports 39-bit virtual addresses (512 GB512\text{ GB}), but in 64-bit RISC-V, address bit 38 is sign-extended across bits 63–39. xv6 defines MAXVA = 1L << (9 + 9 + 9 + 12 - 1) = 1L << 38 = 2^{38} (256 GB256\text{ GB}) to restrict user address space to the lower half, ensuring bit 38 is never set in valid user addresses and preventing unwanted sign-extension into negative 64-bit address space.

Eager vs. Lazy Allocation Paradigms

Operating systems handle heap growth under two contrasting paradigms:

  1. Eager Allocation (Default xv6): When user space invokes sbrk(n), sys_sbrk() immediately calls uvmalloc(). uvmalloc() allocates physical RAM frames with kalloc() for every newly requested page, clears them with memset(), and maps them into p->pagetable before returning the old break.
    • Limitation: If an application reserves a large memory buffer (e.g. 50 MB) but only accesses a small fraction, eager allocation wastes physical RAM by pre-allocating frames that may never be referenced.
  2. Lazy Allocation (Lab 4 Goal): Decouples virtual address reservation from physical memory allocation. When user space calls sbrk(n), the kernel simply advances p->sz and returns immediately without allocating physical frames (kalloc()). Physical RAM frames are only allocated and mapped when the process actually touches a page, triggering a page fault that the kernel intercepts and resolves transparently.

4. Part 2: Page and Frame Accounting System Calls

The lab introduces two accounting system calls to measure memory:

// countvp: Total virtual pages allocated to the process address space
int countvp(void) {
    struct proc *p = myproc();
    return PGROUNDUP(p->sz) / PGSIZE;
}

// countpp: Physical frames currently mapped to process address space
int countpp(void) {
    struct proc *p = myproc();
    int count = 0;
    for (uint64 va = 0; va < p->sz; va += PGSIZE) {
        pte_t *pte = walk(p->pagetable, va, 0); // alloc = 0! Do not allocate tables
        if (pte != 0 && (*pte & PTE_V))
            count++;
    }
    return count;
}

Critical Implementation Details

  1. Use walk(..., 0), not walk(..., 1): Counting must be strictly observational and never create page tables.
  2. Use walk(), not walkaddr(): walkaddr() rejects pages without PTE_U. Because the guard page has a physical frame and PTE_V set (lacking only PTE_U), walkaddr() would incorrectly skip the guard page.
  3. Null Check First: Always check pte != 0 before dereferencing *pte to avoid kernel panics when traversing unmapped address regions.
  4. countvp rounds up. A partly used last page counts as one page. p->sz = 0x3001 gives PGROUNDUP(0x3001) / PGSIZE = 0x4000 / 0x1000 = 4. The guard page is already inside 0–p->sz, so nothing is added on top.

What countpp Does Not Count

Frame Why it is not counted
Frames that hold the page tables They are reached through non-leaf entries, not through a user address.
The process’s kernel stack It lives in the kernel’s page table.
TRAPFRAME and TRAMPOLINE They sit far above p->sz, so the loop never reaches them.

The guard page’s frame is counted.

lazytest calls sbrk(4096 * 30), then writes one byte at offsets 0, 4096, …, 4096 × 29 from the returned address: 30 different pages. It prints both counts before, after sbrk, and after touching.

5. Part 3: RISC-V Trap Registers & The Trampoline

When a user process generates a trap (system call, timer interrupt, or page fault), the hardware switches from User Mode to Supervisor Mode and populates three hardware registers:

Register Hardware Function
scause Identifies the trap cause: 8 = system call (ecall), 12 = instruction fetch fault, 13 = load page fault, 15 = store/AMO page fault (cause 14 is reserved in RISC-V).
sepc Holds the virtual address of the instruction that was executing when the trap occurred.
stval Holds the exact faulting memory address (data address) that triggered the page fault.
  • sepc is where the code is. stval is what memory it touched. For a fault on a heap byte, sepc is a small address in the program’s code and stval is the heap address.
  • stval is not rounded to a page boundary. The handler rounds it down itself when it maps the page.
  • An AMO (atomic memory operation, such as amoswap from __sync_lock_test_and_set) both reads and writes. RISC-V reports its page fault as a store/AMO fault: 15, not 13.

What the Supplied Kernel Does on a Page Fault

usertrap() in kernel/trap.c handles scause 8 as a system call and checks for a device interrupt. Anything else falls into the last branch. That branch prints scause, sepc and stval and calls setkilled(p). A few lines later, if (killed(p)) exit(-1); ends the process. Only that process dies. The kernel carries on, the shell’s wait() returns, and you get a prompt back.

The manual asks you to add a short diagnostic in that path. It must name load (13) and store (15) page faults and print r_stval(). Keep the kill for now.

The fault Program

user/fault.c calls sbrk(0) to learn the current break without growing anything. It targets PGROUNDUP(break), then reads (fault read) or writes (fault write) one byte there.

  • Why round up: memory is mapped in whole pages. If the break is in the middle of a page, the bytes just past it are still in that mapped page and do not fault. The next page boundary is the first byte that is surely unmapped. If the break is already on a boundary, the break itself is that byte.
  • Why volatile: a read whose result is thrown away looks useless to the compiler, which could delete it. volatile keeps the load or store in the machine code.
Run scause stval
fault read 13 (load) the printed target
fault write 15 (store) the printed target

The program prints its target before the access, so you can match it with stval in the kernel message. Its last line, “ERROR: access returned”, must never print: the process dies at the access.

The Trampoline Mechanism

Switching to kernel mode does not change the satp page table register. The CPU must initially execute kernel entry code using the user process’s page table.

  1. stvec points to uservec in the Trampoline page (kernel/trampoline.S).
  2. The Trampoline is mapped at the identical virtual address (TRAMPOLINE = 2^{38} - PGSIZE = MAXVA - PGSIZE) in both user and kernel page tables.
  3. uservec saves all 31 mutable general-purpose registers (x1–x31x1\text{--}x31; x0x0 is hardwired to 0) into the process’s TRAPFRAME page.
  4. uservec switches satp to the kernel root page table and jumps to usertrap(). Because TRAMPOLINE shares the exact same virtual address in both tables, instruction execution continues seamlessly across the address space swap.

Why TRAPFRAME, not the kernel stack: until satp changes, only pages in the user table are reachable. TRAPFRAME is one of them; the kernel stack is not.

Frames behind the two pages: the trampoline is the same code for everyone, so one frame is mapped in every process. Each process saves its own registers, so each process has its own trapframe frame.

Back out: usertrapret() points future traps at uservec, stores the kernel values uservec needs next time into the trapframe, and sets sepc to p->trapframe->epc. It then calls userret on the trampoline. userret switches satp back to the user table, restores the registers from TRAPFRAME, and runs sret to return to user mode at sepc.

6. Part 4: Implementing Lazy Heap Allocation

In lazy allocation, sbrk() acts as a virtual reservation: it advances p->sz without allocating physical RAM frames. When the process subsequently attempts to load or store to an unmapped page, the MMU triggers a page fault (cause 13 or 15), allowing the kernel to allocate and map the frame on demand.

Step 1: Update sys_sbrk() (Kernel Address Reservation)

In kernel/sysproc.c, modify sys_sbrk() to avoid calling growproc() on positive allocations:

uint64 sys_sbrk(void) {
    uint64 addr;
    int n;
    struct proc *p = myproc();

    argint(0, &n);
    addr = p->sz;

    if (n > 0) {
        uint64 newsz = addr + n;
        // Check for integer overflow and prevent expanding into trap pages
        if (newsz < addr || newsz >= TRAPFRAME)
            return -1;
        p->sz = newsz; // Lazily update size only (no uvmalloc)
    } else if (n < 0) {
        if (growproc(n) < 0) // Immediate deallocation on heap shrink
            return -1;
    }
    return addr; // Returns original program break
}
  • Keep sbrk(0), the old-break return value and shrinking exactly as they were.
  • Why the new >= TRAPFRAME check: eager sbrk failed naturally when uvmalloc could not allocate or map. Lazy sbrk only raises a number, so nothing else stops a huge request pushing p->sz over TRAPFRAME and TRAMPOLINE (defined in kernel/memlayout.h). newsz < addr catches a sum that wrapped round.
  • Do not create empty PTEs for the new range. A missing table and an invalid entry both fault on access, and mappages builds any missing tables when the page is finally mapped.

Step 2: Handle Page Faults in usertrap()

In kernel/trap.c, intercept page fault causes 13 and 15, routing them to lazy_alloc():

// Inside usertrap() in kernel/trap.c:
} else if (r_scause() == 13 || r_scause() == 15) {
    uint64 fault_va = r_stval();
    if (lazy_alloc(p, fault_va) < 0) {
        setkilled(p); // Segmentation fault: illegal access, terminate process
    }
}

Implement lazy_alloc():

int lazy_alloc(struct proc *p, uint64 va) {
    // 1. Boundary check: Address must strictly reside within allocated heap
    if (va >= p->sz)
        return -1;

    uint64 a = PGROUNDDOWN(va);

    // 2. Permission check: If page is already mapped, fault was a permission violation
    pte_t *pte = walk(p->pagetable, a, 0);
    if (pte != 0 && (*pte & PTE_V))
        return -1;

    // 3. Allocate, clear, and map physical frame
    char *mem = kalloc();
    if (mem == 0)
        return -1; // Out of physical RAM

    memset(mem, 0, PGSIZE);

    if (mappages(p->pagetable, a, PGSIZE, (uint64)mem, PTE_R | PTE_W | PTE_U) != 0) {
        kfree(mem); // Prevent memory leak on mapping failure
        return -1;
    }

    // 4. Do NOT modify p->trapframe->epc!
    // Returning allows the CPU to re-execute the exact instruction that faulted.
    return 0;
}

How the handler tells a first touch from a real error:

Fault on… Below p->sz? Leaf entry Action
Untouched heap page yes missing or not valid allocate and map
Guard page yes valid, no PTE_U kill
Write to code yes valid, no PTE_W kill
Above the break (the fault program) no – kill

va < p->sz alone is not enough, because the guard page and the code are also below p->sz. An untouched heap page is the only case with no valid leaf entry. A page that is valid but faulted anyway is a protection violation.

  • Use stval, not sepc. sepc is the instruction’s address.
  • Check the range before rounding. See Section 7, point 2.
  • Check the range before walk. walk panics for va >= MAXVA. Testing va < p->sz first keeps walk safe, because p->sz is below the trap pages.
  • Clean up on failure. If mappages fails after kalloc succeeded, kfree the frame before killing, or it is lost. uvmalloc uses the same pattern.
  • Without the valid-PTE check, a stack overflow into the guard page reaches mappages on a valid entry. mappages panics with “remap”, which crashes the whole kernel instead of killing one process.
  • “Kill” means setkilled(p). The existing if (killed(p)) exit(-1); below finishes the job.

Step 3: Prevent Panics in uvmunmap()

Because lazy allocation leaves holes in the address space, process exit (uvmfree) and negative sbrk() calls will encounter unmapped virtual pages. In kernel/vm.c, replace the panics with continue:

void uvmunmap(pagetable_t pagetable, uint64 va, uint64 npages, int do_free) {
    uint64 a;
    pte_t *pte;

    for (a = va; a < va + npages * PGSIZE; a += PGSIZE) {
        if ((pte = walk(pagetable, a, 0)) == 0)
            continue; // Skip missing intermediate page table
        if ((*pte & PTE_V) == 0)
            continue; // Skip unmapped lazy page
        if (PTE_FLAGS(*pte) == PTE_V)
            panic("uvmunmap: not a leaf");
        if (do_free) {
            uint64 pa = PTE2PA(*pte);
            kfree((void*)pa);
        }
        *pte = 0;
    }
}

Who calls uvmunmap:

Function Used by Without the fix
uvmdealloc(pt, old, new) negative sbrk panics on the untouched pages that fall off the end
uvmfree(pt, sz) process exit: unmaps 0–sz, then frees the tables the first exit after a partly touched heap panics “uvmunmap: not mapped”

Keep the “not a leaf” panic. A valid entry with only PTE_V set points to another page table, not a data frame. Freeing it as data would be a real bug.

Out of scope, but know why: fork() copies memory with uvmcopy(), which still panics on a missing page. copyin / copyout (used when a system call reads or writes a user buffer) go through walkaddr and fail on an untouched page instead of faulting it in: no user-mode fault happens, so usertrap never runs. Example: p = sbrk(4096); read(fd, p, 100); returns -1. lazytest exercises none of these, so a pass says nothing about them.

7. Lab Checkpoint & Quiz Key Points

  1. Why Instruction Restart Works Without Modifying epc:
    • In system calls (scause == 8), epc is incremented by 4 (epc += 4, the size of a standard 32-bit/4-byte RISC-V instruction) because ecall completed and execution must advance to the next instruction.
    • In page faults, the load/store instruction was halted mid-cycle without completing. Leaving epc untouched causes the hardware to re-execute the identical instruction upon returning to user space (sret). Because the handler has now installed a valid PTE, the re-executed instruction succeeds.
  2. Why Check va < p->sz Before PGROUNDDOWN(va):
    • If p->sz is not page-aligned (e.g. 0x4050), a bad access to 0x4060 would be rounded down to 0x4000. If evaluated after rounding, 0x4000 < p->sz would erroneously treat an illegal out-of-bounds access as a legitimate lazy allocation.
  3. Eager vs. Lazy Memory Verification:
    • Under eager allocation, sbrk(30 pages) increases both countvp() and countpp() by 30 immediately.
    • Under lazy allocation, sbrk(30 pages) increases countvp() by 30 while countpp() remains unchanged (+0). As memory pages are sequentially written, countpp() increments page by page upon each fault.
