Synchronization and semaphores

How xv6 stops two CPUs from entering the same critical section, how a process waits for a condition without wasting CPU time, how you build a blocking semaphore on top of both, and how you use it to fix a lost update and coordinate a bounded buffer. Checked against the course's lab3 branch.

Part 1.1

Spinlocks: why acquiring must be one atomic step

This lab runs with CPUS=3, so three processes can be running at literally the same instant. If two of them touch the same kernel data, you need a way to say "only one CPU in here at a time". That's a lock.

A spinlock is just a word in memory, locked, in struct spinlock (kernel/spinlock.h). 0 means free, 1 means held. The obvious way to take it is "check it's 0, then set it to 1". That doesn't work.

The broken version: check, then set

Two CPUs both want an unlocked lock:

StepCPU 0CPU 1locked
1reads locked → 0, "it's free"0
2reads locked → 0, "it's free"0
3sets locked = 1, enters1
4sets locked = 1, enters1

Both CPUs saw 0 before either wrote 1, so both believe they hold the lock. The gap between the check and the set is the whole problem.

The fix: test-and-set

acquire() uses __sync_lock_test_and_set(&lk->locked, 1), which compiles to a single RISC-V instruction, amoswap. It writes 1 and returns the old value in one indivisible step. No other CPU can sneak in between the read and the write.

while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
  ;   // old value was 1: someone holds it, try again (spin)

If two CPUs swap at the same moment, the hardware orders them. The first gets back 0 and owns the lock. The second gets back the 1 the first one just wrote, so it keeps spinning.

Why disabling interrupts isn't enough

acquire() starts with push_off(), which turns off interrupts. It's tempting to think that makes the critical section safe on its own. It doesn't, because interrupts are per CPU: turning them off only stops this CPU from being interrupted. The other two CPUs keep running, and nothing stops them from reaching the same data.

So what are disabled interrupts for? If an interrupt handler on this CPU tried to take a lock this CPU already holds, it would spin forever, because the holder can't run until the handler returns. Keeping interrupts off while a lock is held rules that deadlock out. The atomic swap is what keeps other CPUs out.

  • Atomic swap stops other CPUs entering.
  • Interrupts off stops this CPU deadlocking against its own interrupt handler.
  • holding(lk) makes acquire() panic if this CPU tries to take a lock it already holds.
Trap"Interrupts are disabled, so no one else can enter" is only true with one CPU. On a multiprocessor it's the atomic instruction that gives mutual exclusion.
Part 1.2

Waiting for a condition: sleep() and wakeup()

A spinlock is fine for a wait of a few instructions. But sometimes a process has to wait for something that may take ages: a semaphore to become non-zero, a child to exit. Spinning that whole time burns a CPU doing nothing. It's better to go to sleep and be woken when the condition changes.

The kernel gives you two functions in kernel/proc.c:

sleep(chan, lk)
Mark me SLEEPING on channel chan and give up the CPUNot the same as the user sleep(ticks) system call. This one waits for a condition, not a time.
wakeup(chan)
Make every process sleeping on chan RUNNABLEIt skips the process calling it.
chan
Any address both sides agree onJust a label for "who to wake". It isn't a queue and it doesn't hold the data.

The danger: a lost wakeup

Waiting means two steps: check the condition, then go to sleep. Picture a naive version where the waiter checks, lets go of the lock protecting the data, and only then marks itself SLEEPING:

StepWaiterSignaller
1checks: value is 0, must wait
2releases the lock
3takes the lock, value = 1, calls wakeup
4wakeup finds nobody SLEEPING yet, does nothing
5marks itself SLEEPING, sleeps forever

The value is 1, but the waiter sleeps forever because its wakeup came in the gap between its check and its sleep.

How xv6 closes the gap: two locks

lk
The condition lockProtects the shared data being checked (for your semaphore, its value). The caller holds it while checking.
p->lock
The process lockProtects this process's state and sleep channel. wakeup() must take it to look at the process.
sleep(chan, lk):
  acquire(&p->lock);   // 1. grab my process lock FIRST
  release(lk);         // 2. only now let go of the condition lock
  p->chan = chan;
  p->state = SLEEPING; // 3. mark myself asleep
  sched();             // 4. switch away (the scheduler releases p->lock)
  p->chan = 0;         // ...woken up and picked again
  release(&p->lock);
  acquire(lk);         // 5. take the condition lock back before returning

The signaller holds lk while it changes the data and calls wakeup(). To check whether the waiter is asleep, wakeup() must take the waiter's p->lock. The waiter took that lock before releasing lk and keeps it until it's SLEEPING and has switched away. So at every moment the waiter is protected by at least one of the two locks. There's no gap to lose the wakeup in.

Why the waiter must re-check in a loop

wakeup() only makes sleepers RUNNABLE. It doesn't run them straight away, and it doesn't reserve anything for them. Two things can happen before a woken process actually runs:

  • wakeup() wakes every process on that channel. If one unit became available and three were waiting, only one can have it.
  • Another process can grab the resource in the time between "made RUNNABLE" and "actually running".

So the waiter wraps its check in a while, not an if: wake up, take lk back, look again, and sleep again if it still can't proceed.

TrapBeing woken doesn't mean the condition is true. It only means "something changed, go and look".
Part 1.3

Spinning vs sleeping

Sleeping isn't free. It costs a trip through sched() into the scheduler, picking another process, and later a wakeup plus another switch back in. That overhead is a fixed cost, on the order of hundreds to thousands of cycles. Spinning costs exactly as long as the wait.

WaitCheaperWhy
10 cyclesSpinThe wait is over long before a context switch could even finish
10,000 cyclesSleepSpinning wastes 10,000 cycles that another process could use; the switch costs far less

The manual asks you to state your assumptions. Here are the ones that matter:

  • Spinning only makes sense if the lock holder is running on another CPU and will release soon. With one CPU, the holder can't run while you spin, so you'd spin for your entire time slice.
  • These numbers are illustrations, not measured xv6 thresholds. The real break-even depends on how expensive a switch is on that machine.
Part 2

Completing the blocking semaphore

A semaphore combines the two tools from Part 1: a short spinlock to update its count safely, and sleep()/wakeup() to wait when the count is zero.

Three names that look alike

NameWhereWhat it does
seminit()kernel, at bootSets up the whole semaphores[32] array: marks every slot unused and initialises each slot's lock
sem_init(value)user system callWhat a user program calls to get a semaphore
sem_alloc(value)kernelWhat sys_sem_init calls: finds a free slot, sets its value, returns its index as the semid, or -1 if all 32 are taken

Each slot is a struct semaphore holding a lock, a value and an in_use flag. A semid is just the slot's index in the kernel array.

This semaphore never goes negative

Lecture versionThis lab
WaitDecrement first; block if it went below 0Sleep while the value is 0; decrement once it's positive
Value rangeCan be negativeAlways 0 or more
Negative value means|S| processes are blockedNever happens
TrapThe manual says not to mix the two. In this lab, a value of 0 can mean "nobody waiting" or "five processes waiting". The count doesn't tell you how many are blocked.

What each operation has to do

The TODOs ask you to uncomment struct semaphore *sem = &semaphores[semid]; and fill in the rest. In outline:

sem_wait:
  acquire(&sem->lock)
  while value == 0:
      sleep(sem, &sem->lock)    // channel = this semaphore's address
  value--
  release(&sem->lock)

sem_signal:
  acquire(&sem->lock)
  value++
  wakeup(sem)                  // same channel as the waiters
  release(&sem->lock)

sem_getvalue:
  acquire, copy value, release, return the copy
  • Lock: each semaphore's own sem->lock. It's the condition lock from Part 1: it protects value.
  • Channel: the semaphore's own address. Waiters on semaphore 3 aren't woken by a signal on semaphore 5.
  • Why sleep gets the lock: if the waiter slept while holding sem->lock, the signaller could never take it to increment the value, and everyone would be stuck. sleep() releases it safely and takes it back before returning.
  • Why while: wakeup() wakes every waiter on the channel, but one signal adds only 1. Whoever runs first takes it. The rest see 0 again and go back to sleep.
  • Why getvalue locks: so it never reads value halfway through someone else's update.

What sem_basic does and doesn't check

The basic test does sem_init(1), then wait, then signal, and checks the value reads 1 → 0 → 1. It prints [sem_basic] PASS: Basic semaphore operations work.

It never waits on a value of 0, so it never tests blocking, sleeping, waking or the re-check loop. You have to explain those from your code.

When it's safe to free

sem_free() just marks the slot unused. It doesn't wake anyone sleeping on it and doesn't wait for users to finish. Freeing too early means a sleeper may never be woken, or the slot gets handed to a new sem_init while an old process still uses it. So: allocate before fork(), free only after every user has finished, which in the tests means after the parent's wait().

Practice
Three processes sleep in sem_wait on the same semaphore, whose value is 0. One process calls sem_signal once. What happens?
  1. Exactly one sleeper is made RUNNABLE, and it decrements the value
  2. All three become RUNNABLE; one decrements the value and the other two go back to sleep
  3. All three decrement the value, which ends at -2
  4. No sleeper wakes until the value reaches 3

wakeup() wakes everyone on the channel. The while loop is what makes the other two sleep again, and the value never drops below 0 in this design.

Part 3

Protecting the shared counter

Counter 0 lives in kernel memory (ucnt[] in kernel/ucnt.c). The test forks once, and parent and child each add 1 to it N = 1,000 times, so the total should be 2,000. Each increment in do_work() is two separate system calls:

int val = ucnt_get(0);   // read
ucnt_set(0, val + 1);    // write

How an update gets lost

StepParentChildCounter
1ucnt_get → 55
2ucnt_get → 55
3ucnt_set(6)6
4ucnt_set(6)6

Two increments happened, but the counter only went up by 1. Each call on its own is fine. The damage happens in the gap between the read and the write, when the other process reads the same old value.

TrapEntering the kernel doesn't make the pair atomic. Two system calls are two separate trips into the kernel, and the other process can run in between. And one run that happens to print 2,000 doesn't prove there's no race; the bad timing just didn't happen that time.

The fix

  • Create one semaphore with value 1 in race_test(), before fork(). 1 means one process may be inside at a time, which is mutual exclusion.
  • Wrap the whole read-then-write in wait and signal, so the get and the set happen together, with no other increment in between.
  • Check the results: sem_init can return -1.
  • Parent: wait(0), then check, then free. The child might still be incrementing until it exits, and the semaphore can't be freed while the child might still use it.

Wrapping each call on its own (wait, get, signal, then wait, set, signal) doesn't help: the gap between get and set is still unprotected, and that gap is exactly where the other process gets in.

Why the child's semid still works

fork() copies user memory, so the child gets its own copy of the variable semid. But semid is just a number: an index into semaphores[] in kernel memory. Kernel memory isn't copied by fork. Parent and child pass the same number, so they reach the same kernel semaphore. The counter works the same way, which is why both processes see one shared counter.

Practice
A student places sem_wait before ucnt_get and sem_signal right after it, and a second wait/signal pair around ucnt_set. The final count is sometimes below 2,000. Why?
  1. The semaphore must be initialised to 2 for two processes
  2. sem_signal wakes the other process too early
  3. The gap between the get and the set is still unprotected
  4. The child has a different copy of the semaphore
Part 4

Producers and a consumer

The kernel buffer ubuf has UBUF_SIZE = 16 slots arranged in a circle. Two child processes produce, each writing the 48 characters of msg. The parent consumes, making 96 reads. The buffer functions check nothing: a write into a full buffer overwrites data, and a read from an empty one returns rubbish. So you need three separate guarantees:

  • A producer waits when there's no empty slot.
  • The consumer waits when there's no filled slot.
  • Only one process touches the buffer's indices at a time.

Three semaphores and their starting values

At the start the buffer is empty, so:

SemaphoreCountsStarts at
emptyfree slots a producer may fill16 (UBUF_SIZE)
fullfilled slots the consumer may read0
mutexwho may touch the buffer1

These go in struct buf_sem and are created in producer_consumer() before the fork loop, so both children inherit the same ids.

The order of calls

producer, for each character:      consumer, for each read:
  wait(empty)                        wait(full)
  wait(mutex)                        wait(mutex)
  ubuf_write(c)                      ubuf_read()
  signal(mutex)                      signal(mutex)
  signal(full)                       signal(empty)

The pattern: wait for a slot first, then take the mutex, do the operation, release the mutex, then announce the slot you've created for the other side.

Why the order of the two waits matters

Swap them in the consumer so it takes the mutex first, and start with an empty buffer:

  1. The consumer takes the mutex, then waits on full. It's 0, so the consumer sleeps while still holding the mutex.
  2. A producer gets past wait(empty), then waits on mutex. The consumer holds it, so the producer sleeps.
  3. The consumer needs a producer to signal full. The producer needs the consumer to release the mutex. Neither can move: deadlock.

The rule: never sleep waiting for space or data while holding the mutex.

Why counting slots isn't enough

With 16 empty slots, both producers get past wait(empty) at once. Without the mutex, here's what the yield() inside ubuf_write() lets happen:

StepProducer AProducer B
1writes into data[tail], then yields
2writes into the same data[tail], overwriting A
3advances tail
4advances tail again, leaving a slot that was never written

The empty/full counts only say how many slots are available. They don't stop two processes using the same index at once. That's the mutex's job. The yield() calls exist to force this interleaving to show up if your mutual exclusion is wrong.

Cleanup and what the test proves

The parent consumes all 96 characters, calls wait(0) twice to reap both producers, then frees all three semaphores. Success prints [producer_consumer] PASS: message delivered.

The consumer only checks that each byte it reads is one of the characters in msg (c, a, f or e). It doesn't compare the stream to an expected order. A lost byte replaced by an old one, a duplicate, or a reordering could all still pass. So the pass result only supports your argument about counts, mutual exclusion and order. It doesn't prove correctness on its own.

Practice

  3. The consumer reads rubbish from an empty slot
  4. The producers overwrite each other's characters

Before the quiz

Self-check

Tap a question to reveal the answer.

01Why can't a spinlock use "read locked, then write 1"?+

Two CPUs can both read 0 before either writes 1, so both enter. Test-and-set (amoswap) reads and writes in one indivisible step, so only one CPU can see 0.

02Why doesn't disabling interrupts keep other CPUs out?+

Interrupts are per CPU. Disabling them only stops this CPU being interrupted, which prevents a deadlock with its own interrupt handlers. Other CPUs are kept out by the atomic swap.

03In sleep(chan, lk), what are lk and p->lock for?+

lk is the condition lock, protecting the shared data being checked. p->lock protects the process's state and channel. sleep takes p->lock before releasing lk, so the waiter is always covered by one of them.

04How does that ordering prevent a lost wakeup?+

wakeup must take the waiter's p->lock to check it. The waiter holds that lock from before it releases lk until it is SLEEPING and switched away, so wakeup can never see it "about to sleep".

05Does wakeup() run the woken process?+

No. It only makes matching sleepers RUNNABLE. They run when the scheduler picks them, and nothing is reserved for them.

06Why must a woken process re-check its condition?+

wakeup wakes every sleeper on the channel, and another process may take the resource before it runs. So it re-checks in a while loop and sleeps again if needed.

07Spin or sleep for 10 cycles? For 10,000?+

Spin for 10, because a context switch costs far more. Sleep for 10,000, because spinning wastes the CPU. This assumes the holder runs on another CPU; the numbers are illustrations, not xv6 thresholds.

08seminit vs sem_init vs sem_alloc?+

seminit: kernel, at boot, sets up the whole array. sem_init: the user system call. sem_alloc: the kernel function sem_init's handler calls to grab a free slot.

09Which lock and channel do sem_wait and sem_signal use?+

The semaphore's own sem->lock, and the semaphore's own address as the channel. Both must use the same channel.

10How is this lab's semaphore different from the lecture's?+

It never goes negative. Wait sleeps while the value is 0 and decrements only when positive, so the value doesn't count blocked processes.

11What does sem_basic leave untested?+

Blocking. It never waits on 0, so sleeping, waking and the re-check loop aren't exercised.

12When is it safe to free a semaphore here?+

Only after every user has finished, i.e. after the parent's wait(). sem_free doesn't wake sleepers or wait for users; it just marks the slot unused.

13Why is protecting ucnt_get and ucnt_set separately not enough?+

The gap between them is still open. The other process can read the same old value there, and one update is lost.

14Why do parent and child share one semaphore after fork?+

semid is just an index into the kernel's semaphores[] array. fork copies the number, not kernel memory, so both reach the same kernel semaphore.

15Initial values of empty, full and mutex?+

empty = 16 (UBUF_SIZE), full = 0, mutex = 1, because the buffer starts empty.

16Why wait on empty/full before mutex?+

Sleeping on empty/full while holding the mutex stops the other side from ever getting the mutex to change the count. That's a deadlock.

17Why isn't counting slots enough without a mutex?+

Counts limit how many slots are used, not which index. Two producers can write the same data[tail] before either advances it; the yield() makes this show up.

18What does the producer_consumer pass prove?+

Only that every byte read was one of c, a, f or e. It doesn't rule out loss, duplication or reordering.
