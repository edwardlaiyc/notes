Virtual memory and lazy allocation

How xv6 turns a process's addresses into real memory, how you count what a process has reserved versus what it actually holds, what happens when a process touches memory it shouldn't, and how to hand out heap memory only when it's first used. Checked against the course's lab4 branch.

Part 1.1

Page tables: from a process's address to real memory

Every process believes its memory starts at address 0 and runs up to some size. But there is only one RAM, shared by every process and the kernel. So the addresses a program uses can't be the real RAM addresses. Something has to translate.

  • A virtual address is what the program uses. Each process has its own set.
  • A physical address is a real location in RAM.
  • Memory is handled in 4,096-byte blocks. A block of virtual addresses is a page. A block of RAM is a frame. (xv6's comments call frames "physical pages", same thing.)
  • A page table is the per-process lookup that says "virtual page X lives in frame Y, and these accesses are allowed". The CPU hardware reads it on every memory access.

Why three levels instead of one big table

The obvious design is one flat array with an entry per virtual page. xv6's address space has 227 possible pages, and each entry is 8 bytes, so a flat table would be 1 GiB per process, even for a program using a few pages. That's hopeless.

The fix is a tree. The top table splits the address space into big chunks. A chunk nobody uses has no table below it at all. Only the parts a process actually uses get filled in. RISC-V's scheme for this is called Sv39: 39-bit virtual addresses, three levels of tables.

Working out the bit fields

Two sizes give you everything:

  1. A page is 4,096 = 212 bytes, so the offset (which byte inside the page) needs 12 bits: bits 11–0.
  2. Each page table is itself one page. 4,096 bytes ÷ 8 bytes per entry = 512 = 29 entries, so each index needs 9 bits.
  3. Stack three indexes above the offset, starting from level 0 just above bit 11.
FieldBitsRole
Level-2 index38–30Pick an entry in the root table
Level-1 index29–21Pick an entry in a level-1 table
Level-0 index20–12Pick the entry that maps this page to a frame
Page offset11–0Pick the byte inside that frame

9 + 9 + 9 + 12 = 39 bits, hence Sv39. xv6 only uses the lower half of that range: MAXVA in kernel/riscv.h is 238, so every address it uses has bits 63–38 equal to zero. The macro PX(level, va) pulls out one index: shift right by 12 + 9 × level, then keep the low 9 bits.

What's in a page-table entry (PTE)

Each 8-byte entry holds a 44-bit physical page number (PPN: the frame's address with its low 12 bits dropped, since frames always start on a 4,096 boundary) plus flag bits:

PTE_V
ValidIf this is 0, the entry means nothing and any access through it faults.
PTE_R / W / X
Read, write, execute allowed
PTE_U
User mode may use itWithout U, only the kernel can touch the page. This is how the stack guard page is blocked.

The same entry format means different things at different levels:

  • A valid level-2 or level-1 entry points to the next table down. It has V set but none of R, W, X.
  • A valid level-0 entry (a "leaf") points to the frame that holds the actual data, with R/W/X/U saying what's allowed.

Three fields of struct proc you'll use

p->sz
Process size in bytesThe user address range is 0 up to (not including) p->sz. Also called the program break.
p->pagetable
This process's root page table
p->trapframe
Where the user's registers are saved during a trap (Part 3)

walk() and walkaddr()

walk(pagetable, va, alloc) in kernel/vm.c does the lookup in software, the same way the hardware does:

for level = 2, then 1:
  pte = &pagetable[PX(level, va)]
  if pte is valid:  pagetable = the table it points to
  else if alloc:    kalloc() a fresh page, zero it,
                    install it here with PTE_V only
  else:             return 0              // no table: nothing mapped
return &pagetable[PX(0, va)]              // pointer to the L0 entry
  • It returns a pointer to the level-0 entry, not a frame address. That entry may still be invalid. You check PTE_V yourself.
  • With alloc = 1, the only thing it creates is missing page-table pages. It never allocates a frame for data.
  • It panics if va >= MAXVA.

walkaddr(pagetable, va) calls walk with alloc = 0 and returns the frame's physical address, but only if the entry is valid and has PTE_U. The kernel uses it when handling an address a user passed in, so a user can't trick the kernel into reading a page the user isn't allowed to touch.

Trap"walk() allocates memory" is half true. It can allocate frames for page tables. Allocating and mapping a data frame is a separate job (kalloc + mappages).
Part 1.2

Growing the heap: sbrk() and eager allocation

A process's heap grows with the system call sbrk(n): "move the end of my memory (the program break, p->sz) by n bytes". Here's the path a request takes:

  1. malloc runs out of free space and calls morecore() in user/umalloc.c, which asks for at least 4,096 header units with sbrk().
  2. The user stub (generated from user/usys.pl) puts the syscall number in a register and executes ecall, trapping into the kernel.
  3. sys_sbrk() in kernel/sysproc.c saves the old size, addr = p->sz, calls growproc(n), and returns addr.
  4. growproc() in kernel/proc.c: if n > 0 it calls uvmalloc(); if n < 0 it calls uvmdealloc(); if n = 0 it changes nothing. Then it sets p->sz.
  5. uvmalloc() in kernel/vm.c does the real work, one page at a time.
for each page from PGROUNDUP(oldsz) up to newsz:
  mem = kalloc()                  // take a free frame
  memset(mem, 0, PGSIZE)          // clear it
  mappages(pagetable, a, PGSIZE, mem, PTE_R|PTE_U|PTE_W)
  // on any failure: kfree what was just taken, undo earlier pages, return 0
kalloc()
Take one free 4,096-byte frame off the kernel's free listIn kernel/kalloc.c. Returns 0 if RAM is exhausted. It fills the frame with junk bytes, which is why the caller must clear it.
kfree(pa)
Put a frame back on the free list
mappages(pt, va, size, pa, perm)
Install leaf entries so va maps to paUses walk(…, 1) to create any missing tables. Panics if an entry is already valid ("remap"). Returns -1 if a table can't be allocated.

Why clear the frame? A recycled frame may still hold another process's data. Handing it over uncleared would leak that data.

This is eager allocation: the frames are handed out the moment the memory is asked for, whether or not the program ever touches them.

What sbrk returns, and why the old break

CallEffectReturns
sbrk(n), n > 0grows the heap by n bytesold break

Returning the old break hands the caller the start of the memory it just got: the new region runs from old break to old break + n. That's exactly the pointer morecore() turns into a free block.

Practice
p->sz is 0x5000. A process calls sbrk(8192). What does the call return, and what is p->sz afterwards?

  2. Returns 0x5000; p->sz = 0x7000

8,192 = 0x2000. sbrk returns the old break, the start of the new region. On the supplied eager kernel, both pages are allocated immediately.

Part 2

Counting virtual pages and physical frames

To tell eager and lazy allocation apart, you need two numbers: how much address space a process has reserved, and how much RAM is actually backing it. You'll add two system calls for these.

countvp()
Virtual pages in the range 0 to p->szA partly used last page counts as one. Includes the guard page.
countpp()
Frames backing that same range through valid level-0 entriesIncludes the guard page's frame, even though user access to it is off.

Both work on the calling process, which you get with myproc().

countvp: just arithmetic

The range is 0 up to p->sz, and any partly used page still counts. That's PGROUNDUP(p->sz) / PGSIZE. PGROUNDUP (in kernel/riscv.h) rounds an address up to the next multiple of 4,096, or leaves it alone if it's already on one.

countpp: walk every page and look

count = 0
for va = 0; va < p->sz; va += PGSIZE:
  pte = walk(p->pagetable, va, 0)       // alloc = 0: look, never create
  if pte != 0 and (*pte & PTE_V):
    count++
  • alloc must be 0. A counting call must not change the page table it's measuring.
  • Use walk, not walkaddr. walkaddr returns 0 for any entry without PTE_U, so it would skip the guard page. The manual says the guard page's frame counts.

Why the guard page has a frame but no PTE_U

In exec(), xv6 allocates two pages above the program with uvmalloc, then calls uvmclear() on the lower one. uvmclear clears that entry's PTE_U bit. So the page is still valid and still has a frame, but any user access to it faults. If the stack overflows downward, it hits this page and the process is killed instead of silently overwriting its own data.

What is not counted

  • Frames holding the page tables themselves. They're reached through non-leaf entries, not through a user address.
  • The process's kernel stack, which lives in the kernel's page table.
  • TRAMPOLINE and TRAPFRAME, which are far above p->sz, so the loop never reaches them.

Wiring the two system calls

Same steps as Lab 1. This branch's syscall numbers end at 21 (SYS_close), so the new ones are 22 and 23.

  1. kernel/syscall.h: #define SYS_countvp 22 and SYS_countpp 23.
  2. kernel/syscall.c: an extern uint64 sys_countvp(void); declaration for each, and an entry in the syscalls[] table.
  3. kernel/sysproc.c: the two handlers. walk is already declared in kernel/defs.h, so you can call it there. If you put the counting code in vm.c instead, declare your function in defs.h.
  4. user/usys.pl: entry("countvp"); and entry("countpp");. usys.S is generated from this; don't edit it.
  5. user/user.h already declares both. Delete the two placeholder functions at the top of user/lazytest.c so its calls reach your system calls.

Part 3.1–3.2

Page faults: what happens on a bad access

A trap is anything that forces the CPU out of the user program and into the kernel. There are three kinds: a system call (the program asked), a device interrupt (hardware needs attention), and an exception (the instruction itself went wrong). A page fault is an exception: the hardware couldn't translate the address, or the entry doesn't allow that kind of access.

On a trap, the CPU fills three registers that usertrap() in kernel/trap.c can read with functions from kernel/riscv.h:

scause
Why the trap happened8 = system call. 12 = instruction-fetch page fault, 13 = load page fault, 15 = store/AMO page fault (AMO: atomic memory operation, counted as a write).
sepc
Address of the instruction that trappedWhere the program counter was.
stval
For a page fault, the virtual address it tried to accessThis is the one you care about for memory.
Trapsepc is where the code is; stval is what memory it touched. For a fault on a heap byte, sepc is a small address in the program's code and stval is the heap address. Don't mix them up.

What the supplied kernel does

usertrap() handles scause 8 as a system call and checks for a device interrupt. Anything else falls into the last branch, which prints scause, sepc and stval and calls setkilled(p). A few lines later, if(killed(p)) exit(-1); ends the process. Only that one process dies. The kernel carries on, the shell's wait() returns, and you get a prompt back.

The manual asks you to add a short diagnostic in that path that names load (13) and store (15) page faults and prints r_stval(). Keep the kill for now.

The fault program

user/fault.c calls sbrk(0) to learn the current break without growing anything, then picks PGROUNDUP(break) as its target.

  • Why round up? Memory is mapped in whole pages. If the break is in the middle of a page, the bytes just past it are still inside that mapped page and wouldn't fault. The next page boundary is the first byte that's definitely unmapped. If the break is already on a boundary, it is itself that first unmapped byte.
  • Why volatile? A read whose result is thrown away looks useless to the compiler, which could delete it. volatile forces the load or store to stay in the machine code.
Runscausestval
fault read13 (load)the printed target
fault write15 (store)the printed target

The program prints its target before the access, so you can match it with stval in the kernel's message. The final "ERROR: access returned" line should never print, because the process is killed at the access itself.

Part 3.3

The trampoline: switching page tables mid-flight

The user program runs with its own page table. The kernel runs with the kernel's page table. The register satp says which table the hardware is using. So entering the kernel means changing satp. That raises a problem: the very next instruction is fetched through the new table. If the code doing the switch isn't at the same virtual address in both tables, the CPU fetches garbage.

The fix is the trampoline: one page of assembly (kernel/trampoline.S) mapped at the same address, TRAMPOLINE (the top page, MAXVA − PGSIZE), in every user page table and in the kernel's. Code running there survives the switch because its address means the same thing either side.

Into the kernel: uservec

  1. The trap jumps to uservec (on the trampoline page), still using the user page table.
  2. It saves all the user's registers into the TRAPFRAME page. That page is mapped in the user table, just below the trampoline, so it can be reached before the switch. (sscratch briefly holds a0 to free a register.)
  3. It loads the kernel stack pointer, CPU id, address of usertrap and the kernel's page table from the trapframe.
  4. It writes the kernel table into satp (with sfence.vma to flush stale translations), then jumps to usertrap().

Back out: usertrapret and userret

  1. usertrapret() points future traps at uservec, stores the kernel values uservec will need next time into the trapframe, and sets sepc to p->trapframe->epc, the user instruction to resume at.
  2. It calls userret on the trampoline, passing the user page table.
  3. userret switches satp back to the user table, restores registers from TRAPFRAME, and runs sret to drop to user mode at sepc.

For a system call, usertrap() adds 4 to epc so the program resumes after the ecall. Remember that for Part 4.

  3. The kernel stack belongs to another process
  4. TRAPFRAME is faster memory
Part 4.1–4.2

Lazy allocation: frames only on first touch

Programs often reserve far more heap than they use. With eager allocation, every reserved page costs a frame immediately. The fix is lazy allocation: sbrk() only reserves the address range, and a frame is allocated the first time each page is actually touched. Pages never touched cost no data frame at all.

The trick is that the first touch of a reserved-but-unmapped page causes a page fault. Instead of killing the process, the kernel recognises "this is a page I promised but haven't delivered", delivers it, and lets the instruction try again.

4.1 Reserve without allocating

Change positive sbrk(n) so it only raises p->sz:

sys_sbrk(n):
  addr = p->sz
  if n > 0:
    newsz = addr + n
    if newsz < addr or newsz >= TRAPFRAME:  // wrapped round, or into trap pages
      return -1
    p->sz = newsz                          // no uvmalloc: nothing mapped yet
  else if n < 0:
    shrink as before (growproc / uvmdealloc)
  return addr                              // still the old break
  • Keep sbrk(0), the old-break return value and shrinking exactly as they were.
  • The size check matters because nothing else will stop a huge request now. TRAPFRAME and TRAMPOLINE are defined in kernel/memlayout.h.
  • You don't create empty PTEs for the new range. A missing table or an invalid entry both fault on access, and mappages builds any missing tables when you finally map the page.

4.2 Tell a valid first touch from a real error

Now a load or store page fault can mean two very different things. The handler must decide which:

Fault on…Below p->sz?Leaf entryAction
Untouched heap pageyesmissing or not validallocate and map
Guard pageyesvalid, no PTE_Ukill
Write to codeyesvalid, no PTE_Wkill
Above the break (the fault program)non/akill

The key insight: checking va < p->sz alone isn't enough, because the guard page and code are also below p->sz. What sets an untouched heap page apart is that it has no valid leaf entry at all. Any page that's valid but faulted anyway is a protection violation.

in usertrap(), for scause 13 or 15:
  va = r_stval()                            // the address, not sepc
  if va >= p->sz:              kill
  pte = walk(p->pagetable, va, 0)
  if pte != 0 and (*pte & PTE_V):  kill     // exists, so it's a protection fault
  mem = kalloc()
  if mem == 0:                 kill
  memset(mem, 0, PGSIZE)
  if mappages(p->pagetable, PGROUNDDOWN(va), PGSIZE, mem,
              PTE_R | PTE_W | PTE_U) != 0:
    kfree(mem); kill
  // do NOT touch p->trapframe->epc
  • Check the range before rounding. If p->sz isn't page-aligned, an address just above it rounds down into the last valid page and would wrongly pass. Compare the raw stval first.
  • Check the range before calling walk. walk panics for addresses at or above MAXVA. Since p->sz is below the trap pages, testing va < p->sz first keeps walk safe.
  • Clean up on failure. If mappages fails after kalloc succeeded, free the frame before killing, or it's lost for good. This is the same pattern as uvmalloc().
  • "Kill" means setkilled(p); the existing if(killed(p)) exit(-1); below finishes the job.

Why the instruction is retried, not skipped

For a system call, epc is bumped by 4 because the ecall has done its job. A page fault is different: the load or store never happened. After mapping the page, you return with epc still pointing at that same instruction. It runs again, the translation now succeeds, and the program never knows anything happened.

Practice
A student's handler allocates a frame for any load/store fault with stval < p->sz. What breaks?
  1. Nothing; every address below p->sz is legitimate
  2. Heap pages never get mapped
  3. A fault on the guard page reaches mappages on a valid entry, which panics with "remap" instead of killing the process
  4. The program break moves

The guard page already has a valid leaf (it just lacks PTE_U). Only a page with no valid entry may be allocated. The same check also stops a write to read-only code from being "fixed".

Part 4.3–4.4

Cleaning up a heap with holes

With lazy allocation, a process can exit or shrink its heap while some reserved pages were never touched. Those pages have no frame. But the freeing code assumes every page in range is mapped:

uvmunmap(pt, va, n, do_free)
Remove n pages of mappings starting at va, freeing frames if do_freePanics "uvmunmap: walk" if there's no table, and "uvmunmap: not mapped" if the entry isn't valid.
uvmdealloc(pt, old, new)
Used by negative sbrk; calls uvmunmap on the pages that fall off
uvmfree(pt, sz)
Used when a process exits; calls uvmunmap on 0 to sz, then frees the tables

So the first exit after a partly touched heap would panic the whole kernel. The fix is in uvmunmap(): when walk returns 0 or the entry isn't valid, that's an untouched page. Skip it (continue) instead of panicking. Free frames that are present as before.

Keep the "not a leaf" check. A valid entry with only PTE_V set points to another page table, not a data frame. Freeing it as data would be a real bug.

TrapOut of scope, but know why: fork() copies memory with uvmcopy(), which still panics on a missing page, and copyin/copyout (used when a system call reads or writes a user buffer) fail on untouched pages instead of faulting them in. lazytest doesn't exercise any of these, so a pass says nothing about them.

Extra checks the manual asks for

  • One touch only. Temporarily change the touch loop to one iteration, keeping the 30-page sbrk. PP should rise by exactly 1, and the process should exit without a uvmunmap panic. That exit is your hole-skipping fix working. Restore the loop afterwards.
  • Negative sbrk over a partly touched region must release it without panicking (same fix, through uvmdealloc).
  • fault read / fault write still die. Their target is at or above the break and was never reserved, so va >= p->sz sends them to kill. lazytest's pages are below p->sz with no entry, so they're allocated. That's the whole difference.
Practice
After implementing lazy sbrk and the fault handler but not changing uvmunmap, lazytest with a one-iteration touch loop ends how?
  1. Normally, PP +1
  2. Normally, PP +30
  3. The kernel panics with "uvmunmap: not mapped" when the process exits
  4. The process is killed on its first touch

Optional: growing the stack

The stack is fixed at one page with a guard below it. To grow it on demand you'd treat a fault just below the stack as legitimate, map a new page there, and move the guard page down so overflow is still caught. The hard part is telling "the stack wants to grow" from "a wild pointer hit the guard", which usually means setting a maximum stack size.

Before the checkpoints

Self-check

Tap a question to reveal the answer.

01Page vs frame vs PTE?+

A page is 4,096 bytes of virtual address space. A frame is 4,096 bytes of RAM. A PTE is the 8-byte entry that maps a page to a frame (or to the next table) and holds the V/R/W/X/U flags.

02Bit ranges of the three indexes and the offset?+

L2 38–30, L1 29–21, L0 20–12, offset 11–0. The offset is 12 bits because 4,096 = 212; each index is 9 bits because each table has 512 = 29 entries.

03Why three levels instead of one table?+

A flat table would need an entry for every possible page (about 1 GiB per process). A tree only has tables for regions that are in use.

04What does walk() return, and what can it allocate?+

A pointer to the level-0 entry (which may be invalid), or 0. With alloc = 1 it can allocate missing page-table pages, never data frames.

05Why does walkaddr() check PTE_U?+

It's used for addresses a user handed to the kernel. Refusing non-user pages stops a process from getting the kernel to read memory the process itself may not touch, like the guard page.

06Where does eager allocation happen for sbrk?+

In uvmalloc(), called from growproc(): kalloc a frame, memset it to 0, mappages it with PTE_R|PTE_U|PTE_W, for every new page.

07Why does sbrk return the old break?+

The old break is the start of the newly added region, which is the pointer the caller needs.

08countvp formula?+

PGROUNDUP(p->sz) / PGSIZE, so a partly used last page counts.

09Why use walk(…, 0) rather than walkaddr for countpp?+

walkaddr skips entries without PTE_U, so it would miss the guard page, whose frame must be counted. alloc = 0 so counting never creates tables.

10On the eager kernel, why doesn't PP rise when lazytest touches the pages?+

All 30 frames were already mapped inside the sbrk call, so the touches fault nothing and allocate nothing.

11scause codes for page faults?+

12 instruction fetch, 13 load, 15 store/AMO. (8 is a system call.)

12sepc vs stval on a page fault?+

sepc is the address of the faulting instruction. stval is the virtual address it tried to access.

13Why does fault target PGROUNDUP(break)?+

Bytes just past a mid-page break are still inside a mapped page. The next page boundary is the first byte guaranteed to be unmapped.

14Why must the trampoline be mapped at the same address in both page tables?+

The code that changes satp keeps running after the change. The next instruction is fetched through the new table, so the code must be at the same virtual address in both.

15How does the lazy handler tell a heap page from a protection fault?+

The address must be below p->sz and have no valid leaf entry. A valid entry that still faulted (guard page, read-only code) is a protection violation and is killed.

16Why not advance epc after fixing a page fault?+

The load or store never completed. Returning to the same instruction makes it run again, now with the page mapped.

17What must change in uvmunmap, and what must stay?+

Skip pages with no table or an invalid entry instead of panicking; they were never touched. Keep the "not a leaf" panic, since a PTE_V-only entry points to a page table, not data.

18Why does lazytest survive its faults while fault is killed?+

lazytest's pages are inside the reserved range (below p->sz) with no entry yet. fault's target is at or above the break and was never reserved.

19What does a lazytest pass not show?+

It doesn't test fork with untouched pages (uvmcopy), system calls reading or writing untouched buffers (copyin/copyout), or exact counts, since it accepts any PP increase of at least 30.
