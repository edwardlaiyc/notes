# Before you start

1. Read Appendix A (the project description) first. It feeds most of Q1–Q3.
2. Underline each **actor** (people, devices, external systems), each **function** (verb phrases), each **condition** ("if", "only when", "within"), and each **stored thing** (nouns).
3. Time: about 30 minutes per question. Q1(a) (the use case diagram) is the largest single part, about 18 marks. Give it the time it is worth.
4. The exam is open-book. Bring these notes, but practise the methods before the exam. You will not have time to learn a method during the exam.

# Q1 — Use case model (about 25 marks)

## (a) Use case diagram (18–19 marks)

1. List the actors. Check for devices and external systems as well as people. The system itself is not an actor.
2. List one use case for each goal. Use verb + noun names.
3. Draw the system boundary with the system name.
4. Connect actors to use cases with plain lines.
5. Add `<<include>>` for steps that always happen (login, check access, log activity). Arrow: base → included.
6. Add `<<extend>>` for steps that happen only under a condition (clarify unclear command, handle network failure). Arrow: extending → base. Write the condition.
7. Add actor generalization where two actors share use cases.
8. Check the list in Part 3.

## (b) Use case description (6–7 marks)

Give exactly the fields that the question asks for. Usually: actors, preconditions, flow of events, alternative flows.

- Mark the initiating actor.
- Numbered steps. Actor step, then system step.
- Alternative flow: "AF-S*n*: if …, 1. …, 2. return to step *m*."
- Use the terms from the description.

## (b) or (c) Activity diagram with swimlanes (7–8 marks)

- One swimlane for each actor, for the system and for each external system or device that works in the process.
- Decisions with a guard on each outgoing arrow.
- Fork and join only for parallel activities.
- Start and end nodes.

# Q2 — Analysis models and process (about 25 marks)

## (a) Conceptual class diagram (8–9 marks)

- Only the function that the question names.
- Boundary for each actor (UI) and for each device or external system (interface).
- Control for each use case.
- Entity for each stored noun.
- Show the stereotypes. No attributes or operations unless asked.
- Actor → boundary → control → entity. No boundary–entity link.
- Entity associations with multiplicities.

## (b) State machine diagram (4–6 marks)

- One object only: the one the question names (for example "the access controller" or "the conversation session").
- States are conditions that last. Events are on the arrows.
- Guards in `[ ]`. Actions after `/`.
- Start node, end node(s), and an exit from each non-final state.

## (c) Waterfall versus Agile (4–5 marks)

- Use the headings that the question gives (flexibility, customer involvement, delivery).
- Give one advantage of each model.
- If a requirement changes: Waterfall goes back through the phases with a formal change request. Agile updates and re-prioritises the backlog for a later sprint.

## (d) Scrum situation (5–8 marks)

Typical situations: advantages and challenges of sprints, sprints that overrun, an unhappy customer after a sprint. Answer with Scrum roles (PO, Scrum Master, team), events (planning, daily Scrum, review, retrospective) and artifacts (backlog, velocity, burndown). Each cause needs a matching corrective action. See Part 8.

## Calculations

- Velocity = total points ÷ sprints.
- Sprints = total points ÷ velocity, rounded up.
- Cost = sprints × Scrum team members (PO + SM + developers) × cost per member per sprint.

# Q3 — Design (about 25 marks)

## (a)(i) Architecture and detailed class diagram (8–15 marks)

1. Name the architecture: layered (three layers), or MVC for systems with many UIs or views.
2. Justify it with one or two facts from the description.
3. Draw the layers. Put boundaries in Presentation, controls in Application Logic, entities in Persistent Data.
4. Give each class key attributes (with types) and methods.
5. Dependencies go down only. Add multiplicities.
6. Add interfaces where things vary.

## (a)(ii) One NFR and an alternative architecture (8 marks)

1. Name the NFR and quote the part of the description that shows it.
2. Explain why the first architecture is weak for it.
3. Propose the alternative (client–server with replicated servers, event-based, MVC, security layer). Draw it simply. Explain how it meets the NFR.

## (b)(i) Scenario with more than one design pattern (6 marks)

1. Choose a feature with an Observer problem and a Strategy problem (and a Factory to create the strategy).
2. State each design problem.
3. Draw the class diagram. Label each role.

## (b)(ii) Evaluate patterns (3 marks)

"Overusing patterns makes code complex" or "Is it always good to combine patterns?": agree in part. Patterns give flexibility and loose coupling when the problem is real. Without a real need, they add classes, indirection and learning cost. Use a pattern only when the requirements show the need for it.
