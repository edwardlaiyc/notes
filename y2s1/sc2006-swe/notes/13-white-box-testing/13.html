Black-box testing verifies software against external specifications without knowledge of internal code structure. In contrast, white-box testing (structural or glass-box testing) derives test cases directly from the source code implementation. It analyzes control logic, data dependencies, and internal state transitions.

White-box testing is applied primarily at the unit testing level by developers to verify individual functions, methods, and algorithmic branches. Because exhaustively executing every possible path through a program is practically impossible due to loops and combinatorial branch explosions, structural testing relies on rigorous coverage criteria and basis path testing to guarantee that every independent execution path is exercised at least once.

1. Control Flow Graphs (CFG)

A Control Flow Graph (CFG) is a directed graph G=(V,E)G = (V, E) modeling all execution paths that can be traversed through a program:

  • Nodes (VV): Represent executable code sequences.
    • Process Block: A maximal sequence of statements executed strictly sequentially with single entry and single exit. Sequential assignments, arithmetic operations, and method calls without branches are grouped into a single node.
    • Decision Point (Predicate Node): A statement that alters control flow based on a condition (if, while, for, switch).
  • Edges (EE): Directed transfers of control between nodes. Binary decision nodes produce exactly two outgoing edges labeled true and false.

Mapping Programming Constructs to Graph Nodes

Construct Structural Representation in CFG Outgoing Edges
Sequence (s1; s2;) Single combined process block node. 11
if (cond) { s1; } Decision diamond/circle for condition. One edge targets s1 (true), one edge bypasses s1 (false). Both meet at the subsequent statement. 22
if (cond) { s1; } else { s2; } Decision node with true edge targeting s1 and false edge targeting s2. Both converge at downstream merge point. 22
while (cond) { body; } Decision node. true enters body, which loops back to the condition node. false exits the loop. 22
for (init; cond; step) { body; } init forms a preceding process node. cond forms a decision node. step executes at the tail of body before looping back to cond. 22
switch (expr) { case ... } An N-ary decision node with NN outgoing edges targeting matching case blocks, plus a default exit edge. NN

2. Coverage Criteria Hierarchy

Structural testing establishes quantitative thresholds to evaluate test thoroughness. Four ascending tiers of coverage define the testing hierarchy:

Coverage Criterion Formal Requirement Subsumption Hierarchy Weakness
Level 1: Statement Coverage (SCS_C) Every executable statement (node) in the program is executed by at least one test case. Weakest A single test case can achieve 100% statement coverage for an if block without an else branch, completely ignoring the false execution path.
Level 2: Branch Coverage (BCB_C) Every decision outcome (both true and false edges) is traversed at least once. Subsumes SCS_C Tests individual decision edges but misses combinations of branches across consecutive decisions.
Level 3: Basis Path Coverage Every linearly independent execution path (basis path) through the CFG is executed at least once. Subsumes BCB_C and SCS_C Guarantees all statements and decision edges are covered while testing independent branch interactions with minimal test cases (CCCC).
Level 4: Full Path Coverage Every distinct path from entry to exit is executed. Strongest Infeasible in practice. Any program containing unbounded loops possesses an infinite number of paths.

[!IMPORTANT] Subsumption Relationship: Full Path Coverage⟹Basis Path Coverage⟹Branch Coverage⟹Statement Coverage\text{Full Path Coverage} \implies \text{Basis Path Coverage} \implies \text{Branch Coverage} \implies \text{Statement Coverage} Achieving Branch Coverage guarantees 100% Statement Coverage. Achieving Statement Coverage does not guarantee Branch Coverage.

3. Cyclomatic Complexity (CC)

Introduced by Thomas McCabe, Cyclomatic Complexity (CCCC) measures the structural complexity of a program. In control flow testing, CCCC defines the number of linearly independent paths through the code, establishing the exact minimum number of test cases required to achieve basis path coverage.

Mathematical Formulas

For any connected control flow graph, CCCC can be calculated using three equivalent formulas:

  1. Edges and Nodes Formula: CC=E−N+2CC = E - N + 2 Where EE is the number of directed edges and NN is the number of nodes.

  2. Predicate Nodes Formula: CC=P+1CC = P + 1 Where PP is the number of binary decision points (predicates such as simple if, while, or for conditions).

  3. Enclosed Regions Formula: CC=RCC = R Where RR is the number of enclosed planar regions bounded by edges, plus 11 for the infinite open exterior region: R=Enclosed Regions+1R = \text{Enclosed Regions} + 1

[!WARNING] Compound Conditions: If a decision condition contains boolean operators (&&, ||), each individual condition represents an independent binary decision. In strict basis testing, PP increments for each sub-condition: if (a>0&&b==3)⟹P=2⟹CC=2+1=3\text{if } (a > 0 \;\&\&\; b == 3) \implies P = 2 \implies CC = 2 + 1 = 3

4. Basis Path Testing Protocol

A basis path (linearly independent path) is any path through a CFG that introduces at least one edge not traversed by any previously identified basis path. The set of all basis paths forms a basis spanning the entire execution space.

Step-by-Step Derivation Protocol

  1. Construct the CFG: Number all statements. Group sequential non-branching statements into single nodes. Represent each decision as a branching node. Connect control transfers with directed edges.
  2. Compute Cyclomatic Complexity (CCCC): Evaluate CC=E−N+2=P+1CC = E - N + 2 = P + 1. The resulting integer K=CCK = CC specifies exactly how many basis paths must be found.
  3. Select a Baseline Path: Choose a typical, clean through-path from entry to exit representing default program execution (e.g. executing loops zero or one time, following standard valid logic).
  4. Derive Remaining K−1K - 1 Basis Paths by Decision Inversion: Systematically retrace the baseline path and invert the outcome of each decision point one by one:
    • Path 2: Invert the outcome of the first decision point; follow baseline logic for all subsequent decisions.
    • Path 3: Invert the outcome of the second decision point; follow baseline logic elsewhere.
    • Path ii: Invert the outcome of the i−1i-1-th decision point. Each new path introduces at least one previously unvisited edge, preserving linear independence.
  5. Handling Loops: Loops introduce cycles. To prevent combinatorial explosion when generating basis paths, execute loops zero times (bypassing the loop) and exactly once (entering and exiting the loop).
  6. Construct Test Cases: For each basis path, identify concrete input values that force execution along that path, and record the expected output (oracle).

[!TIP] Feasible vs. Infeasible Paths: A mathematically derived basis path may be executionally infeasible if internal variable dependencies prevent a specific combination of conditions from occurring simultaneously. If an infeasible path occurs, testers replace it with an alternative independent path that is executable.

6. Control Flow vs. Data Flow Testing

While control flow testing derives paths based purely on execution control branches, data flow testing focuses on variable lifecycles:

Dimension Control Flow Testing Data Flow Testing
Primary Driver Branching structure, decisions, and loop constructs. Variable definition and variable usage points.
Core Abstraction Control Flow Graph (nodes = statements, edges = flow). Def-Use Pairs (DU pairs: where variable is defined vs where used).
Coverage Goal Statement, Branch, or Basis Path coverage. All-Defs, All-Uses, or All-DU-Paths coverage.
Defect Detection Missing branches, unreached statements, incorrect loop bounds. Uninitialized variables, dead variables (defined but never read), overwritten variables.
