A software process model is an abstract representation of the software development lifecycle. It prescribes the operational workflow, sequencing of engineering activities, deliverable milestones, and management validation gates required to transform customer requirements into a deployed system.

Selecting the appropriate process model depends heavily on project characteristics: requirement stability, technological maturity, system scale, regulatory constraints, and the acceptable tolerance for project risk.

1. Traditional and Plan-Driven Process Models

Plan-driven (prescriptive) models emphasize upfront planning, exhaustive architectural specification, and formal milestone reviews:

The Waterfall Model (Linear Sequential)

The classic Waterfall model executes the core SDLC phases in a strict linear sequence:

  • Key Invariant: A phase initiates only after the preceding phase completes and passes formal milestone verification.
  • Strengths: Simple to manage; clear milestones; disciplined documentation baseline.
  • Critical Vulnerability (The “Waterfall Fallacy”): Assumes requirements can be frozen upfront. In practice, clients discover their true needs only after seeing working software. Deferring integration and testing to the very end pushes defect discovery to the right, causing massive cost blowouts when late architectural flaws emerge.

The V-Model (Verification and Validation)

The V-Model refines the Waterfall lifecycle by explicitly pairing every upstream design activity with a corresponding downstream testing level:

Business Requirements ────────────────────────► User Acceptance Testing (UAT)
   │                                                     ▲
   ▼                                                     │
System Architecture ──────────────────────────► System Testing
   │                                                     ▲
   ▼                                                     │
Detailed Object Design ───────────────────────► Integration Testing
   │                                                     ▲
   ▼                                                     │
   Implementation (Coding) ───────────────────► Unit Testing
  • Early Test Design: Test plans and test cases are designed concurrently during their corresponding specification phases before coding begins.

Prototyping Lifecycle

When requirements are volatile or poorly understood, a prototyping cycle is introduced:

Elicit Outline Requirements→Build Quick Prototype→Evaluate with Users→Refine Requirements\text{Elicit Outline Requirements} \longrightarrow \text{Build Quick Prototype} \longrightarrow \text{Evaluate with Users} \longrightarrow \text{Refine Requirements}

  • Throwaway Prototyping: A rapid, low-fidelity prototype built strictly to explore requirements and resolve UI uncertainty, then discarded. Production code is built cleanly from scratch.
  • Evolutionary Prototyping: The prototype starts with well-understood requirements and is progressively engineered into the final production system.

Incremental Development

Instead of delivering the entire software system in a single monolithic release, the project is decomposed into a series of functional increments:

  • The highest-priority core infrastructure and features are implemented in Increment 1.
  • Each increment undergoes its own requirements, design, implementation, and testing cycle, producing a working release deployed to users.
  • Accommodates changing customer requirements while ensuring early delivery of business value.

Boehm’s Spiral Model (Risk-Driven)

The Spiral model structures development as a repeating series of evolutionary loops, explicitly guided by risk analysis:

  • Each 360-degree cycle traverses four quadrants:
    1. Determine Objectives: Define goals, alternative implementations, and operational constraints.
    2. Identify and Resolve Risks: Perform formal risk analysis, prototyping, benchmarking, and simulation.
    3. Development and Verification: Build and verify the next level of the software system.
    4. Plan Next Phase: Review progress with stakeholders and establish the scope for the subsequent spiral.

2. Process Model Decision Matrix

Dimension Waterfall Prototyping Incremental Spiral
Requirement Volatility Requires frozen, stable requirements upfront. Accommodates high ambiguity and evolving needs. Accommodates changes between successive increments. Accommodates frequent requirement shifts via risk loops.
User Involvement High at start (requirements) and end (acceptance). Low during implementation. Continuous user feedback throughout prototyping. High at every incremental delivery milestone. High at the planning quadrant of each loop.
Risk Management Poor: Late integration conceals catastrophic defects. Moderate: Exposes user interface and workflow risks early. Good: Early delivery of core increments mitigates project risk. Superb: Explicit quadrant dedicated entirely to risk mitigation.
Working Software Available only at the end of the project. Early disposable mockups available immediately. Available at the end of each increment. Available at the completion of operational spirals.
Best Suited For Well-understood domains, embedded firmware, safety-critical aerospace systems. Greenfield applications with high UX uncertainty. Commercial enterprise software, web portals, e-commerce. Large, mission-critical systems with severe technical and financial risks.

3. Official Tutorial Problems

Tutorial 4 Q1: Root causes of high software development costs

Question: Why are software development costs so high? Analyze the four primary drivers of development expense.

Solution: Software development costs are dominated by rework—wasted effort spent building, dismantling, and re-engineering system components. The four primary cost drivers are:

  1. Unacceptably Low Quality: Defect-ridden code necessitates unplanned cycles of bug triage, debugging, patch development, and full regression testing across design, implementation, and verification.
  2. Developing the Wrong Software Functions: Misunderstanding the problem domain results in implementing features that do not solve the customer’s operational problem, requiring complete redesign and reimplementation.
  3. Developing the Wrong User Interface: A poorly structured UI impedes user workflows, generating excessive support overhead and forcing costly interface reconstruction.
  4. Developing Unnecessary (Gold-Plated) Functions: Implementing complex, non-requested features consumes development and testing bandwidth without delivering commercial value, while unnecessarily inflating system maintenance overhead.

(Note: The latter three causes stem directly from failures in Requirements Engineering).

Tutorial 4 Q3 & Q4: Inherent software characteristics and contrast with hardware manufacturing

Question: (a) Discuss the intrinsic characteristics of software (malleability, complexity, size) that complicate its development. (b) Explain the two fundamental differences between software engineering and hardware manufacturing.

Solution:

Part (a): Intrinsic Software Characteristics

  1. Malleability: Software is radically easy to alter at the textual level. This creates continuous pressure from stakeholders to accommodate late design changes rather than stabilizing baseline specifications. Constant tweaking introduces unanticipated side-effects and structural decay.
  2. Complexity: Software exhibits arbitrary logical complexity with non-linear state spaces. No two components are completely identical. Unlike physical systems governed by continuous physical laws, software executes in discrete steps where an isolated off-by-one fault can crash an entire platform.
  3. Scale and Size: Software scales without spatial boundaries. As code size increases, internal communication paths and module interdependencies grow quadratically (O(n2)O(n^2)), causing defect density to compound rapidly.

Part (b): Contrast with Hardware Manufacturing

  1. Design Synthesis vs. Physical Replication: In hardware manufacturing, design occurs once, after which identical physical copies are mass-produced on an assembly line governed by statistical process control. In software engineering, copying the product is trivial (a bitwise disk clone); the entirety of the cost and effort resides in the unique creative design and intellectual synthesis of the prototype.
  2. Failure Mechanisms and Wear: Hardware components undergo physical wear, mechanical fatigue, and thermal stress, exhibiting a classic “bathtub curve” failure rate over time. Software never wears out or rusts physically; software failures are exclusively caused by latent design faults, untested execution paths, or changes in the execution environment (software entropy).
