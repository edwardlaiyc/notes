Section 1: Exam Question 1 Playbook — Requirements & Use Case Modeling (25 Marks)

1A. Functional vs. Non-Functional Requirements (FR vs. NFR)

Decision Matrix

Dimension Functional Requirements (FR) Non-Functional Requirements (NFR)
Core Question What must the system do? How well must the system behave?
Focus Functions, user workflows, data calculations, business rules, interfaces. Quality attributes, operational limits, environmental constraints.
Syntactic Template “The system shall [action verb] [entity] when [event] occurs.” “The system must be [quality attribute] [quantified metric].”
Validation Test Binary functional completion (feature works or does not work). Quantitative benchmark under specified operating conditions.

NFR Quality Attribute Taxonomy & Metric Verification

  • Performance: “95% of queries must return results within ≤500 ms\le 500\text{ ms} under a load of 1,000 concurrent users.”
  • Reliability & Availability: “Uptime ≥99.9%\ge 99.9\% (maximum unplanned downtime ≤8.76 hours/year\le 8.76\text{ hours/year}); MTTR ≤30 minutes\le 30\text{ minutes}.”
  • Security: “All network traffic encrypted with TLS 1.3; passwords hashed using bcrypt (cost factor ≥12\ge 12); RBAC enforced.”
  • Usability: “A novice user must complete initial registration within ≤90 seconds\le 90\text{ seconds} with zero errors after reading a 1-page guide.”
  • Maintainability: “Mean Time to Repair (MTTR) critical defects ≤2 hours\le 2\text{ hours}; unit test coverage ≥85%\ge 85\%.”
  • Scalability: “Architecture must support a 4×4\times increase in daily transaction volume without changing database schema.”

[!WARNING] Trap: Eliminating Vague Adjectives: Words like “fast”, “secure”, “user-friendly”, “adequate”, “normal”, and “reliable” are strictly non-verifiable. Replace every qualitative adjective with a specific number, time limit, percentage, or tolerance threshold!

1B. Use Case Diagram Construction

Rules & Invariants

  1. System Boundary: A labeled rectangle enclosing all use cases. Use cases reside inside; actors reside outside.
  2. Actor Rules:
    • Actors are external roles interacting directly with the system: Human User, External Device/Sensor, or External Software/API.
    • THE SYSTEM UNDER DESIGN IS NEVER AN ACTOR.
  3. Use Case Naming: Active Verb + Specific Noun (Log Shipment, Validate Credentials, Generate Report).
  4. Communication Association: A plain solid line connecting an Actor to a Use Case. No arrows, no labels.

<<include>> vs. <<extend>> Decision Criteria

Architectural Test <<include>> <<extend>>
Is execution mandatory? Yes (Always): The base use case unconditionally executes the included use case. No (Optional): Executes only if a specific guard condition evaluates to true.
Is base complete on its own? Incomplete: Base cannot achieve its goal without the included behavior. Complete: Base use case is fully meaningful even if extension never fires.
Arrowhead Direction Base points to Included: Base→≪include≫Included\text{Base} \xrightarrow{\ll\text{include}\gg} \text{Included} Extending points back to Base: Extending→≪extend≫Base\text{Extending} \xrightarrow{\ll\text{extend}\gg} \text{Base}
Annotation Required None. Extension Point name and Guard Condition enclosed in notes.
Clue Words in Scenario “always”, “must first”, “prior to”, “for every”, “shared step”. “optionally”, “if required”, “in case of error”, “when requested”.

1C. Standard Use Case Description (Specification) Table

Use this exact 8-field structure when asked to write a use case specification:

Use Case ID:      UC-01
Use Case Name:    <Active Verb + Noun> (e.g. Allocate Storage Silo)
Actors:           <Initiating Actor> (Initiator), <Secondary Actors / Devices>
Preconditions:    <Conditions that must strictly hold before initiation>
Postconditions:   <Guarantees satisfied upon successful completion>

Primary Flow of Events (Main Success Scenario):
  1. Actor initiates action by [inputting data / pressing control].
  2. System validates [input criteria].
  3. System executes [computation / state mutation].
  4. System prompts actor for [next input].
  5. System records [record] and displays [confirmation message].

Alternative Flows:
  AF-2a (<Descriptive Condition>):
    1. If [alternate condition holds], system executes [alternate action].
    2. System rejoins Primary Flow at Step <N>.

Exceptions:
  EX-2a (<Failure Condition>):
    1. System detects [error / timeout / invalid credential].
    2. System displays [error message], logs [event], and terminates use case.

Section 2: Exam Question 2 Playbook — Conceptual Modeling & Processes (25 Marks)

2A. Conceptual Domain Class Diagram

Modeling Protocol & Invariants

  • Goal: Capture problem domain concepts, attributes, and relationships.
  • CRITICAL INVARIANT: NEVER include methods/operations in a Conceptual Class Diagram. Methods belong to Detailed Object Design (Q3), not Conceptual Modeling!
  • Class Box: Name at top, typed attributes in the middle compartment. Bottom compartment is omitted or left empty.

Class Stereotypes (Robustness Analysis)

  • <<entity>>: Persistent business domain data and long-term records (Silo, Account, Shipment).
  • <<boundary>>: User interface screens, forms, sensor drivers, or external gateways (LoginForm, WeighbridgeInterface).
  • <<control>>: Coordinates use case workflow sequencing and business logic (AllocationManager, LoginController).
  • Communication Invariant: Actor →\to Boundary →\to Control →\to Entity. Boundary never communicates directly with Entity; Boundary never talks to Boundary; Entity never calls Control.

Relationship Syntax & Multiplicity

  • Association (Solid Line): Structural link. Read multiplicity at the far end:
    • 1: Exactly one.
    • 0..1: Zero or one (optional).
    • * or 0..*: Zero or more.
    • 1..*: One or more (mandatory collection).
  • Aggregation (♢\diamondsuit—): Hollow diamond at the “whole”. Part can exist independently of whole (e.g., Department ♢\diamondsuit— Professor).
  • Composition (⬧\blacklozenge—): Filled diamond at the “whole”. Part lifecycle strictly bound to whole; destroying whole destroys parts (e.g., Order ⬧\blacklozenge— OrderItem).
  • Generalization (△\triangle—): Solid line with hollow triangle pointing to superclass (e.g., ArrivalShipment →\to Shipment).

2B. Dynamic Models: State Machines vs. Activity Diagrams

Decision Factor State Machine Diagram (Statechart) Activity Diagram (Workflow)
Scope Discrete lifecycles and modes of ONE entity or object. Operational workflow across multiple actors and subsystems.
Trigger Mechanism Event-driven: Sits in state until an external event fires. Flow-driven: Automatically advances as each action finishes.
Transition Syntax event(parameters) [guard] / action Unlabeled control arrows; guards on decision diamond outputs.
Concurrency Orthogonal nested sub-states. Explicit Fork (split) and Join (synchronization barrier) bars.
Partitioning Composite states and sub-state machines. Swimlanes mapping actions to responsible actors/tiers.

2C. Software Process Models Decision Matrix

Model Requirement Stability User Involvement Risk Strategy Best Suited For
Waterfall Must be frozen upfront. Start & End only. Late integration; high risk. Stable, well-understood domains; safety-critical systems.
V-Model Frozen upfront. Start & End only. Early test design mitigates defect escape. Rigorous systems requiring formal compliance verification.
Prototyping Highly volatile / unknown. Continuous. Disposes of UI/workflow uncertainty early. Greenfield applications with novel user interfaces.
Incremental Core stable, details evolve. At each increment release. Early releases deliver value and mitigate risk. Enterprise commercial systems, e-commerce portals.
Spiral Evolving via risk loops. At each planning quadrant. Explicit risk assessment in every loop. Massive, high-risk, mission-critical systems.

2D. Agile & Scrum Worked Calculations

Scrum Roles, Ceremonies, and Artifacts

  • 3 Roles: Product Owner (prioritizes backlog), Scrum Master (removes blockers, servant leader), Development Team (cross-functional builders).
  • 4 Ceremonies: Sprint Planning, Daily Scrum (15-min standup), Sprint Review (increment demo), Sprint Retrospective (process improvement).
  • 3 Artifacts: Product Backlog (DEEP: Detailed, Emergent, Estimated, Prioritized), Sprint Backlog, Potentially Shippable Increment.

Formulas & Calculation Recipe

Team Velocity=Total Completed Story PointsNumber of Sprints\text{Team Velocity} = \frac{\text{Total Completed Story Points}}{\text{Number of Sprints}}

Sprints Required=⌈Total Product Backlog PointsTeam Velocity⌉\text{Sprints Required} = \left\lceil \frac{\text{Total Product Backlog Points}}{\text{Team Velocity}} \right\rceil

Sprint Cost=Total Team Members (PO + SM + Devs)×Cost per Member per Sprint\text{Sprint Cost} = \text{Total Team Members (PO + SM + Devs)} \times \text{Cost per Member per Sprint}

Total Project Cost=Sprint Cost×Sprints Required\text{Total Project Cost} = \text{Sprint Cost} \times \text{Sprints Required}

  • INVEST User Story Criteria: Independent, Negotiable, Valuable, Estimable, Small, Testable.
  • Sprint Burndown Chart: Y-axis = Remaining story points/hours; X-axis = Sprint days. Above ideal line = behind schedule; below = ahead.

Section 3: Exam Question 3 Playbook — Architecture & Design Patterns (25 Marks)

3A. Architectural Styles & NFR Trade-offs

Architectural Style Topology & Characteristics Key Advantage Critical Weakness
Layered (4-Layer) Presentation →\to Application →\to Domain →\to Technical Services. Downward dependencies only. High maintainability, strict separation of concerns. Call indirection performance overhead.
Client-Server Centralized server nodes serve distributed thin/thick clients over network. Centralized data consistency and access control. Single point of failure; network latency bottlenecks.
Three-Tier (3-Tier) Physical separation: Presentation Tier ↔\leftrightarrow App Logic Tier ↔\leftrightarrow DB Tier. Independent horizontal scalability of tiers. Deployment complexity; network serialization overhead.
Pipe-and-Filter Data stream transformed through independent filters connected by pipes. High throughput; easily parallelized on multi-core. Inefficient for interactive request-response UIs.
Event-Driven (Pub/Sub) Producers broadcast events to event bus; decoupled consumers subscribe. Extreme runtime decoupling and dynamic topology. Non-deterministic latency; hard to debug message traces.
Peer-to-Peer (P2P) Decentralized nodes act simultaneously as clients and servers. Massive fault tolerance; zero single point of failure. Complex distributed state and security consensus.

NFR to Architecture Mapping Rules

  • If question demands High Scalability & Traffic Handling ⟹\implies Propose Replicated 3-Tier with Load Balancer.
  • If question demands Continuous High Availability (24/7 Zero Downtime) ⟹\implies Propose Active-Passive / Active-Active Clustered Nodes with Automated Failover.
  • If question demands Stream Transformation Throughput ⟹\implies Propose Pipe-and-Filter Pipeline.
  • If question demands Multiple Reactive User Interfaces ⟹\implies Propose Model-View-Controller (MVC).

3B. Detailed Class Diagram Mapping (4-Layer Architecture)

When asked to map analysis classes to a Detailed Class Diagram:

  1. Divide canvas into 4 horizontal layers: Presentation, Application, Domain, Technical Services.
  2. Assign BCE classes:
    • Presentation Layer: Boundary classes (ShipmentInterface, MainUI).
    • Application Layer: Control classes (ShipmentManager, AllocationManager).
    • Domain Layer: Entity classes (Shipment, Silo, SiloAllocation).
    • Technical Services Layer: Interfaces & Drivers (ISensorDriver, DatabaseGateway).
  3. Add typed attributes (- id: int) and method signatures (+ allocateSilo(s: Shipment): boolean).
  4. Enforce Downward Dependencies: Arrows point down only. Lower layers never call upper layers directly!

3C. GoF Design Patterns Catalog

1. Strategy Pattern (Behavioral)

  • Problem: Multiple interchangeable algorithms or protocol variations; conditional switch/if-else blocks violate Open-Closed Principle.
  • Structure: Context ♢→\diamondsuit\to <<interface>> Strategy ←\leftarrow ConcreteStrategyA, ConcreteStrategyB.
  • Example: Payment processing (CreditCardStrategy, PayPalStrategy), Network protocols (FiveGStrategy, WiFiStrategy).

2. Observer Pattern (Behavioral)

  • Problem: One-to-many dependency where state changes in a Subject require automatic notification to multiple Observers without tight coupling.
  • Structure: Subject (maintains List<IObserver>, attach(), detach(), notify()) ♢→\diamondsuit\to <<interface>> IObserver (update()) ←\leftarrow ConcreteObserver.
  • Push vs. Pull: Push sends detailed data inside update(data); Pull passes minimal signal update(), observer calls subject.getState().

3. Factory Method Pattern (Creational)

  • Problem: Client code directly invoking new ConcreteClass() couples code to specific implementations.
  • Structure: Creator defines factoryMethod() : Product; ConcreteCreator instantiates ConcreteProduct.
  • Synergy with Strategy: Factory instantiates the appropriate ConcreteStrategy based on configuration and injects it into Context.

4. Decorator Pattern (Structural)

  • Problem: Need to dynamically attach additional behaviors to an object at runtime without rigid inheritance class explosion.
  • Structure: Decorator implements Component interface and wraps a Component reference.

5. Adapter Pattern (Structural)

  • Problem: Converting the incompatible interface of a legacy or 3rd-party class into an interface clients expect.
  • Structure: Adapter implements TargetInterface and delegates to wrapped Adaptee instance.

Section 4: Exam Question 4 Playbook — Testing & Maintenance (25 Marks)

4A. Black-Box Equivalence Partitioning & Boundary Value Analysis

Partitioning Rules

  1. Continuous Range [Min…Max][Min \dots Max]:
    • 1 Valid Class: Min≤x≤MaxMin \le x \le Max
    • 2 Invalid Classes: x<Minx < Min and x>Maxx > Max
    • Boundary Values Tested (Triplet for each boundary BB): Just Below (B−Δ),On Boundary (B),Just Above (B+Δ)\text{Just Below } (B - \Delta), \quad \text{On Boundary } (B), \quad \text{Just Above } (B + \Delta) (Where Δ=1\Delta = 1 for integers, 0.010.01 for currency, 1 ms1\text{ ms} for time).
  2. Discrete Finite Set {V1,V2,…,Vn}\{V_1, V_2, \dots, V_n\}:
    • 1 Valid Class: x∈{V1,…,Vn}x \in \{V_1, \dots, V_n\}
    • 1 Invalid Class: x∉{V1,…,Vn}x \notin \{V_1, \dots, V_n\}
    • Boundary Values: NONE. Discrete sets have no ordinal continuum; state explicitly: “Discrete inputs have zero boundary values.”

4B. Defensive Test Cases Table Protocol

When constructing the test matrix:

  1. Valid Test Cases: Combine valid boundary values across all input parameters. All inputs in a valid row must be valid. Expected Result = Accept / Normal Processing.
  2. Invalid (Defensive) Test Cases:
    • THE SINGLE FAULT ASSUMPTION: Every invalid test case must contain exactly ONE invalid input parameter, holding all other parameters strictly valid!
    • Why? If a test row contains two invalid inputs and is rejected, a bug in validating the second input is completely masked by the rejection of the first.
    • Expected Result = Specific Rejection / Error Exception.
| Test ID | Input A | Input B | Tested Condition | Expected Result (Oracle) |
|---|---|---|---|---|
| TC-01 | Valid Min | Valid Min | Valid Boundary Combination | Accept |
| TC-02 | Valid Max | Valid Max | Valid Boundary Combination | Accept |
| TC-03 | Invalid Low | Valid Interior | Input A: Just below min bound | Reject (Input A too low) |
| TC-04 | Invalid High| Valid Interior | Input A: Just above max bound | Reject (Input A too high) |
| TC-05 | Valid Interior | Invalid Low | Input B: Just below min bound | Reject (Input B too low) |

4C. White-Box Control Flow Testing & Cyclomatic Complexity

Control Flow Graph (CFG) Construction

  • Group sequential non-branching statements into single Process Nodes.
  • Map decisions (if, while, for) to Decision Nodes with branching true and false edges.

Cyclomatic Complexity (CCCC) Formulas

CC=E−N+2CC = E - N + 2 CC=P+1CC = P + 1 CC=Enclosed Regions+1CC = \text{Enclosed Regions} + 1 (Where E=edgesE = \text{edges}, N=nodesN = \text{nodes}, P=binary predicate decision pointsP = \text{binary predicate decision points}).

Coverage Hierarchy & Subsumption

Full Path Coverage⟹Basis Path Coverage⟹Branch Coverage (BC)⟹Statement Coverage (SC)\text{Full Path Coverage} \implies \text{Basis Path Coverage} \implies \text{Branch Coverage } (B_C) \implies \text{Statement Coverage } (S_C)

  • 100%100\% Branch Coverage guarantees 100%100\% Statement Coverage.
  • 100%100\% Statement Coverage does not guarantee Branch Coverage.

Deriving Basis Path Set (K=CCK = CC Paths)

  1. Path 1 (Baseline): A typical through-path from entry to exit (loops executed 0 or 1 time).
  2. Paths 2 to KK: Invert the outcome of each decision point one by one while keeping subsequent decisions at their baseline paths.
  3. For each basis path, define concrete test inputs and the expected output oracle.

4D. Testing Levels & Economics of Defect Repair

  • Testing Levels: Unit (Developer, internal logic) →\to Integration (Developer/Integrator, module interfaces) →\to System (QA Team, end-to-end FRs/NFRs) →\to Acceptance (Customer, UAT sign-off).
  • Cost of Late Faults (Boehm’s Escalation Curve): Requirements (1×)→Design (3–5×)→Coding (10×)→Testing (15–20×)→Operations (100–200×)\text{Requirements } (1\times) \longrightarrow \text{Design } (3\text{--}5\times) \longrightarrow \text{Coding } (10\times) \longrightarrow \text{Testing } (15\text{--}20\times) \longrightarrow \text{Operations } (100\text{--}200\times)
  • Shift-Left Principle: Moving testing and verification as early as possible into the lifecycle to intercept defects while the cost of rework remains at 1×1\times.

4E. Software Maintenance & Refactoring Catalogue

Maintenance Categories

Maintenance Type Primary Driver Purpose Approximate Effort
Corrective Reactive (Defects) Fixing bugs, crashes, vulnerabilities in production. ~20%
Adaptive Reactive (Environment) Adapting to changed OS, hardware, DB, or regulatory laws without changing features. ~20%
Perfective Proactive (User Value) Adding new features, improving UI, optimizing performance (Dominates maintenance!). ~55%
Preventive Proactive (Quality) Refactoring code, reducing technical debt to prevent future faults. ~5%

Code Smells & Refactoring Solutions

Code Smell Architectural Symptom Refactoring Remedy
Duplicate Code Identical logic in multiple places. Extract Method or Pull Up Method.
Long Method Method with too many lines and responsibilities. Extract Method or Decompose Conditional.
Large Class (God Class) Class violating Single Responsibility Principle. Extract Class or Extract Subclass.
Feature Envy Method in Class A heavily accesses fields of Class B. Move Method into Class B.
Switch Statements on Type Repetitive conditional branches on type codes. Replace Conditional with Polymorphism (Strategy/State Pattern).
Shotgun Surgery A single conceptual change requires edits across many classes. Move Method / Move Field to consolidate concerns.
