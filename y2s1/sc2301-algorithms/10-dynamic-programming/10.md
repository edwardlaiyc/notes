# 10. Dynamic Programming

This chapter covers the dynamic programming lectures (Weeks 9 and 10). Like divide and conquer (Chapter 2), **dynamic programming** (DP) solves a problem by solving smaller versions of it. The difference: in DP the smaller problems **overlap**, so a plain recursion solves the same small problem again and again. DP solves each one **once**, stores the answer, and reuses it.

This often turns an exponential-time algorithm into a polynomial-time one. The chapter shows the idea on Fibonacci numbers, then applies it to the **longest common subsequence** and the **0/1 knapsack** problem. It ends with a recipe for designing a DP algorithm for a new problem.

---

## 1. What Goes Wrong with Plain Recursion?

### 1.1 Divide and conquer against dynamic programming

Both strategies follow the same outline:

1. Divide the problem into smaller sub-problems.
2. Solve each sub-problem recursively.
3. Combine the sub-solutions into a solution for the whole problem.

The difference is in the sub-problems:

* **Divide and conquer:** the sub-problems are **independent**. In mergesort, the left half and the right half share no work.
* **Dynamic programming:** the sub-problems **overlap**. The same sub-problem appears in many places. DP adds one rule:

> **Never compute the answer to the same sub-problem more than once.**

### 1.2 Example: Fibonacci numbers

The Fibonacci numbers are

$$F_0 = 0, \qquad F_1 = 1, \qquad F_n = F_{n-1} + F_{n-2} \text{ for } n \ge 2.$$

The direct recursive code:

```
int fib(n) {
    if (n == 0 || n == 1) return n;
    else return fib(n - 1) + fib(n - 2);
}
```

![The calls made by fib(6). Each node is one call. fib(2) alone is computed 5 times (the blue nodes).](10-artifacts/fib-call-tree.png){width=80%}

The tree repeats a lot of work:

* `fib(4)` is computed 2 times;
* `fib(3)` is computed 3 times;
* `fib(2)` is computed 5 times.

### 1.3 How many calls?

For `fib(6)`:

* The tree is a **full** binary tree down to depth 3, which is $n/2$. (The shortest branch subtracts 2 each time.)
* The deepest branch has depth 5, which is $n - 1$. (It subtracts 1 each time.)

A full binary tree of depth $D$ has $1 + 2 + 4 + \dots + 2^D = 2^{D+1} - 1$ nodes. The call tree contains a full tree of depth 3, and fits inside a full tree of depth 5. So the number of calls $R$ is between the sizes of those two full trees:

$$2^4 - 1 < R < 2^6 - 1.$$

In general, put $D = n/2$ for the lower bound and $D = n - 1$ for the upper bound:

$$2^{n/2 + 1} - 1 < R < 2^n - 1.$$

This is **exponential**, $O(2^n)$. Yet there are only $n + 1$ **different** sub-problems, $F_0$ to $F_n$. Almost all the work is repeated work.

## 2. The Fix: Store Each Answer Once

### 2.1 The dictionary

Keep a **dictionary** of answers already computed. It is usually an array. Before solving a sub-problem, check the dictionary:

* **already solved:** retrieve the stored answer;
* **not solved yet:** solve it, then store the answer.

![The same tree with stored answers. Green: base cases. Yellow: computed for the first time and stored. Purple: retrieved from the dictionary. Grey: never called.](10-artifacts/fib-pruned-tree.png){width=70%}

Only one thin path of the tree is really computed. Each purple node costs $O(1)$, and everything below it disappears.

> The main feature of DP: it **replaces an exponential-time computation by a polynomial-time one**, by storing solutions and never recomputing them.

This is the same idea as DFS (Chapter 5). DFS explores only **undiscovered** vertices, and just checks the others. DP solves only **unsolved** sub-problems, and just retrieves the others.

### 2.2 Top-down: memoization

Keep the recursion, and add the dictionary. The lecture's steps:

1. Write the problem $P$ in terms of smaller versions of itself, $Q_1, Q_2, \dots$
2. Turn this into a recursive function.
3. Use a dictionary to store the solutions of sub-problems.
4. In the recursive function:
    * **before** a recursive call on $Q_i$, check the dictionary. If $Q_i$ is solved, retrieve it. Otherwise, make the call;
    * **just before returning** the solution of $P$, store it in the dictionary.

Storing the result of each call this way is called **memoization**.

```
int fibDP(n) {
    int f1, f2;
    if (n == 0 || n == 1) {
        store(Soln, n, n);
        return n;
    }
    if (not member(Soln, n - 1)) f1 = fibDP(n - 1);
    else                         f1 = retrieve(Soln, n - 1);
    if (not member(Soln, n - 2)) f2 = fibDP(n - 2);
    else                         f2 = retrieve(Soln, n - 2);
    f1 = f1 + f2;
    store(Soln, n, f1);
    return f1;
}
```

The dictionary `Soln` is an array, filled with $-1$ at the start ("not solved"):

| Operation | Code |
| :--- | :--- |
| `member(Soln, j)` | return `Soln[j] != -1` |
| `store(Soln, j, s)` | `Soln[j] = s` |
| `retrieve(Soln, j)` | return `Soln[j]` |

**Cost.**

* Each call does $O(1)$ work, not counting its own recursive calls.
* `fibDP` really runs only once for each value from 0 to $n$: $n + 1$ calls.
* Total: **$O(n)$**.

### 2.3 Bottom-up: tabulation

Instead of recursion, fill the dictionary **in an order where every answer is ready before it is needed**. Start from the smallest sub-problems and build up.

```
soln[0] = 0;
soln[1] = 1;
for j = 2 to n
    soln[j] = soln[j-1] + soln[j-2];
```

For $n = 6$:

| $j$ | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| `soln[j]` | 0 | 1 | 1 | 2 | 3 | 5 | 8 |

This is also **$O(n)$**, with no recursion overhead.

### 2.4 Saving memory

The dictionary does not always need every answer. Fibonacci looks back only two steps, so two variables are enough:

```
a = 0; b = 1;                 // F(0), F(1)
for j = 2 to n { c = a + b; a = b; b = c; }
return b;                     // for n >= 1
```

This uses $O(1)$ memory. The same trick works whenever each row of a table depends only on the row before it. But if you need to **rebuild** the solution (Section 4.6), you must keep the whole table.

## 3. The Subproblem Graph

### 3.1 What it is

The **subproblem graph** of a recursive algorithm has:

* one **vertex** for each sub-problem;
* an **edge** from $I$ to $J$ if solving $I$ calls $J$ **directly**.

![The subproblem graph of fib(6). Each vertex n has edges to n-1 and n-2.](10-artifacts/fib-subproblem-graph.png){width=70%}

### 3.2 What it tells you

* **It must be a DAG** (a directed graph with no cycles, Chapter 5). A cycle would mean a sub-problem depends on itself, and the recursion would never end.
* **Fill order.** Solve each sub-problem after every sub-problem it points to. That is a **reverse topological order** of the graph. For Fibonacci: $0, 1, 2, \dots, n$.
* **Number of vertices** = number of distinct sub-problems = size of the dictionary.
* **Number of edges** = total work spent combining answers.

So the running time is roughly

$$\text{time} \approx (\text{number of sub-problems}) \times (\text{work per sub-problem}).$$

### 3.3 The bottom-up steps (lecture)

1. Write the problem in terms of smaller versions of itself: the **sub-problems**.
2. Relate them with a **recursive function**.
3. Draw the **subproblem graph** (it must be a DAG). Find the dependencies and a topological order.
4. Use a **dictionary** to store the sub-problem solutions.
5. In an iterative function:
    * state the **base cases** and their solutions;
    * fill in the dictionary in topological order, using smaller solutions to build larger ones;
    * find the original problem in the table;
    * if needed, use **parent pointers** to recover the actual solution, not just its value.

## 4. When Does DP Give the Optimal Answer?

### 4.1 Optimization problems

DP is mainly a tool for **optimization problems**: find the best (shortest, longest, cheapest, most profitable) solution.

### 4.2 The principle of optimality

DP works when the problem satisfies the **principle of optimality**:

> The sub-solutions of an optimal solution are themselves optimal solutions of their sub-problems.

Example: if $A \to B \to C \to D$ is a shortest path from $A$ to $D$, then $A \to B \to C$ is a shortest path from $A$ to $C$. (Chapter 6, Lemma 1.)

**Why it matters.** DP builds the best answer for a big problem **only** from the best answers of smaller problems. That is valid only if a best solution is always made of best parts.

### 4.3 How to prove it for a problem

Use a **cut-and-paste** argument by contradiction:

1. Take an optimal solution of the whole problem.
2. Suppose one of its parts is **not** optimal for its sub-problem.
3. Cut out that part, and paste in a better solution of the sub-problem.
4. The whole solution is now better, and still valid.
5. That contradicts "the solution was optimal". So every part must be optimal.

In step 4, check that the pasted part still fits: it must not break any rule of the problem.

### 4.4 The DP selection rule

> When there are several possibilities, **compute all of them and take the best**.

This is the difference from a **greedy** algorithm (Chapter 6), which picks the choice that looks best now and never checks the others.

## 5. Longest Common Subsequence (LCS)

### 5.1 Definitions

* A **subsequence** of a sequence keeps some of its characters, **in their original order**, and drops the rest. The kept characters do not have to be next to each other.
    * For $s$ = ACTTGCG: ACT, AG, ATTC, T and ACTTGC are subsequences.
    * TTA is not (the order is wrong). AGGC is not (there is no C after the two Gs).
* A **common subsequence** of $x$ and $y$ is a subsequence of both.
* A **longest common subsequence (LCS)** is a common subsequence of maximum length. It may **not be unique**.

The LCS length measures how similar two sequences are, for example two DNA strands or two versions of a document.

**The problem.** Given $x = \langle x_1, \dots, x_n \rangle$ and $y = \langle y_1, \dots, y_m \rangle$, find $LCS(n, m)$, the length of an LCS.

**Brute force.** List all subsequences of $x$ (up to $2^n$ of them) and check each against $y$. This is exponential.

### 5.2 Step 1: smaller versions of the problem

Let $LCS(i, j)$ be the LCS length of the **prefixes** $x_1 \dots x_i$ and $y_1 \dots y_j$. Look at the **last** characters, $x_i$ and $y_j$.

**Case 1: $x_i = y_j$.**

* This character can be the last character of the LCS.
* Before it comes an LCS of the shorter prefixes $x_1 \dots x_{i-1}$ and $y_1 \dots y_{j-1}$.
* So $LCS(i, j) = LCS(i-1, j-1) + 1$.

**Case 2: $x_i \ne y_j$.**

* They cannot both be the last character of a common subsequence. So $x_i$ is not used, or $y_j$ is not used, or neither.
* If $x_i$ is not used, the answer is $LCS(i-1, j)$.
* If $y_j$ is not used, the answer is $LCS(i, j-1)$.
* We do not know which, so compute **both** and take the larger (the DP selection rule).

**Principle of optimality.** In each case, the shorter part must itself be an LCS of the shorter prefixes. If it were not, a longer one would give a longer LCS for $(i, j)$.

### 5.3 Step 2: the recursive function

$$LCS(i, j) = \begin{cases}
0 & \text{if } i = 0 \text{ or } j = 0, \\[4pt]
LCS(i-1, j-1) + 1 & \text{if } i, j > 0 \text{ and } x_i = y_j, \\[4pt]
\max\big(LCS(i-1, j),\; LCS(i, j-1)\big) & \text{if } i, j > 0 \text{ and } x_i \ne y_j.
\end{cases}$$

* **Base case:** an empty prefix has nothing in common with anything.
* A plain recursive version is very slow, because the same $(i, j)$ pairs are reached again and again.

### 5.4 Steps 3 and 4: subproblem graph and table

Each $(i, j)$ depends on three cells:

* $(i-1, j-1)$: diagonally up-left;
* $(i-1, j)$: above;
* $(i, j-1)$: to the left.

![The subproblem graph of LCS(6, 5). Every cell points up, left and diagonally up-left.](10-artifacts/lcs-subproblem-graph.png){width=70%}

The dictionary is an $(n+1) \times (m+1)$ array `c`.

* Fill row 0 and column 0 with 0.
* Then fill **row by row**, from row 1 to row $n$, and **left to right** within each row.
* When you reach a cell, its three dependencies are already filled.

### 5.5 Step 5: the code

```
int LCS(n, m) {
    for i = 0 to n  c[i][0] = 0;
    for j = 1 to m  c[0][j] = 0;
    for i = 1 to n
        for j = 1 to m
            if (x[i] == y[j])
                c[i][j] = c[i-1][j-1] + 1;
            else if (c[i-1][j] >= c[i][j-1])
                c[i][j] = c[i-1][j];
            else
                c[i][j] = c[i][j-1];
    return c[n][m];
}
```

**Cost.**

* The two loops run $nm$ times. Each iteration takes constant time.
* **Time: $O(nm)$.**
* **Space: $O(nm)$**, for the $(n+1) \times (m+1)$ array.

### 5.6 Recovering the subsequence itself

The table gives only the **length**. To get the subsequence, keep a **hint array** `h` (parent pointers). It records which case produced each cell:

| Hint | Meaning | Came from |
| :---: | :--- | :--- |
| `\` | $x_i = y_j$; this character is in the LCS | $(i-1, j-1)$ |
| `|` | $c[i][j] = c[i-1][j]$ | above |
| `—` | $c[i][j] = c[i][j-1]$ | the left |

* Column 0 is filled with `|`, and row 0 with `—`.
* **Tie rule:** when $c[i-1][j] = c[i][j-1]$, the code takes from **above** (`|`), because it tests `>=`.

To read the LCS, start at `h[n][m]` and follow the hints back until you reach row 0 or column 0:

```
getSequence(n, m) {
    s = empty stack;
    i = n; j = m;
    while (i != 0 and j != 0) {
        if (h[i][j] == '\')       { s.push(x[i]); i--; j--; }
        else if (h[i][j] == '|')  i--;
        else                      j--;
    }
    pop and output everything from s;     // the LCS, in order
}
```

* Each diagonal step gives one character of the LCS.
* The characters come out **last first**, so a stack puts them back in order.
* Each step lowers $i$ or $j$ (or both). So there are at most $n + m$ steps: **$O(n + m)$**.

### 5.7 Example 1 (lecture): $x$ = ACGGA, $y$ = ACTG

The length table:

| | | A | C | T | G |
| :---: | :---: | :---: | :---: | :---: | :---: |
| | 0 | 0 | 0 | 0 | 0 |
| **A** | 0 | 1 | 1 | 1 | 1 |
| **C** | 0 | 1 | 2 | 2 | 2 |
| **G** | 0 | 1 | 2 | 2 | 3 |
| **G** | 0 | 1 | 2 | 2 | 3 |
| **A** | 0 | 1 | 2 | 2 | 3 |

So $LCS(5, 4) = 3$. Following the hints back from $(5, 4)$:

| Cell | Hint | Action |
| :--- | :---: | :--- |
| $(5, 4)$ | `|` | move up |
| $(4, 4)$ | `\` | record **G**, move diagonally |
| $(3, 3)$ | `|` | move up |
| $(2, 3)$ | `—` | move left |
| $(2, 2)$ | `\` | record **C**, move diagonally |
| $(1, 1)$ | `\` | record **A**, move diagonally |
| $(0, 0)$ | — | stop |

Reading the recorded characters in reverse gives the LCS **ACG**.

![LCS of x = ACGGA and y = ACTG. Top: the length table; LCS(5, 4) = 3. Bottom: the hint array. Following the highlighted path from the bottom-right corner gives the LCS ACG.](10-artifacts/lcs-hint-example.png){width=90%}

### 5.8 Example 2 (lecture): $x$ = CGGTAT, $y$ = AGTTGC

The lecture's second example gives $LCS(6, 6) = 3$. Following the hints from $(6, 6)$ records T, T, G, so the LCS is **GTT**. Other LCSs of length 3 may exist. The tie rule (take from above) decides which one the algorithm finds.

### 5.9 Filling an LCS table by hand

1. Draw the table with $x$ down the side and $y$ across the top. Add a row 0 and a column 0 of zeros.
2. For each cell, row by row:
    * if the row's character **equals** the column's character: take the **upper-left** value **plus 1**;
    * otherwise: take the **larger** of the cell **above** and the cell to the **left**. On a tie, take **above**.
3. The length is the **bottom-right** cell.
4. To get the subsequence, walk back from the bottom-right. On a match, go diagonally and record the character. Otherwise, move to the neighbour you copied from.

## 6. The 0/1 Knapsack Problem

### 6.1 The problem

* A knapsack holds a total weight of at most $C$, a positive integer.
* There are $n$ objects. Object $i$ has weight $w_i$ and profit $p_i$, all positive integers.
* Find the **largest total profit** of a subset of the objects whose total weight is at most $C$.

"0/1" means each object is either taken **whole** (1) or **left** (0). You cannot take part of an object.

Example use: $C$ is an amount of money to invest, the $w_i$ are the costs of possible investments, and the $p_i$ their expected returns.

**Brute force.** There are $2^n$ subsets of $n$ objects. Checking them all takes $O(2^n)$ time.

### 6.2 Step 1: smaller versions of the problem

Look at the **last** object, object $n$. Either the best solution takes it, or it does not.

* **Take object $n$** (only possible if $w_n \le C$):
    * it earns $p_n$;
    * it uses up $w_n$ of the capacity;
    * the rest of the profit is the best for the first $n - 1$ objects with capacity $C - w_n$.
* **Leave object $n$:**
    * the profit is the best for the first $n - 1$ objects with the full capacity $C$.

Compute both and take the better one.

### 6.3 Step 2: the recursive function

Let $P(C, j)$ be the largest profit from a subset of the **first $j$ objects**, with capacity $C$.

**Base cases** (no objects, or no capacity):

$$P(C, 0) = 0, \qquad P(0, j) = 0.$$

**Recursion:**

$$P(C, j) = \begin{cases}
\max\big(P(C, j-1),\; p_j + P(C - w_j, j-1)\big) & \text{if } w_j \le C, \\[4pt]
P(C, j-1) & \text{if } w_j > C.
\end{cases}$$

### 6.4 Step 3: the subproblem graph

$(C, j)$ depends on two cells, both in column $j - 1$:

* $(C, j-1)$: the same capacity (leave object $j$);
* $(C - w_j, j-1)$: a smaller capacity (take object $j$).

Only the sub-problems reachable from $(C, n)$ are really needed.

![The subproblem graph for C = 20 and four objects with weights 4, 6, 8, 6. Each (capacity, j) points to (capacity, j-1) and (capacity - w_j, j-1).](10-artifacts/knapsack-subproblem-graph.png){width=75%}

### 6.5 Steps 4 and 5: the table and the code

The dictionary is `profit[C+1][n+1]`:

* **rows** are capacities $0 \dots C$;
* **columns** are objects $0 \dots n$.

Fill row 0 and column 0 with 0. Then fill each row $r = 1 \dots C$ from left to right, $c = 1 \dots n$.

```
int knapsack(int[] w, int[] p, int C, int n) {
    for c = 0 to n  profit[0][c] = 0;
    for r = 1 to C  profit[r][0] = 0;
    for r = 1 to C                         // capacity
        for c = 1 to n {                   // objects 1..c are allowed
            profit[r][c] = profit[r][c-1];                 // leave object c
            if (w[c] <= r)
                if (profit[r][c] < profit[r - w[c]][c-1] + p[c])
                    profit[r][c] = profit[r - w[c]][c-1] + p[c];   // take object c
        }
    return profit[C][n];
}
```

### 6.6 Example 2 (lecture): $C = 3$

| Object | 1 | 2 | 3 |
| :--- | :---: | :---: | :---: |
| Weight $w$ | 1 | 2 | 3 |
| Profit $p$ | 1 | 4 | 6 |

Each cell is $\max(\text{left},\; p_c + \text{the cell } w_c \text{ rows up in the previous column})$:

| $r$ | $c = 0$ | $c = 1$ | $c = 2$ | $c = 3$ |
| :---: | :---: | :---: | :---: | :---: |
| 0 | 0 | 0 | 0 | 0 |
| 1 | 0 | 1 | 1 | 1 |
| 2 | 0 | 1 | 4 | 4 |
| 3 | 0 | 1 | 5 | 6 |

Three cells worked out in full:

* $(2, 2)$: leave object 2 gives $\text{profit}[2][1] = 1$. Take it gives $4 + \text{profit}[0][1] = 4$. Best: **4**.
* $(3, 2)$: leave gives $1$. Take gives $4 + \text{profit}[1][1] = 5$. Best: **5**.
* $(3, 3)$: leave gives $5$. Take gives $6 + \text{profit}[0][2] = 6$. Best: **6**.

The answer is $\text{profit}[3][3] = 6$: take object 3 alone.

### 6.7 Example 1 (lecture): $C = 20$

Weights 4, 6, 8, 6 and profits 7, 6, 9, 5. The table below shows rows 10 to 20.

![The completed table (rows 10 to 20) for C = 20, with weights 4, 6, 8, 6 and profits 7, 6, 9, 5. The answer is profit[20][4] = 22.](10-artifacts/knapsack-table.png){width=85%}

The answer is $\text{profit}[20][4] = 22$.

### 6.8 Which objects were taken?

Walk back from $\text{profit}[C][n]$:

* if $\text{profit}[r][c] = \text{profit}[r][c-1]$: object $c$ was **left**. Move to column $c - 1$, same row;
* otherwise: object $c$ was **taken**. Move to row $r - w_c$, column $c - 1$.

Stop at column 0. Or store a parent pointer in each cell while filling the table.

For Example 1: at $(20, 4)$ the value 22 equals $(20, 3)$, so object 4 was left. At $(20, 3)$, $22 \ne 13$, so object 3 (weight 8) was taken; move to $(12, 2)$. There $13 \ne 7$, so object 2 (weight 6) was taken; move to $(6, 1)$, which is 7, not 0, so object 1 was taken. The objects are 1, 2, 3: weight $4 + 6 + 8 = 18 \le 20$, profit $7 + 6 + 9 = 22$.

### 6.9 Cost, and why it is "pseudo-polynomial"

The table has $(C+1)(n+1)$ cells, each filled in $O(1)$:

$$\text{time} = \text{space} = O(nC).$$

That looks polynomial, but it is **not** polynomial in the usual sense.

* An algorithm is **strongly polynomial** if its time is a polynomial in the **size** of the input. Here the input holds $n$ weights and $n$ profits.
* An algorithm is **pseudo-polynomial** if its time is a polynomial in the **numeric value** of the input.

$C$ is a single number. Writing it takes only about $\log_2 C$ bits. If $C$ doubles, the input grows by just one bit, but the running time doubles. Measured against the input size, $O(nC)$ is exponential.

> The DP algorithm for 0/1 knapsack is **pseudo-polynomial**. It is fast only when $C$ is small.

## 7. Shortest Paths in a DAG

The lecture outline lists this topic, but its slides were not released. The standard method fits this chapter's recipe:

* **Sub-problem:** $dist(v)$, the shortest distance from the source $s$ to $v$.
* **Recursion:**

$$dist(s) = 0, \qquad dist(v) = \min_{(u, v) \in E} \big(dist(u) + w(u, v)\big).$$

* **Order:** the graph is a DAG, so the subproblem graph has no cycles. Compute the $dist$ values in **topological order** (Chapter 5), so every $u$ is done before $v$.
* **Cost:** each edge is used once, so $O(|V| + |E|)$.
* Unlike Dijkstra (Chapter 6), this works with **negative** edge weights, because there is no cycle.

Replacing min with max gives the **longest** path in a DAG.

## 8. Designing a DP Algorithm for a New Problem

### 8.1 The recipe

Use the same five steps every time.

1. **Define the sub-problem in words.** Say exactly what $F(i)$ or $F(i, j)$ means. For example: "the largest profit using only the first $i$ items", or "the number of ways to reach position $(i, j)$". A vague definition causes most errors.
2. **Write the recursion and the base cases.**
    * Think about the **last decision**: what happens to the last item, the last character, the last step?
    * Each possible decision gives one term.
    * Combine the terms with **max**, **min** or **sum**, depending on the question.
    * State the base cases: empty input, size 0 or 1, the first row and column.
3. **Draw the subproblem graph.** Start from the original problem. Draw edges to the sub-problems its recursion calls, then theirs, down to the base cases. Label each node with its value if asked.
4. **Choose the table and the fill order.** One table entry per distinct sub-problem. Fill in an order where everything a cell needs is already filled.
5. **State the complexity.**

$$\text{time} \approx (\text{number of sub-problems}) \times (\text{work per sub-problem}), \qquad \text{space} = \text{table size}.$$

### 8.2 How the shape of the recursion sets the table

| The sub-problem is indexed by | Table | Fill order |
| :--- | :--- | :--- |
| One number $i$ (a prefix, a size) | 1-D array | $i = 0, 1, 2, \dots$ |
| Two prefixes $(i, j)$, or a grid position | 2-D array | row by row, left to right |
| An interval $(i, j)$ of one sequence | 2-D array | by **increasing length** $j - i$ |
| A size and a capacity, as in knapsack | 2-D array | by capacity, then by item |

And the cost of one cell:

* If a cell looks at a **fixed** number of other cells (LCS: 3; knapsack: 2), each cell is $O(1)$.
* If a cell takes a max, min or sum over **all smaller** values (for example $F(n) = \sum_{k < n} F(k)$), each cell costs $O(n)$. The total time is then (number of cells) $\times\, O(n)$.

### 8.3 The plain recursion is usually exponential

To find the running time of the recursive version **without** a dictionary, write its cost as a recurrence, and solve it with Chapter 8's methods.

* If each call makes two or more calls on sizes only slightly smaller, the cost grows like Fibonacci or faster: **exponential**.
* With a dictionary, the cost drops to (number of distinct sub-problems) $\times$ (work per sub-problem).

## 9. DP, Divide and Conquer, and Greedy

| Statement | D&C | Greedy | DP |
| :--- | :---: | :---: | :---: |
| Divides a problem into sub-problems and builds larger solutions from smaller ones | Yes | — | Yes |
| Sub-problems are independent | **Yes** | — | **No** |
| Stores sub-problem solutions and reuses them | No | No | **Yes** |
| Divides at fixed, chosen-in-advance points (such as the middle) | Yes | — | No |
| At each step, picks the locally best choice and never undoes it | — | **Yes** | No |
| At each step, computes all choices and selects the best | — | — | **Yes** |
| Solves sub-problems in a fixed order (by size, or topological order) | — | — | Yes (bottom-up) |
| Always optimal | — | Only with a proof | Yes, if the principle of optimality holds |

## 10. Common Traps

* DP needs **overlapping** sub-problems. Without overlap, plain divide and conquer is enough.
* DP gives the optimal answer only if the **principle of optimality** holds.
* Memoization is **top-down** (recursion + dictionary). Tabulation is **bottom-up** (loops in a correct order). Both have the same complexity.
* The subproblem graph must be a **DAG**. Fill the table in **reverse topological** order: dependencies first.
* Time $\approx$ (number of sub-problems) $\times$ (work per sub-problem). Do not forget the second factor when a cell loops over many choices.
* Plain recursive Fibonacci makes $O(2^n)$ calls. With memoization: $O(n)$ time. Bottom-up with two variables: $O(1)$ space.
* A **subsequence** keeps the order but need not be contiguous. A **substring** must be contiguous.
* LCS: time and space $O(nm)$; traceback $O(n + m)$. On a tie, the lecture code takes from **above** (`|`).
* An LCS may not be unique. The tie rule decides which one the traceback finds.
* In the knapsack table, **rows are capacities** and **columns are objects**: `profit[r][c]`.
* The "take" option reads from the **previous column** ($c - 1$), not the same column. Reading the same column would let an object be taken twice.
* 0/1 knapsack in $O(nC)$ is **pseudo-polynomial**, not polynomial, because $C$ is a value, not an input size.
* Greedy by profit per unit weight does **not** solve 0/1 knapsack.
