2. Divide and conquer: mergesort

Facts

Name the three steps of divide and conquer, and say which step does the work in mergesort and in quicksort.

Answer

Divide the problem, conquer the sub-problems recursively, combine the answers. Mergesort divides trivially (split at the middle) and does the work in combine (merge). Quicksort does the work in divide (partition) and its combine is empty.

How many comparisons does merging two sorted lists with m elements in total need in the best and worst case?

Answer
  • Best: m/2, when every element of one list is smaller than every element of the other (the shorter side ends first; with equal lengths m/2).
  • Worst: m-1, when the two lists interleave, so one list is exhausted only at the very end.

Write the recurrence for the worst-case comparisons of mergesort and solve it for n=2^k.

Answer

W(n)=2W(n/2)+n-1 with W(1)=0. Solution: W(n)=n\lg n-n+1. Check n=2: 2-2+1=1 comparison.

Write the recurrence for the best-case comparisons of mergesort and solve it for n=2^k.

Answer

B(n)=2B(n/2)+n/2 with B(1)=0. Solution: B(n)=\frac{n}{2}\lg n. Check n=2: 1 comparison.

Time, space and stability of mergesort.

Answer

\Theta(n\log n) in best, average and worst case. O(n) extra space for the merge buffer, so it is not in-place. Stable, provided the merge takes from the left list when keys are equal (the usual merge). Careful: the lecture’s merge pseudocode takes one equal key from each half when the two heads are equal, which reorders equal keys when a half holds duplicates, e.g. [2_a,2_b,2_c]\to[2_a,2_c,2_b] (see AY21/22 S2 1(b) below).

How many levels does the mergesort recursion tree have, and what is the cost per level?

Answer

About \lceil\lg n\rceil+1 levels. Every level merges a total of n elements, so each level costs \Theta(n). Total \Theta(n\log n).

Find the maximum and minimum of n numbers with divide and conquer. How many comparisons?

Answer

Split into halves, find (max, min) of each, then compare the two maxima and the two minima. With base case of 2 elements (1 comparison), for n=2^k: T(n)=2T(n/2)+2, T(2)=1, so T(n)=\frac32 n-2. The naive method uses 2n-2.

Detect duplicates in an array of n keys. Give the method and its cost.

Answer

Sort, then compare each pair of neighbours: \Theta(n\log n) with a comparison sort. If keys are integers in a range of size O(n), use a counter array instead: \Theta(n).

Why does the merge step need a buffer? Can it be done in place?

Answer

Writing a merged element into the array may overwrite an element not yet read. A buffer holds one input list while merging back. In-place merging exists but is complicated and slower in practice, so the standard mergesort uses O(n) extra space.

Problems

Problem 1: counting comparisons exactly

(a) Mergesort on the array [5,2,4,7,1,3,2,6]. Write the merges in the order they happen, with the number of comparisons each makes.

Answer

The recursion splits to singletons, then merges bottom-up left to right.

Merge Result Comparisons
[5],[2] [2,5] 1
[4],[7] [4,7] 1
[2,5],[4,7] [2,4,5,7] 3
[1],[3] [1,3] 1
[2],[6] [2,6] 1
[1,3],[2,6] [1,2,3,6] 3
[2,4,5,7],[1,2,3,6] [1,2,2,3,4,5,6,7] 7

Total 17. For n=8 the worst case is 8\lg8-8+1=17, so this input is a worst case. Every merge uses its maximum m-1 comparisons: in each one, the two lists run out at almost the same time. In the last merge, 7 is the overall maximum, so the right list [1,2,3,6] is exhausted first only after 7 comparisons.

(b) Give a different array of 8 distinct numbers that needs only the best-case number of comparisons, and state that number.

Answer

Any sorted array, for example [1,2,3,4,5,6,7,8]. Every merge finishes the left list first, so each merge of size m uses m/2 comparisons. Total B(8)=\frac82\cdot3=12.

(c) Link to heapsort and quicksort: for which of the three sorts does the input order change the number of comparisons by more than a constant factor?

Answer

Only quicksort: its worst case is \Theta(n^2) and its best case is \Theta(n\log n). Mergesort differs by at most a factor of 2 between best \frac n2\lg n and worst n\lg n. Heapsort is \Theta(n\log n) for every input.

(d) Mergesort on a linked list: does the O(n) extra space requirement change? Does the time change?

Answer

Merging two linked lists needs no buffer, only pointer changes, so the extra space drops to O(1) for the merge (plus O(\log n) recursion stack). The time stays \Theta(n\log n). Finding the middle costs O(n) per level, which does not change the recurrence T(n)=2T(n/2)+\Theta(n).

Past-year questions

Questions from past papers (SC2001/CZ2101/CE2001). Every answer was worked out and checked by code; where a circulated official solution exists it was compared, and disagreements are flagged.

AY25/26 S2 1(a) Insertion Sort and Merge Sort (on n elements). A. Besides the input array, Insertion Sort needs an extra O(n) memory to store the sorted result. B. Insertion Sort has running time O(n^2) in the average case. C. If the input is almost sorted (only a few inversions), Insertion Sort is faster than Merge Sort. D. Insertion Sort has running time O(n\log n) in the best case. E. None of the above.

Answer

B and C.

  • A false: insertion sort is in place (O(1) extra).
  • B true: average \Theta(n^2). C true: \Theta(n+k) for k inversions beats \Theta(n\log n) when k is small.
  • D: the best case is \Theta(n). Read as an upper bound, O(n\log n) is technically still true, but the examiner means the tight bound, so treat D as false and expect it to be marked that way.
  • E false because B and C are true.

AY25/26 S2 1(b) Insertion Sort and Merge Sort. A. Both use a divide-and-conquer algorithm. B. One element can participate in n-1 merges in Merge Sort. C. Merge Sort has running time O(n\log n) in the worst case. D. Merge Sort has running time O(n\log n) in the average case. E. A stable sort preserves the relative order of equal elements; Merge Sort guarantees this.

Answer

C, D and E.

  • A false: insertion sort is incremental, not divide and conquer.
  • B false: an element takes part in exactly one merge per level of the recursion, so in \lceil\lg n\rceil merges, not n-1.
  • C and D true: \Theta(n\log n) in every case.
  • E true: the merge takes from the left list when keys are equal, so the sort is stable.

AY25/26 S1 1(b) Which statements about sorting algorithms are TRUE? A. Insertion Sort has best case O(n), average case O(n\log n), worst case O(n^2). B. If the array is mostly sorted except for a few elements, Insertion Sort provides the best performance. C. MergeSort’s worst-case time complexity is the same as its best-case time complexity. D. Heapsort has time complexity O(n) if the array is already sorted.

Answer

B and C.

  • A false: the average case of insertion sort is \Theta(n^2), not n\log n.
  • B true: time is \Theta(n+k) for k inversions, so a few misplaced elements give near-linear time.
  • C true: both are \Theta(n\log n) (best-case comparisons are half the worst case, still \Theta(n\log n)).
  • D false: building the heap is O(n) but the extraction phase is \Theta(n\log n) whatever the input.

AY24/25 S2 1(b) MergeSort (in-place version from the lecture). (i) For the input array A=[4,2,1,5,7,8], how many times is merge() called during sorting? (ii) Are the numbers of key comparisons the same for X=[3,2,1,6,5,4] and Y=[6,5,4,3,2,1]? Explain.

Answer

(i) 5. Every call of merge() reduces the number of sorted pieces by one. The sort starts with 6 single elements and ends with 1 sorted array, so merge() runs n-1=5 times, for any input order. Count by structure: each half of 3 needs 2 merges (a 2+1 split), plus 1 final merge: 2+2+1=5.

(ii) Yes, both need 7 comparisons. Split each array into two halves of 3.

  • X: sort [3,2,1]: split [3,2] and [1]. Merge [3] and [2]: 1 comparison, giving [2,3]. Merge [2,3] with [1]: 1 comparison (2>1, then the right list is empty). So 2. Sort [6,5,4] the same way: 2. Final merge [1,2,3] with [4,5,6]: the left list empties first, 3 comparisons. Total 2+2+3=7.
  • Y: the halves are [6,5,4] and [3,2,1]. Each costs 2 as above. The final merge of [4,5,6] with [1,2,3] empties the right list after 3 comparisons. Total 2+2+3=7.

In both arrays each half is a reversed triple and the two halves do not interleave, so the cost is the same.

Link (a surprise). Mergesort cost does not follow “sortedness”. Over all 720 permutations of 6 keys the cost ranges from 7 to 11, and 7 is the minimum, reached by both X and Y. With 6 keys the already sorted array costs 9, more than the reversed one (7), because the 3-key half splits as 2 + 1 and the left-heavy split favours a reversed input. For n a power of 2 sorted and reversed both give the best case \frac n2\lg n (12 comparisons for n=8). Code: verify/v_pyp_2425s2.py.

AY24/25 S1 1(b) Which statements about the time complexity of the InsertionSort algorithm (on n elements) are TRUE? A. Best case is O(n), average case is O(n\log n), and worst case is O(n^2). B. The worst-case time complexity ONLY occurs when the input array is sorted in reverse order. C. The best-case time complexity ONLY occurs when the input array is already sorted. D. As the average case is between the worst and the best, we can use the Squeeze Theorem to obtain the average-case time complexity. E. None of the above.

Answer

E (none).

  • A false: the average case is \Theta(n^2) (about n^2/4 inversions).
  • B false: the running time is \Theta(n+I) for I inversions, so any input with \Theta(n^2) inversions (not only the exact reverse) is \Theta(n^2).
  • C false for the same reason: any input with O(n) inversions (sorted except for a few elements) runs in \Theta(n).
  • D false: between the best case n and the worst case n^2 the average could be anything. The average case must be computed from the input distribution.

Caution: read literally with exact comparison counts and distinct keys, B and C hold (only strictly decreasing input hits the maximum). The word ONLY is the trap, and the examiner means the asymptotic classes, so E is the intended answer.

AY23/24 S2 1(b) Consider the in-place Merge Sort algorithm taught in the lecture. It consists of two steps: Step-1 split the input array into two subarrays; Step-2 merge two sorted subarrays into one sorted array. (i) If the two subarrays have n elements in total, how many key comparisons are required for Step-2 in the worst case? (ii) Let W(n) be the number of key comparisons for the worst case of Merge Sort. Define the recurrence of W(n), without solving it. (iii) How many key comparisons does Step-2 need in the best case? (iv) Define the recurrence of the best-case count B(n), without solving it.

Answer

(i) n-1. Each comparison puts one key into the output, and the last key needs no comparison. The worst case is when the two lists interleave, so neither empties until one key is left.

(ii) W(1)=0 and W(n)=W(\lfloor n/2\rfloor)+W(\lceil n/2\rceil)+n-1 for n\ge2. (For n=2^k: W(n)=2W(n/2)+n-1, which solves to n\lg n-n+1.)

(iii) \lfloor n/2\rfloor. The merge ends when one list runs out. In the best case all keys of the smaller list come first, so it costs exactly the size of the smaller list, \lfloor n/2\rfloor.

(iv) B(1)=0 and B(n)=B(\lfloor n/2\rfloor)+B(\lceil n/2\rceil)+\lfloor n/2\rfloor. (For n=2^k: B(n)=2B(n/2)+n/2, which solves to \frac n2\lg n.)

Check by brute force over all permutations of n=1..7: the maximum and minimum number of comparisons equal W(n)=0,1,3,5,8,11,14 and B(n)=0,1,2,4,5,7,9 (code, with the split \lfloor n/2\rfloor and \lceil n/2\rceil). Merging 4+4 keys costs between 4 and 7 comparisons, and 3+4 between 3 and 6.

Link. Both recurrences are master case 2: \Theta(n\lg n). The best case is a factor of 2 cheaper: \frac n2\lg n against n\lg n. So mergesort cannot be much faster on a “good” input, unlike insertion sort (n-1 against n^2/2).

AY23/24 S1 2(a) Show that the average-case time complexity of MergeSort running on N elements is O(N\lg N). (Hint: consider the worst and best cases first.)

Answer

Any input’s cost lies between the best-case and the worst-case cost, so the average cost, being a mean over inputs, also lies between them. If both ends are \Theta(N\lg N), the average is squeezed.

  • Worst case. Merging two sorted halves of total size n needs at most n-1 comparisons, so W(n)=2W(n/2)+n-1. This is master case 2 (a=b=2, f(n)=\Theta(n)), so W(n)=\Theta(n\lg n). For n=2^k it is exactly n\lg n-n+1.
  • Best case. The merge needs at least \lfloor n/2\rfloor comparisons (one list runs out first and the smaller list has \lfloor n/2\rfloor keys), so B(n)=2B(n/2)+n/2, again case 2, B(n)=\Theta(n\lg n). For n=2^k it is exactly \frac n2\lg n.
  • Squeeze. B(n)\le A(n)\le W(n), so \frac n2\lg n\le A(n)\le n\lg n-n+1, which means A(n)=\Theta(n\lg n) and in particular O(n\lg n). \blacksquare

(The upper bound is the only half the question needs: A(n)\le W(n)=O(n\lg n).)

Link. The average is closer to the worst case than to the best. Merging two random sorted lists of sizes a and b costs on average a+b-\frac a{b+1}-\frac b{a+1} comparisons (checked by brute force), so A(n)=2A(n/2)+n-2+\frac4{n+2}. That gives exactly 4.667 for n=4 and 15.733 for n=8 (also confirmed by trying all 8! inputs), between the bounds 12 and 17. Mergesort is oblivious: its cost varies only by a constant factor (about 2), unlike quicksort or insertion sort.

AY22/23 S2 1(b) Consider the in-place Merge Sort algorithm taught in the lecture. (i) Let W(n) denote the number of key comparisons required for the worst case of Merge Sort, where n is the input size. Define the recurrence equation of W(n), without solving it. (ii) Let B(n) denote the number of key comparisons for the best case. Define the recurrence equation of B(n), without solving it.

Answer

Merging two sorted halves of total size n costs at most n-1 comparisons (the two lists interleave) and at least \lfloor n/2\rfloor (all keys of the smaller list come first).

(i) W(1)=0 and W(n)=W(\lfloor n/2\rfloor)+W(\lceil n/2\rceil)+n-1 for n\ge2. For n=2^k it is W(n)=2W(n/2)+n-1, which solves to n\lg n-n+1.

(ii) B(1)=0 and B(n)=B(\lfloor n/2\rfloor)+B(\lceil n/2\rceil)+\lfloor n/2\rfloor for n\ge2. For n=2^k it is B(n)=2B(n/2)+n/2, which solves to \frac n2\lg n.

Brute force over all permutations for n=1..7 gives W=0,1,3,5,8,11,14 and B=0,1,2,4,5,7,9, equal to the recurrences (code).

Link. Both are master case 2, \Theta(n\lg n). See the AY2324 S2 answer (the same two parts) and the AY2324 S1 2(a) average-case squeeze: \frac n2\lg n\le A(n)\le n\lg n-n+1.

AY22/23 S1 1(b) Consider the input array A=[8,5,7,12,9,2] sorted by the in-place Merge Sort of the lecture. (i) The execution is visualised in Figure Q1b. Fill in all the missing parts (marked “__“) of the figure. (ii) Merge Sort has two steps: Step-1 split the array into two subarrays, Step-2 merge two sorted subarrays into one. If the two subarrays have n elements in total, how many key comparisons does Step-2 need in the worst case?

Answer

(i) The lecture code is

mergesort(n, m):  mid = (n+m)/2
    if m-n <= 0: return          // one element or empty
    else if m-n > 1: mergesort(n, mid); mergesort(mid+1, m)
    merge(n, m)                  // a 2-element array is merged directly

The label mergesort():k numbers the calls in the order they are made (call 1 is the whole array and the left half is always explored before the right half). The label merge()@k is the merge at the end of call k. A 2-element array makes no recursive calls (it is merged at once), but a 1-element array that is the right half of a 3-element array is still a call, so it gets a number.

call array merge()@ result of that merge
mergesort():1 8 5 7 12 9 2 @1 2 5 7 8 9 12
mergesort():2 8 5 7 @2 5 7 8
mergesort():3 8 5 @3 5 8
mergesort():4 7 (none) 7
mergesort():5 12 9 2 @5 2 9 12
mergesort():6 12 9 @6 9 12
mergesort():7 2 (none) 2

So the blanks are: left half mergesort():2 has children :3 (8, 5) and :4 (7); right half is mergesort():5 (12, 9, 2) with children :6 (12, 9) and :7 (2). The merges are @3 (gives 5 8), @2 (gives 5 7 8), @6 (gives 9 12), @5 (gives 2 9 12), @1 (gives 2 5 7 8 9 12). They execute in the order 3, 2, 6, 5, 1 (a merge runs after both its children finish). Both numberings agree with the circulated solution, and the table was reproduced by running the lecture code.

(ii) n-1. Each comparison moves one key into the output; the last key needs no comparison. The worst case is when the two sorted halves interleave so that neither empties early.

Link. Five merges for six keys again equals n-1: every merge reduces the number of sorted pieces by one. The numbering of merge()@k by the call that triggers it (not by time) is what lets you read a recursion tree: the merges happen bottom-up, but they are labelled top-down.

AY21/22 S2 1(b) A sorting algorithm is called stable if elements of equal keys remain their original order after being sorted by the algorithm. Decide if the Mergesort algorithm learnt in our lectures is stable. If your answer is yes, provide a brief justification. Otherwise, give a counter-example.

Answer

It depends on how the merge breaks a tie, and the lecture’s pseudocode, read literally, is not stable.

  • The usual merge (“if the left head is \le the right head, take the left one”) is stable: when keys are equal the left key, which came first in the input, goes out first, and the two halves keep their own order. A merge of two stable sorted halves is then stable, and so is the whole sort (induction on the recursion).
  • The lecture’s merge (slides 48 to 57) handles equal heads differently: “the 1st elements of the 2 halves are equal: the 1st element of the 1st half joins the end of the merged list, then the 1st element of the 2nd half also joins”. This puts one equal key from each half out together, so an equal key from the right half can overtake a second equal key still waiting in the left half.

Counter-example for the lecture’s merge. Label equal keys by their input order: A=[2_a,\,2_b,\,2_c]. The lecture’s recursion splits it into [2_a,2_b] and [2_c], and merging them gives: equal heads, so 2_a joins, then 2_c joins; the left half still holds 2_b, which is appended last. Result [2_a,2_c,2_b], not [2_a,2_b,2_c]. So the algorithm as written on the slides is not stable. (Checked by code: with three key values and arrays of length up to 6, the lecture’s merge reorders equal keys in 612 of 1089 input patterns, while the usual “take left on ties” merge never does.)

If every key value occurs at most once in each half, the lecture’s merge is stable (a pair of equal heads is taken left first), which is probably what the slides intend.

What to write. State which merge you mean. I would write: “No, as written on the lecture slides: counter-example [2_a,2_b,2_c]\to[2_a,2_c,2_b]. The standard merge that always takes from the left on ties is stable.” If your tutor’s mark scheme says “stable”, the second sentence covers it.

Link. Stability is a property of the tie rule, not of the divide-and-conquer shape. Radix sort needs a stable inner sort (Tutorial 3 Q2 and the links page, Problem 5), so it would be wrong to use the slide merge as the digit sort of a radix sort.

AY21/22 S1 1(b) (MCQ) Given n entries, the time complexity of the MergeSort algorithm is: A. Always O(n\log n). B. Always O(n^2). C. O(n\log n) only for the Best Case. D. O(n^2) only for the Best Case. E. O(n\log n) only for the Worst Case. F. O(n^2) only for the Worst Case.

Answer

A. Mergesort always splits into halves and merges, whatever the input order. The merge costs between \lfloor n/2\rfloor and n-1 comparisons, so best, average and worst case are all \Theta(n\log n) (master case 2).

AY20/21 S2 2(a) An input array [7,20,15,14,1,8,9,25] is given for MergeSort. After the array is recursively divided into the smallest subarrays, show the intermediate and output arrays by running the merge function step by step in the MergeSort algorithm. Show also the number of key comparisons in each step.

Answer

The lecture’s recursion mergesort(n,m) splits at mid=(n+m)/2, and a 2-element array is merged directly. The split tree is [7,20,15,14\,|\,1,8,9,25], then [7,20\,|\,15,14] and [1,8\,|\,9,25]. The merges run bottom-up, left subtree first:

step merge output comparisons
1 [7] with [20] [7,20] 1 (7\le20)
2 [15] with [14] [14,15] 1 (15>14)
3 [7,20] with [14,15] [7,14,15,20] 3 (7<14, 20>14, 20>15; then the right list is empty)
4 [1] with [8] [1,8] 1
5 [9] with [25] [9,25] 1

7 [7,14,15,20] with [1,8,9,25] [1,7,8,9,14,15,20,25] 7 (7>1, 7<8, 14>8, 14>9, 14<25, 15<25, 20<25)

AY19/20 S1 2(b) Consider an input array with integers in descending order. Mergesort is applied to sort it in ascending order. Is this input array a best case, intermediate case, or worst case of Mergesort when measured by the number of key comparisons? Briefly justify your answer.

Answer

Best case. In the lecture’s mergesort a merge of a left list L and a right list R needs at least \min(|L|,|R|) comparisons, and exactly that many when one whole list is output before the other starts. In a descending input every key of the left half is larger than every key of the right half, at every level of the recursion. So in each merge the right list is output completely first (each right key is compared once with the front of the left list and wins), then the rest of the left list is appended without comparisons. The cost is |R|=\lfloor\text{size}/2\rfloor, the minimum possible.

Example n=8, [8,7,6,5,4,3,2,1]:

step arrays after merging comparisons
1 [7,8]\ [5,6]\ [3,4]\ [1,2] 1+1+1+1 = 4
2 [5,6,7,8]\ [1,2,3,4] 2+2 = 4
3 [1,2,3,4,5,6,7,8] 4

Total 4+4+4=12=\frac n2\lg n, the best-case value (the worst case for n=8 is n\lg n-n+1=17).

For the lecture’s split (the left half gets the extra key when the size is odd) a descending input is the best case for every n: the cost equals B(n)=B(\lfloor n/2\rfloor)+B(\lceil n/2\rceil)+\lfloor n/2\rfloor for n=1..24 (code).

Link. An ascending input is also best for n=8 (12 comparisons) but not for odd sizes with this split: for n=6 it costs 9 against 7 for the descending input, and for n=7 it costs 11 against 9. In an ascending input the whole left half is output first, so each merge costs the size of the left half, which is the larger half when the size is odd. So “sorted input is the best case” is a habit from insertion sort, not a property of mergesort.

AY18/19 S1 3(b) Consider the following modification to MergeSort, called 3-way MergeSort. It divides the array into three subarrays (as equally-sized as possible), sorts them recursively, and then calls a 3-way merge function. The 3-way merge function combines three sorted subarrays into one sorted array in the following way. It merges the first two subarrays by calling the merge function in the original MergeSort. It then merges the resultant array with the third subarray, again by calling the original merge function. Given three equally-sized sorted subarrays with n elements in total as input, what is the worst-case number of key comparisons in the 3-way merge function? Briefly justify your answer.

Answer

\dfrac{5n}3-2 comparisons. The original merge of two sorted lists with a+b keys needs at most a+b-1 comparisons.

  • First merge: two subarrays of \frac n3 keys each, \frac{2n}3 keys in total: at most \frac{2n}3-1.
  • Second merge: the result (\frac{2n}3 keys) with the third subarray (\frac n3 keys), n keys in total: at most n-1.

Total worst case \Big(\dfrac{2n}3-1\Big)+(n-1)=\dfrac{5n}3-2. Both bounds can be reached together (the three arrays interleave perfectly), so it is exact: a brute force over all interleavings gives 8, 13, 18 for n=6,9,12, equal to \frac{5n}3-2.

Link. Merging three lists as two 2-way merges costs \frac53n per level, more than the n of an ideal 3-way merge; over \log_3n levels the total is \frac53n\log_3n=\frac{5}{3\lg3}\,n\lg n\approx1.05\,n\lg n against n\lg n for the ordinary 2-way sort. Dividing into more pieces does not help unless the merge looks at all heads at once (which needs a heap of heads).

AY17/18 S1 3(c) The union of two sets A and B is a set C such that an element x is in C if and only if x is in A or B. Note that, if x is in both A and B, then x will appear in the union C exactly once. Suppose that sets A and B are represented by two arrays, and both arrays have been sorted in ascending order. The sum of their sizes |A|+|B| is equal to n. Design an algorithm to compute the union of sets A and B in time O(n). Briefly describe your algorithm and analyse its worst-case time complexity.

Answer

Use the merge step of mergesort, but output an element that occurs in both arrays only once:

i = 0; j = 0
while i < |A| and j < |B|:
    if A[i] < B[j]:  output A[i]; i++
    else if A[i] > B[j]:  output B[j]; j++
    else:  output A[i]; i++; j++          // equal: output once, advance both
append the rest of A (if any), then the rest of B (if any)

Time. Every comparison outputs at least one element and advances at least one index, and each of the n keys is advanced past once, so there are at most n-1 comparisons plus O(n) copying for the remaining tail: O(n) in the worst case, for example A=[1,3,5], B=[2,4,6] (5 comparisons). The output is sorted and has no duplicates because the inputs are sorted sets. (Tested against a set union on 500 random pairs.)

(The circulated solution merges and then removes duplicates, also O(n) in total: n-1 comparisons plus n-1 for the duplicate scan.)

Link. The same two-pointer sweep gives the intersection (output only on equality) and the difference (output only from A). It is the merge of mergesort with the equal case redefined. Notice the equal case: advancing both pointers is safe here because the inputs are sets (no duplicates inside one array).

AY15/16 S1 3(a) In Mergesort algorithm, the merge function takes as input two sorted arrays of approximately equal sizes. However, the merge algorithm can also be used to merge two sorted arrays of very different sizes. Suppose two arrays, A and B, have sizes 3 and 1000 respectively, and both have been sorted in ascending order. Running the merge algorithm to merge A and B into one array in ascending order, what is the best-case number of comparisons and what is the worst-case number of comparisons between array elements? Justify your answer.

Answer

Merging |A|=3 and |B|=1000 keys: every comparison outputs one key, and the merge stops comparing when one array is exhausted.

  • Best case: 3 comparisons (=\min(|A|,|B|)): all three keys of A are smaller than B[0], for example A=[1,1,1] and B=[2,2,\dots,2]. Each comparison outputs one key of A and then A is empty; the 1000 keys of B are copied without comparisons.
  • Worst case: 1002 comparisons (=|A|+|B|-1): neither array runs out until the last key, which happens when the largest key belongs to A and the keys interleave, for example A=[0,500,2000] and B=[1,2,\dots,1000]: only the last key (2000) is output without a comparison. (Confirmed by running the merge: 1002.)

Link. The general range is \min(|A|,|B|) to |A|+|B|-1. For two equal halves (n/2 each) that is n/2 to n-1, the best and worst merges of mergesort; the very unequal case shows why you should merge the shorter array into the longer one by binary search when one side is tiny (3\lg1000\approx30 comparisons instead of 1002).

Tutorial 2 Q1. Maximum and minimum together in about 1.5n comparisons

Use the divide and conquer approach to design an algorithm that finds both the largest and the smallest elements in an array of n integers, assuming that n is a power of two, i.e., n = 2^k for some k \ge 0. Show that your algorithm does at most about 1.5n comparisons of the elements.

Answer: the algorithm 
void findMinMax(int[] ar, int start, int end, int[] minMax)
// minMax is an array of two integers to return the minimum
// and maximum found
{
    int tempMinMax1[] = new int[2];
    int tempMinMax2[] = new int[2];
    int mid;

    if (start == end) {              // one element array
        minMax[0] = ar[start];
        minMax[1] = ar[start];
    }
    else if (end - start == 1) {     // two element array
        if (ar[start] > ar[end]) {
            minMax[1] = ar[start];
            minMax[0] = ar[end];
        } else {
            minMax[0] = ar[start];
            minMax[1] = ar[end];
        }
    }
    else {                           // array longer than two elements
        mid = (start + end) / 2;

        findMinMax(ar, start, mid, tempMinMax1);
        findMinMax(ar, mid+1, end, tempMinMax2);

        if (tempMinMax1[0] < tempMinMax2[0])
            minMax[0] = tempMinMax1[0];
        else minMax[0] = tempMinMax2[0];

        if (tempMinMax1[1] > tempMinMax2[1])
            minMax[1] = tempMinMax1[1];
        else minMax[1] = tempMinMax2[1];
    }
}
  • One element: it is both the min and the max. No comparison.
  • Two elements: one comparison decides both the min and the max.
  • More: solve each half, then compare the two minimums and the two maximums: 2 comparisons.
Answer: the count

Let W_i be the number of comparisons for i elements. Then the recurrence is

W_1 = 0, \qquad W_2 = 1, \qquad W_n = W_{n/2} + W_{n - n/2} + 2.

If n = 2^k, where k is a positive integer, the two halves are equal:

W_n = 2W_{n/2} + 2.

Expand it:

\begin{aligned} W_n &= 2W_{n/2} + 2 \\ &= 2(2W_{n/2^2} + 2) + 2 = 2^2 W_{n/2^2} + 2^2 + 2 \\ &= 2^2(2W_{n/2^3} + 2) + 2^2 + 2 = 2^3 W_{n/2^3} + 2^3 + 2^2 + 2 \\ &\;\;\vdots \\ &= 2^{k-1} W_{n/2^{k-1}} + 2^{k-1} + 2^{k-2} + \dots + 2^2 + 2. \end{aligned}

Since n = 2^k, we get n/2^{k-1} = 2, and W_2 = 1. So

\begin{aligned} W_n &= 2^{k-1} + 2^{k-1} + 2^{k-2} + \dots + 2^2 + 2 \\ &= 2^{k-1} + 2\,(2^{k-2} + 2^{k-3} + \dots + 2 + 1) \\ &= 2^{k-1} + 2\,(2^{k-1} - 1) \qquad \text{(geometric series)} \\ &= 2^{k-1} + 2^k - 2 \\ &= \frac{n}{2} + n - 2 = \frac{3}{2}n - 2. \end{aligned}

General method: count the comparisons of a divide-and-conquer algorithm
  1. Read the base cases off the code, with their cost. Here: 1 element costs 0, 2 elements cost 1.
  2. Write the recurrence: (number of recursive calls) \times W(size of each) + (comparisons in the combine step).
  3. Expand it until the size reaches a base case. Count the expansions: from n = 2^k down to size 2 takes k - 1 halvings.
  4. Add up the combine costs, usually as a geometric series 1 + 2 + \dots + 2^j = 2^{j+1} - 1.

The saving here comes from the base case of 2: one comparison does the work of two. Compare it with the plain scan, which compares each element with both the current min and the current max: 2(n - 1) comparisons.

Extension 1.1. Remove the two-element base case from findMinMax, so the recursion stops only at one element. How many comparisons does it make for n = 2^k? What does this show?

Answer (Extension 1.1)

Now W_1 = 0 and W_n = 2W_{n/2} + 2. Expand all the way, k times:

W_n = 2^k W_1 + (2 + 4 + \dots + 2^k) = 0 + (2^{k+1} - 2) = 2n - 2.

That is no better than the plain scan. The \frac{3}{2}n result depends on the two-element base case. At the bottom level there are n/2 pairs. Without the base case, each pair costs 2 comparisons (min against min, max against max) instead of 1.

Tutorial 2 Q2. Tracing mergesort

Show how merge sort sorts each of the arrays below, and give the number of comparisons among array elements in each case.

  • 14 40 31 28 3 15 17 51
  • 23 23 23 23 23 23 23 23
Answer (first array)

The array is first divided into two equal parts. Each part is sorted by mergesort, which divides it again, until each part holds one item:

Level Parts
Split 1 [14 40 31 28] [3 15 17 51]
Split 2 [14 40] [31 28] [3 15] [17 51]
Split 3 [14] [40] [31] [28] [3] [15] [17] [51]

Then the parts are merged back:

Merge Result Comparisons
Each pair [14 40] [28 31] [3 15] [17 51] 4
Each pair of pairs [14 28 31 40] [3 15 17 51] 5
Final [3 14 15 17 28 31 40 51] 7

In total, 4 + 5 + 7 = 16 comparisons are made.

Where the 5 comes from: merging [14 40] with [28 31] compares 14:28, 40:28, 40:31, then the right list is empty (3). Merging [3 15] with [17 51] compares 3:17, 15:17, then the left list is empty (2).

Answer (second array)

The splits are the same as for the first array, down to eight single 23s. Then:

Merge Result Comparisons
Each pair [23 23] [23 23] [23 23] [23 23] 4
Each pair of pairs [23 23 23 23] [23 23 23 23] 4
Final [23 23 23 23 23 23 23 23] 4

In total, 4 + 4 + 4 = 12 comparisons.

Why only 4 at each level: with equal keys, a merge of m elements costs only m/2 comparisons. In the lecture’s in-place merge, one comparison of two equal keys places both of them (Case 3). In a buffer merge that takes from the left on a tie, the left list empties after m/2 comparisons. Either way, the count is the best case.

General method: count the comparisons of one merge

Each comparison sends one element to the output. The comparisons stop when one list is empty. So for two lists with m elements in total:

\text{comparisons} = m - (\text{elements still left in the other list}).

  • Most: m - 1, when the last two elements are in different lists (the lists interleave).
  • Fewest: the size of the smaller list, when all of it is smaller than all of the other list.

Trace mergesort bottom-up, level by level, and add one count per merge. Check the total against the bounds for n = 2^k: best \frac{n}{2}\lg n, worst n \lg n - n + 1.

Extension 2.1. Mergesort runs on the sorted array 1 2 3 4 5 6 7 8. How many comparisons does it make? Check the answer, and the two answers above, against the best and worst cases for n = 8.

Answer (Extension 2.1)

In every merge, the left list is entirely smaller, so it empties first. A merge of m elements costs m/2:

  • pairs: 4 \times 1 = 4;
  • pairs of pairs: 2 \times 2 = 4;
  • final: 4.

Total 12, the best case \frac{n}{2}\lg n = 4 \times 3 = 12.

The worst case is n \lg n - n + 1 = 24 - 8 + 1 = 17. So the three arrays give 12 (sorted), 12 (all equal) and 16 (first array). All lie between 12 and 17, as they must.

Tutorial 2 Q3. Finding duplicates

Suppose we have an unsorted array A of n elements, and we want to know if the array contains any duplicate elements.

  1. Outline (clearly) an efficient method for solving this problem.
Answer (a)

First, sort the array in increasing (or decreasing) order. Then scan the sorted array once and check for equal adjacent elements. After sorting, equal elements always sit next to each other.

Bool ExistDuplicate(int A[], int n) {
    MergeSort(A, n);   // or Heapsort
    for (int i = 1; i < n; i++) {
        if (A[i] == A[i-1])
            return true;
    }
    return false;
}
  1. What is the asymptotic order of the running time of your method in the worst case? Justify your answer.
Answer (b)

The worst-case time for sorting is \Theta(n \lg n), using mergesort (or heapsort). The time for the scan is \Theta(n). Therefore, the overall worst-case running time is \Theta(n \lg n).

Do not use quicksort here: its worst case is \Theta(n^2).

  1. Suppose we know the n elements are integers from the range 1, \dots, 2n, so other operations besides comparing keys may be done. Give an algorithm for the same problem that is specialized to use this information. Give the asymptotic order of the worst case running time for this solution. It should be of lower order than your solution for part (a).
Answer (c)

Count how many elements have each key value. Use an array of 2n counters, one for each possible value, and use the key value as the index.

  • We can quit as soon as any count becomes 2.
  • We scan the n-element array once, and each element takes constant time to count. So the overall worst-case running time is \Theta(n).
  • It uses \Theta(n) extra memory for the counters. Setting them all to 0 also costs \Theta(n).
General method: two ways to bring equal items together

Many problems ask whether two items are equal, or close, or related. Comparing every pair costs \Theta(n^2). Two faster ways:

  1. Sort, then scan neighbours. Related items end up next to each other. Cost: \Theta(n \log n) with mergesort or heapsort, plus \Theta(n) for the scan. This needs only comparisons.
  2. Use the key as an index. If the keys are integers in a range of size R, an array of R counters answers in \Theta(n + R) time and \Theta(R) memory. This beats sorting only when R is O(n), or at least o(n \log n).

Extension 3.1. An unsorted array holds n integers. Decide whether two of them add up to a given number x. Use only comparisons and additions. Aim for O(n \log n).

Answer (Extension 3.1)

Sort the array with mergesort: \Theta(n \log n). Then scan from both ends:

i = 0; j = n - 1;
while (i < j) {
    if (A[i] + A[j] == x) return true;
    else if (A[i] + A[j] < x) i++;   // need a bigger sum
    else j--;                        // need a smaller sum
}
return false;

Each step moves i or j by one, so the scan is \Theta(n). Total: \Theta(n \log n). It is the “sort, then scan” method: after sorting, the scan never needs to look back.

Extension 3.2. The n integers now come from the range 1, \dots, n^2. Is the counter method from (c) still better than sorting?

Answer (Extension 3.2)

No. The counter array now needs R = n^2 entries. Setting them to 0 alone costs \Theta(n^2) time, and they take \Theta(n^2) memory. Sorting and scanning costs \Theta(n \log n), which is better. The counter method pays off only when the range R is small compared with n \log n.
