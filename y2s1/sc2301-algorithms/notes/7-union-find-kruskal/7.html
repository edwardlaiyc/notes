The Disjoint-Set (Union-Find) data structure maintains dynamic partitions of a universe of elements into disjoint equivalence classes under ongoing union operations and connectivity queries. It serves as the algorithmic engine for Kruskal’s Algorithm, which constructs Minimum Spanning Trees by greedily processing edges in globally increasing weight order.

This chapter traces the evolutionary refinement of Union-Find—from naive QuickFind to optimal Weighted QuickUnion with Path Compression (WQUPC)—and applies it to Kruskal’s MST algorithm, cycle detection, and linear-time edge sorting optimizations.

1. Dynamic Connectivity and the Union-Find Interface

Dynamic connectivity manages NN elements {0,1,…,N−1}\{0, 1, \dots, N - 1\} partitioned into disjoint connected components under two primary operations:

flowchart LR
    Op["Disjoint-Set Interface"] --> F["find(p): Return canonical component identifier for p"]
    Op --> U["union(p, q): Merge component containing p with component containing q"]
    Op --> C["connected(p, q): Evaluate whether find(p) == find(q)"]

2. Progressive Evolution of Union-Find

All variants maintain an integer array id[] of size NN, but differ fundamentally in how component membership is encoded:

flowchart TD
    QF["1. QuickFind<br/>id[p] = Component ID<br/>find: O(1), union: O(N)"] --> QU["2. QuickUnion<br/>id[p] = Parent Node<br/>find: O(N), union: O(N)"]
    QU --> WQU["3. Weighted QuickUnion<br/>Small tree under large tree<br/>find: O(log N), union: O(log N)"]
    WQU --> WQUPC["4. WQU with Path Compression<br/>Flatten tree on find<br/>Nearly linear: O(alpha(N))"]

1. QuickFind (Eager Approach)

  • id[p] stores the component ID of pp.
  • find(p) returns id[p] in Θ(1)\Theta(1) time.
  • union(p, q) scans the entire array to replace all occurrences of id[p] with id[q], taking Θ(N)\Theta(N) time.
  • A sequence of NN unions costs Θ(N2)\Theta(N^2), which does not scale.

2. QuickUnion (Lazy Approach)

  • id[p] points to the parent of pp. Elements form rooted trees where id[root] == root.
  • find(p) chases parent pointers to the root.
  • union(p, q) sets id[find(p)] = find(q) in O(1)O(1) pointer operations after root lookups.
  • Flaw: Trees can degenerate into linear chains of height NN, degrading find to Θ(N)\Theta(N).

3. Weighted QuickUnion

To prevent tall trees, track subtree sizes in sz[]. Always attach the smaller tree beneath the root of the larger tree:

void unionElements(int p, int q) {
    int rootP = find(p);
    int rootQ = find(q);
    if (rootP == rootQ) return;

    if (sz[rootP] < sz[rootQ]) {
        id[rootP] = rootQ;
        sz[rootQ] += sz[rootP];
    } else { // sz[rootP] >= sz[rootQ] (Tie: rootQ under rootP)
        id[rootQ] = rootP;
        sz[rootP] += sz[rootQ];
    }
}

Step-by-Step Method: Proving Depth Bound ≤lg⁡N\le \lg N for Weighted QuickUnion

  1. Condition for Depth Increase: The depth of an arbitrary node xx increases by exactly 1 if and only if its containing tree TxT_x is merged under another tree TyT_y during unionElements(x, y).
  2. Size Doubling Rule: By the weighting rule, TxT_x is attached under TyT_y only when |Ty|≥|Tx||T_y| \ge |T_x|. Consequently, the size of the new merged tree containing xx satisfies: |Tnew|=|Tx|+|Ty|≥|Tx|+|Tx|=2|Tx||T_{\text{new}}| = |T_x| + |T_y| \ge |T_x| + |T_x| = 2|T_x|
  3. Logarithmic Bound:
    • Node xx starts in a tree of size 1 at depth 0.
    • Every time the depth of xx increases by 1, the size of its containing tree at least doubles.
    • Since the maximum possible tree size is NN, the size can double at most ⌊lg⁡N⌋\lfloor \lg N \rfloor times.
    • Therefore, depth(x)≤lg⁡N\text{depth}(x) \le \lg N for all nodes, ensuring find and union execute in O(log⁡N)O(\log N) worst-case time.

4. Path Compression (WQUPC)

When executing find(p), attach every traversed node directly to the canonical root. In two-pass recursion or one-pass loop (path halving):

int find(int p) {
    while (p != id[p]) {
        id[p] = id[id[p]];                 // Path halving: point to grandparent
        p = id[p];
    }
    return p;
}

3. Kruskal’s Minimum Spanning Tree Algorithm

Kruskal’s algorithm constructs an MST by processing edges in globally increasing weight order across a forest of components:

vector<Edge> Kruskal(Graph& G, int V) {
    vector<Edge> MST;
    sort(G.edges.begin(), G.edges.end());   // Sort edges ascending by weight

    DisjointSet ds(V);                     // Initialize |V| isolated components

    for (const Edge& e : G.edges) {
        if (!ds.connected(e.u, e.v)) {     // If e does not close a cycle
            ds.unionElements(e.u, e.v);
            MST.push_back(e);
            if (MST.size() == V - 1)       // Spanning tree complete
                break;
        }
    }
    return MST;
}

Operational Invariants of Kruskal

  1. Component Invariant: Prior to processing, the graph contains |V||V| isolated components. Every accepted edge merges two disjoint components, decreasing the component count by exactly 1.
  2. Termination: Kruskal terminates immediately upon accepting |V|−1|V| - 1 edges. Remaining edges are never evaluated.
  3. Time Complexity:
    • Edge Sorting: O(|E|log⁡|E|)=O(|E|log⁡|V|)O(|E| \log |E|) = O(|E| \log |V|).
    • Union-Find Operations: ≤2|E|\le 2|E| calls to find and |V|−1|V| - 1 calls to union, costing O(|E|α(|V|))O(|E| \alpha(|V|)).
    • Total Time: 𝑶(|𝑬|𝒍𝒐𝒈⁡|𝑽|)\mathbf{O(|E| \log |V|)}, dominated entirely by edge sorting.

Tutorial 6 Q3: Cycle Detection in Undirected Graphs via Disjoint Sets

Question: Design an algorithm using a disjoint-set data structure to determine whether an undirected graph G=(V,E)G = (V, E) contains a cycle. Analyze its time and space complexity.

Solution:

  • Algorithm Design:

    bool HasCycleUndirected(int V, const vector<pair<int, int>>& edges) {
    DisjointSet ds(V);

    for (auto [u, v] : edges) {
        int rootU = ds.find(u);
        int rootV = ds.find(v);

        if (rootU == rootV) {
            return true;                 // Cycle detected: u and v already in same component
        }
        ds.unionElements(rootU, rootV);
    }
    return false;                        // Graph is a forest (acyclic)
}

  • Complexity Analysis:

    • Time Complexity: For |E||E| edges, the algorithm performs at most 2|E|2|E| find operations and |V|−1|V| - 1 union operations. With WQUPC, this executes in O(|V|+|E|α(|V|))O(|V| + |E| \alpha(|V|)) time, which is practically linear.
    • Space Complexity: O(|V|)O(|V|) for id[] and sz[] arrays.
Tutorial 6 Q4: Improving Kruskal’s Runtime with Bounded Integer Weights

Question: Can we improve the asymptotic running time of Kruskal’s algorithm if edge weights are known to be integers in the range {1,2,…,|V|}\{1, 2, \dots, |V|\}? Justify your answer.

Solution:

  • Yes, we can optimize Kruskal to nearly linear time.
    1. Standard Kruskal requires O(|E|log⁡|E|)O(|E| \log |E|) because comparison sorts (e.g. Heapsort, Mergesort) must obey the Ω(|E|log⁡|E|)\Omega(|E| \log |E|) lower bound.
    2. If all edge weights are integers in the range [1..|V|][1..|V|], we can replace comparison sort with Counting Sort (or Bucket Sort).
    3. Counting Sort sorts |E||E| edges with keys in range [1..|V|][1..|V|] in: Θ(|E|+|V|) time.\Theta(|E| + |V|) \text{ time}.
    4. Subsequent cycle checking via WQUPC requires O(|E|α(|V|))O(|E| \alpha(|V|)) time.
    5. Total Running Time: O(|E|+|V|)+O(|E|α(|V|))=𝑶(|𝑬|𝜶(|𝑽|)+|𝑽|).O(|E| + |V|) + O(|E| \alpha(|V|)) = \mathbf{O(|E| \alpha(|V|) + |V|)}. This achieves a near-linear runtime, directly outperforming Prim’s with binary heaps (O(|E|log⁡|V|)O(|E| \log |V|)).
