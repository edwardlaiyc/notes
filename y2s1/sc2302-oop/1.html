Object State, Memory Lifecycle & Encapsulation

1. Definitions Reference

  • Class: A blueprint defining attributes (state) and operations (behaviour) common to all objects of that type.
  • Object: A concrete instance of a class allocated on the heap, defined by identity, state, and behaviour.
  • State: The collective current values stored within an object’s instance fields at a given point in execution.
  • Behaviour: The set of actions an object can perform, implemented via instance methods.
  • Message: A method invocation dispatched to a receiving object reference.
  • Encapsulation: Bundling state variables and the methods operating on them within a single class boundary.
  • Information Hiding: Restricting direct external access to internal data representations using private modifiers, exposing operations solely via public methods.
  • Association: A general relationship where independent objects interact, with no ownership implied.
  • Aggregation: A weak “has-a” whole-part relationship where parts can exist independently of the whole lifecycle (e.g., School and Professor).
  • Composition: A strong “has-a” whole-part relationship where parts cannot exist outside the owning object’s lifecycle (e.g., House and Rooms).

2. Object Lifecycle & Step-by-Step Initialization Formula

The 5-Step Object Creation Algorithm

When new SubClass(...) executes, the JVM follows this exact deterministic trace:

  1. Step 1 (Heap Zeroing): Allocate memory on the heap. Clear all fields across the entire inheritance hierarchy to default binary values (0, 0.0, false, null).
  2. Step 2 (Constructor Routing): Subclass constructor delegates to super(...) or this(...) on line 1. Chaining recurses upward until java.lang.Object is reached.
  3. Step 3 (Superclass Initializers & Body): In textual order, superclass explicit field initializers run, followed by the superclass constructor body.
  4. Step 4 (Subclass Initializers): Subclass explicit field initializers and instance initializer blocks execute in textual order.
  5. Step 5 (Subclass Body): Subclass constructor body finishes execution.

Diagnostic Rules & Edge Case Checks

  • Constructor Line-1 Mutual Exclusion Rule: A constructor cannot contain both super(...) and this(...). Both calls demand placement on the absolute first statement of the constructor body. Whichever call appears on line 2 triggers a compile-time error in that constructor.
  • Overridable Method in Constructor Trap: If a superclass constructor invokes an overridden instance method, dynamic dispatch executes the subclass implementation during Step 3. Because Step 4 has not yet run, the subclass method reads default-zeroed field values, not initialized ones.
  • Field Hiding Resolution Formula: Fields do not participate in polymorphism. For an expression ref.field, resolve field using only the declared static reference type of ref, regardless of the runtime heap object.
  • Variable Initialization Rule:
    • Instance / Static fields: Automatically initialized to default values during allocation.
    • Local variables: Must be explicitly assigned before use; accessing uninitialized local variables produces a compile-time error.
  • No Destructors: Java does not feature destructors; finalization is handled via a finalizer (finalize()) scheduled by the garbage collector.

3. Reference Identity, String Pool & Defensive Guarding

Equality Decision Steps

To evaluate a == b vs a.equals(b):

  1. == Operator: Check memory addresses. Evaluates to true if and only if both operands point to the exact same memory address on the heap.
  2. .equals() Method: Checks logical equivalence if overridden by the class; defaults to reference equality (==) if not overridden.

String Pool Evaluation Matrix

  • String s1 = "Java"; String s2 = "Java"; -> s1 == s2 is true (interned literal reuse).
  • String s3 = new String("Java"); -> s1 == s3 is false (forces distinct heap allocation).
  • s1.equals(s3) is true (compares character contents).

Defensive Copying Checklist (Preventing State Leaks)

  • Rule 1 (Ingestion): Never assign an incoming mutable object or array parameter directly to a private field. Allocate a new instance and copy elements.
  • Rule 2 (Exposure): Never return a direct reference to an internal mutable field or array from a getter method. Return a newly cloned copy.

4. Canonical Class Template Checklist

When constructing a complete entity class from an exam specification or UML diagram, implement elements in this order:

  1. Constants: public static final constants at the top.
  2. Static Variables: Class-level shared state marked private static.
  3. Instance Variables: Encapsulated state marked private.
  4. Constructors: Standard overloaded constructors (using this(...) chaining to avoid duplicate logic) and defensive copy constructors.
  5. Accessors & Mutators: Standard get...() and set...() methods maintaining class validation invariants.
  6. Business Logic Methods: State computations returning values (e.g., area(), findTotal()).
  7. Display / Utility Methods: State printers (e.g., printDetails(), toString()).
public class AccountRecord {
    // 1. Class constant
    public static final double MAX_LIMIT = 5000.0;
    
    // 2. Class shared variable
    private static int activeCount = 0;

    // 3. Encapsulated instance fields
    private String holder;
    private double balance;
    private int[] scores; // mutable array reference

    // 4. Primary Constructor with parameter validation and defensive ingestion
    public AccountRecord(String holder, double balance, int[] inputScores) {
        this.holder = (holder != null) ? holder : "Anonymous";
        this.balance = (balance >= 0 && balance <= MAX_LIMIT) ? balance : 0.0;

        // Defensive copy on ingestion
        if (inputScores != null) {
            this.scores = new int[inputScores.length];
            System.arraycopy(inputScores, 0, this.scores, 0, inputScores.length);
        } else {
            this.scores = new int[0];
        }
        activeCount++;
    }

    // Constructor Chaining (must be first statement)
    public AccountRecord(String holder) {
        this(holder, 0.0, null);
    }

    // Copy Constructor: deep clone
    public AccountRecord(AccountRecord other) {
        this(other.holder, other.balance, other.scores);
    }

    // 5. Accessors and Mutators
    public String getHolder() { return holder; }
    public double getBalance() { return balance; }
    
    public void setBalance(double balance) {
        if (balance >= 0 && balance <= MAX_LIMIT) {
            this.balance = balance;
        }
    }

    // Defensive copy on retrieval
    public int[] getScores() {
        int[] copy = new int[this.scores.length];
        System.arraycopy(this.scores, 0, copy, 0, this.scores.length);
        return copy;
    }

    public static int getActiveCount() {
        return activeCount;
    }
}
// Traps: Parameter Shadowing, Constructor Dispatch & Field Hiding
class SuperNode {
    int value = 100;

    SuperNode() {
        // Polymorphic call during Step 3
        init();
    }

    void init() {
        System.out.println("SuperNode init() value: " + value);
    }
}

class SubNode extends SuperNode {
    int value = 200; // Hides SuperNode.value

    SubNode(int value) {
        // Implicit super() runs first
        // Shadowing trap resolved using this
        this.value = value;
    }

    // Constructor mutual exclusion trap demonstration:
    // SubNode() {
    //     super();
    //     this(10); // COMPILE-TIME ERROR: Call to 'this()' must be first statement in constructor
    // }

    @Override
    void init() {
        // Runs before Step 4 sets value = 200
        System.out.println("SubNode init() value: " + value);
    }
}

// Execution trace demonstration:
// SuperNode constructor runs -> calls SubNode.init() -> value is 0 (heap-zeroed default)
// Then SubNode explicit init sets value to 200 -> then SubNode constructor sets value to 50
SuperNode ref = new SubNode(50); // Prints: "SubNode init() value: 0"
System.out.println("ref.value: " + ref.value); // Prints: 100 (resolved via declared type SuperNode)
// Interactive Application Driver Shell Template (Exam I/O Pattern)
import java.util.Scanner;

public class InteractiveAppDriver {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int choice;
        
        do {
            System.out.println("==== Menu Options ====");
            System.out.println("1. Perform Action A");
            System.out.println("2. Perform Action B");
            System.out.println("3. Quit");
            System.out.print("Choose option (1-3): ");
            
            choice = sc.nextInt();
            sc.nextLine(); // Mandatory buffer flush
            
            switch (choice) {
                case 1:
                    System.out.print("Enter item name: ");
                    String name = sc.nextLine();
                    System.out.println("Processing " + name);
                    break;
                case 2:
                    System.out.println("Executing Action B");
                    break;
                case 3:
                    System.out.println("Exiting application.");
                    break;
                default:
                    System.out.println("Invalid option. Please try again.");
            }
        } while (choice != 3);
        
        sc.close();
    }
}
