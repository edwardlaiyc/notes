Procedural programming structures software as a sequence of procedural calls executing operations on passive data stored in global or shared variables. As applications grow in complexity, unbound data access introduces severe coupling: any routine can corrupt shared state, making code difficult to maintain, verify, and scale.

Object-Oriented Programming (OOP) addresses this fragility by binding data and the operations that mutate that data into self-contained units called objects. Objects communicate exclusively by sending messages (invoking methods), ensuring that internal representation remains shielded from external interference.

1. Procedural vs. Object-Oriented Paradigm

Architectural Dimension Procedural Paradigm (e.g., C) Object-Oriented Paradigm (e.g., Java)
Fundamental Building Block Functions / Procedures Classes and Objects
Data Organization Separated from operations; exposed globally or passed via pointers Encapsulated inside objects; manipulated strictly via member methods
Program Execution Sequential, top-down procedure execution Network of collaborating objects passing messages
Access Control Limited; file-scope static or global Strict access specifiers (private, protected, package-private, public)
Source File Structure Flexible naming A public class Foo must reside in Foo.java

How Java Executes Object-Oriented Code

Java compiles source code (.java) via javac into architecture-neutral bytecode (.class). The Java Virtual Machine (JVM) interprets or Just-In-Time (JIT) compiles this bytecode into native machine instructions on the host platform (“write once, run anywhere”). Java manages memory automatically through an internal garbage collector, disallowing explicit pointer arithmetic and multiple inheritance of state to prevent memory corruption and ambiguity.

2. Core OO Foundations: State, Behaviour, and Identity

Every object possesses three fundamental characteristics:

  1. State: The current values of an object’s internal fields (attributes). State persists across method invocations and can change over time.
  2. Behaviour: What the object can perform in response to messages (its methods). A method invocation may read or modify internal state.
  3. Identity: The unique handle that distinguishes an object from every other object in runtime memory, even if two objects hold completely identical state. In Java, identity corresponds to distinct heap memory locations and unique Object Identifiers (OID).

The Four Pillar Concepts of OOP

                   ┌─────────────────────────────────────────┐
                   │       Object-Oriented Programming       │
                   └────────────────────┬────────────────────┘
          ┌──────────────────┬──────────┴──────────┬──────────────────┐
          ▼                  ▼                     ▼                  ▼
    Abstraction        Encapsulation          Inheritance        Polymorphism
 (Essential models)  (Information hiding)   (Code reuse / is-a) (Dynamic dispatch)
  • Abstraction: Selecting and exposing only the essential characteristics and behaviours relevant to a particular system perspective while filtering out non-essential background details. A Student class within a university portal models matriculation numbers and transcripts, ignoring medical histories or shoe sizes.
  • Encapsulation: Packaging state variables and related operations into a single class boundary, complemented by information hiding—declaring attributes private and exposing only a strictly curated public interface (API) of accessors and mutators.
  • Inheritance: Establishing an “is-a” taxonomy where specialized subclasses inherit fields and methods from generalized superclasses. (Detailed in Chapter 2).
  • Polymorphism: Enabling entities with different underlying implementations to respond to identical method signatures through uniform interfaces. (Detailed in Chapter 4).

Contrast: Encapsulation vs. Information Hiding

Exams routinely test the distinction between these two interrelated concepts:

  • Encapsulation is the structural mechanism of bundling data variables together with the methods that operate upon them into a unified class boundary.
  • Information Hiding is the design principle of deliberately concealing implementation details behind an abstract interface, preventing external components from depending on volatile internal data layouts.

3. Class Structure: Anatomy and Lifecycle

A class serves as the compile-time blueprint or template; an object is a dynamic, concrete instance allocated on the heap at runtime.

public class BankAccount {
    // 1. Class constant: shared across all instances, immutable
    public static final double MIN_BALANCE = 50.0;

    // 2. Class (static) variable: exactly one shared memory cell across all instances
    private static int totalAccounts = 0;

    // 3. Instance variables: allocated per object instance on the heap
    private final String accountNumber;
    private double balance;

    // 4. Overloaded Constructors: initialize state during heap allocation
    public BankAccount(String accountNumber) {
        this(accountNumber, MIN_BALANCE); // Constructor delegation
    }

    public BankAccount(String accountNumber, double initialBalance) {
        this.accountNumber = accountNumber;
        this.balance = Math.max(initialBalance, MIN_BALANCE);
        totalAccounts++;
    }

    // 5. Accessor (getter) and Mutator (setter) enforcing invariants
    public double getBalance() { return balance; }

    public void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    // 6. Class (static) method: operates without requiring an instance
    public static int getTotalAccounts() {
        return totalAccounts;
    }
}

Variable Classifications and Scope

Variable Type Memory Location Lifetime Default Initialization Access via this?
Instance Variable Heap (inside the object) From object allocation until garbage collection Yes (0, 0.0, false, null) Yes
Class (static) Variable Method Area / Metaspace Entire application runtime Yes (0, 0.0, false, null) No (accessed via ClassName.var)
Local Variable Call Stack (inside method frame) Duration of enclosing method or block No (Compile error if read before initialization) No

[!WARNING] Static Scope Limitations: Static methods execute in a class-wide context without an active this reference. A static method cannot directly reference instance variables or call non-static methods without explicitly instantiating an object.

4. Object Creation and Memory Allocation

Executing BankAccount acc = new BankAccount("A101", 500.0); triggers a multi-stage allocation process:

  1. Class Loading: The JVM checks if BankAccount bytecode is loaded into Metaspace. If not, the class loader resolves and initializes static fields.
  2. Heap Memory Allocation: Space sufficient to hold all instance variables (including inherited variables) is carved out on the heap.
  3. Zero-Initialization: The JVM clears the allocated memory block, zero-filling every field (0, 0.0, false, null).
  4. Constructor Execution: The constructor body runs, executing explicit field initializers in declaration order before executing the constructor body statements.
  5. Reference Assignment: The memory address of the newly allocated heap block is returned and stored in the stack reference variable acc.

Reference Semantics vs. Value Semantics

  • Primitives (int, double, boolean): Store the literal value directly in the variable’s memory cell. Assignment (b = a) copies the raw bits.
  • Objects (String, BankAccount, arrays): The variable holds a reference (pointer/address) to the object residing on the heap. Assignment (ref2 = ref1) copies the address, not the object payload. Both variables subsequently reference the identical heap object (aliasing).
BankAccount b1 = new BankAccount("A1", 100.0);
BankAccount b2 = b1;        // Copies address: b1 and b2 alias the exact same object
b2.deposit(50.0);
System.out.println(b1.getBalance()); // Prints 150.0

5. Equality: Identity (==) vs. Equivalence (equals)

In Java, checking equality between two reference variables depends critically on whether you evaluate identity or state:

  • Reference Comparison (==): Compares heap memory addresses. Returns true if and only if both operands point to the exact same memory location.
  • Content Comparison (.equals()): Evaluates logical equivalence of state. The default implementation inherited from java.lang.Object performs reference equality (==). Classes intended for value-based comparison (such as String, Integer, LocalDate) override .equals() to compare encapsulated state attributes.

6. String Handling and the String Constant Pool

String is an immutable reference type in java.lang. Because strings are frequently reused, the JVM maintains an internal cache in heap memory called the String Constant Pool:

String s1 = "Java";               // Allocated in String Pool
String s2 = "Java";               // Reuses existing "Java" from String Pool
String s3 = new String("Java");   // Forces allocation of a distinct new heap object

System.out.println(s1 == s2);      // true  (identical pool reference)
System.out.println(s1 == s3);      // false (distinct heap objects)
System.out.println(s1.equals(s3)); // true  (identical character sequences)
Stack                     Heap Memory
──────                    ─────────────────────────────────────────
[ s1 ] ───────────────┐
                      ├──► [ "Java" ] (Inside String Constant Pool)
[ s2 ] ───────────────┘
                                ▲
[ s3 ] ──► [ String Object ] ───┘ (Distinct object pointing to pooled char array)

Consequences of String Immutability

  1. Any operation that appears to mutate a string (e.g., s.toUpperCase(), s.concat("!"), s.replace(...)) leaves the original object unmodified and allocates a brand-new String object.
  2. String concatenation evaluation proceeds strictly left-to-right:
    • "A" + 1 + 2 ⟹\implies "A1" + 2 ⟹\implies "A12"
    • 1 + 2 + "A" ⟹\implies 3 + "A" ⟹\implies "3A"

7. Defensive Copying: Preventing Encapsulation Leaks

Declaring reference fields private does not guarantee encapsulation if mutable references cross the class boundary via constructors or accessors:

// VULNERABLE: Leaks internal mutable reference
public class Schedule {
    private int[] examDates;

    public Schedule(int[] dates) {
        this.examDates = dates; // Escaping reference! Caller holds reference to internal array
    }
    public int[] getExamDates() {
        return examDates;       // Leaks internal array directly to callers
    }
}

The Defensive Copy Solution: Always clone or create fresh copies of mutable objects on both ingress (constructors/setters) and egress (getters):

// SECURE: Fully encapsulated
public Schedule(int[] dates) {
    this.examDates = dates.clone();
}
public int[] getExamDates() {
    return examDates.clone();
}

8. Tracing Toolkit: Reference Aliasing and Identity

When tracing reference assignments in exam code snippets, apply this deterministic 3-step checklist:

  1. Identify Variable Types: Separate primitive variables (direct bit storage) from reference variables (heap pointers).
  2. Track Assignment Chains:
    • refB = refA copies the pointer. Draw an arrow from refB pointing to refA’s heap box.
    • Any state mutation refB.setX(...) immediately reflects across all alias variables (refA.getX()).
    • Reassigning refA = new Foo() breaks that specific reference pointer; other aliases continue pointing to the previous heap object.
  3. Check Method Argument Passing: Java is strictly pass-by-value. Passing an object reference copies the address into the method’s local parameter. Mutating fields through that parameter mutates the original object; reassigning the parameter variable itself inside the method has zero effect on the caller’s reference.

Wooclap Check: Object Reference Aliasing and Field Mutation

Question: What is the exact terminal output of the following Java program?

class Box {
    int volume;
}

public class TestBox {
    public static void main(String[] args) {
        Box b1 = new Box();
        Box b2 = new Box();
        Box b3 = b1;
        b1.volume = 10;
        b2.volume = 20;
        b3.volume = 30;
        b2 = b3;
        b2.volume = 40;
        System.out.println(b1.volume + " " + b2.volume + " " + b3.volume);
    }
}

Solution: Trace the references step by step:

  1. Box b1 = new Box(); ⟹\implies Heap Object 1 created. b1 →\to Obj1 (volume = 0).
  2. Box b2 = new Box(); ⟹\implies Heap Object 2 created. b2 →\to Obj2 (volume = 0).
  3. Box b3 = b1; ⟹\implies b3 aliases Obj1.
  4. b1.volume = 10; ⟹\implies Obj1 volume becomes 10.
  5. b2.volume = 20; ⟹\implies Obj2 volume becomes 20.
  6. b3.volume = 30; ⟹\implies Obj1 volume becomes 30.
  7. b2 = b3; ⟹\implies b2 now points to Obj1. (Obj2 becomes unreferenced garbage).
  8. b2.volume = 40; ⟹\implies Obj1 volume becomes 40.
  9. b1, b2, and b3 all reference Obj1.

Final Output:

40 40 40
Wooclap Check: String Immutability and Primitive Evaluation

Question: What is the exact terminal output printed by the following code segment?

int i = 10;
int j = i;
String str = "Java";
String str2 = str;
i = 1003;
str = "I love Java";
System.out.println(str2 + j);

Solution:

  1. i = 10; j = i; ⟹\implies j receives a copy of the primitive value 10. Subsequent mutation of i = 1003 does not alter j.
  2. str = "Java"; str2 = str; ⟹\implies str and str2 point to "Java" in the String Constant Pool.
  3. str = "I love Java"; ⟹\implies Because Strings are immutable, a new String "I love Java" is allocated in the pool. str is updated to point to the new string.
  4. str2 continues to point to the original "Java" string.
  5. str2 + j performs string concatenation: "Java" + 10 ⟹\implies "Java10".

Final Output:

Java10
Wooclap Check: String Indexing and Method Evaluation

Question: Determine the output of the following program:

public class StringDemo {
    public static void main(String args[]) {
        char chars[] = {'J', 'O', 'V'};
        String s = new String(chars);
        String s1 = "12345";
        char c = s1.charAt(2);
        int len1 = s.length();
        System.out.println(c + " " + len1);
    }
}

Solution:

  1. s1 = "12345". Indices start at 0: s1.charAt(0) = '1', s1.charAt(1) = '2', s1.charAt(2) = '3'. Hence c = '3'.
  2. s is initialized from {'J', 'O', 'V'}. Its character count is 3. Hence len1 = 3.
  3. Output format prints c + " " + len1 ⟹\implies '3' + space + 3.

Final Output:

3 3
Exam Scenario: OO Modelling for a Mobile Banking System

Question: A mobile banking application allows users to log in, view account balances, transfer money between accounts, and update contact numbers. When modelling this application using object-oriented principles, which of the following is the best choice for a class?

A. A specific user’s savings account balance: $2500.00
B. The action of transferring money between two accounts
C. A general blueprint representing a bank account with attributes and behaviours
D. The text field where the user inputs their username on the login screen

Solution:

  • A is incorrect: A numeric balance is an attribute value representing the state of an account, not a class.
  • B is incorrect: Transferring money is an operation / behaviour, typically implemented as a method (transfer(toAccount, amount)).
  • D is incorrect: A specific input box is a concrete UI widget / boundary detail.
  • C is correct: A class must represent a generalized abstraction and structural blueprint (BankAccount) encapsulating shared attributes (accountNumber, balance) and domain behaviours (deposit(), withdraw()).

Final Answer: C
