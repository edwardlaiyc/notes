Code duplication across related abstractions leads to maintenance fragility and inconsistent bug fixes. Inheritance provides an architectural mechanism to organize classes into hierarchical taxonomies, allowing specialized subclasses (derived / child classes) to inherit fields and methods from generalized superclasses (base / parent classes).

Subclasses model a strict “is-a” relationship: every instance of the subclass is simultaneously an instance of the superclass. In Java, inheritance enables code reuse, extensible frameworks, and subtype polymorphism.

1. The Inheritance Mechanism in Java

In Java, a subclass inherits from a superclass using the extends keyword. Java enforces single inheritance of state: a class may extend at most one superclass, avoiding the multi-parent ambiguities (such as the Diamond Problem) found in C++. Every class that does not declare an explicit superclass implicitly extends java.lang.Object.

public class Employee {
    private String id;
    protected double baseSalary;

    public Employee(String id, double baseSalary) {
        this.id = id;
        this.baseSalary = baseSalary;
    }

    public double calculatePay() {
        return baseSalary;
    }
}

public class Manager extends Employee {
    private double bonus;

    public Manager(String id, double baseSalary, double bonus) {
        super(id, baseSalary); // 1. Delegate initialization to superclass constructor
        this.bonus = bonus;
    }

    @Override
    public double calculatePay() {
        return super.calculatePay() + bonus; // 2. Method refinement via super.method()
    }
}

2. Access and Visibility Modifiers

Java provides four access tiers governing member visibility across class, package, and subclass boundaries:

Modifier Inside Same Class Inside Same Package Subclass (Different Package) World (Everywhere)
public Yes Yes Yes Yes
protected Yes Yes Yes (via inheritance only) No
(package-private / default) Yes Yes No No
private Yes No No No

Subtle Exam Traps with protected

  • A subclass in another package can access protected members of its superclass only through references of its own subclass type (or child subtypes), not through an arbitrary superclass reference variable.
  • Package-private (no modifier) is not a keyword; omitting an access modifier grants access exclusively to classes declared within the identical Java package.

3. Constructor Chaining and Object Instantiation

Constructors are not members of a class and are therefore never inherited by subclasses. Instead, subclass constructors participate in constructor chaining to guarantee that superclass state is fully initialized before subclass initializers run.

       Heap Memory: new Manager("M1", 8000, 2000)
┌───────────────────────────────────────────────────────┐
│ Employee sub-object: id = "M1", baseSalary = 8000.0   │  <- Initialized by Employee()
├───────────────────────────────────────────────────────┤
│ Manager fields:      bonus = 2000.0                   │  <- Initialized by Manager()
└───────────────────────────────────────────────────────┘

The Explicit vs. Implicit Constructor Rules

  1. Automatic Superclass Invocation: If a subclass constructor does not explicitly invoke super(...) or this(...) as its very first statement, the compiler automatically inserts an invisible parameterless super();.
  2. First Statement Constraint: Any explicit constructor call—either super(...) (superclass constructor delegation) or this(...) (overloaded peer constructor delegation)—must be the absolute first statement in the constructor body.
  3. Mutual Exclusion Trap: You cannot call both super(...) and this(...) in the same constructor. A constructor that begins with this(...) delegates superclass invocation to the target constructor.
  4. The Missing No-Arg Trap: If a superclass defines at least one constructor with parameters, the compiler suppresses the automatic default no-arg constructor. If a subclass then attempts to invoke super() (implicitly or explicitly), a compile-time error occurs unless the superclass explicitly declares a parameterless constructor.
class Parent {
    public Parent(int val) { /* ... */ } // No default constructor exists!
}

class Child extends Parent {
    public Child() {
        // COMPILE ERROR: Implicit super() cannot find Parent()!
    }
}

4. Method Overriding vs. Method Overloading

Exam questions routinely test the mechanical differences between overriding and overloading:

Criteria Method Overloading Method Overriding
Class Context Within the same class (or across inherited methods) Between a superclass and a subclass
Method Name Must be identical Must be identical
Parameter List (Signature) Must differ (different types, counts, or order) Must be exactly identical
Return Type Can be identical or different Must be identical, or a covariant subtype
Visibility / Access Can be changed freely Cannot be made more restrictive than parent
Exception Specifiers Can throw any exception Cannot throw broader checked exceptions
Binding Mechanism Static binding (resolved at compile time by compiler) Dynamic binding (resolved at runtime by JVM)

The Covariant Return Type Rule

When overriding a method, the return type may be specialized to a subclass of the original return type:

class AnimalBuilder {
    public Animal build() { return new Animal(); }
}
class DogBuilder extends AnimalBuilder {
    @Override
    public Dog build() { return new Dog(); } // Legal: Dog is a subtype of Animal
}

Visibility Narrowing is Illegal

An overriding method cannot reduce superclass visibility. If Parent.compute() is protected, Child.compute() may be protected or public, but declaring it private or default causes a compilation error.

5. The final Keyword in Inheritance

The final keyword imposes strict immutability and extension constraints depending on target placement:

  • final Variable: The variable can be assigned a value exactly once. For primitive types, the value cannot change; for reference types, the pointer cannot be redirected to another heap object (though the referenced object’s internal fields may remain mutable).
  • final Method: Prevents subclasses from overriding the method. The method implementation is locked, enabling compiler inlining optimizations.
  • final Class: Prevents the class from being extended (extends). All methods of a final class are implicitly final. Standard utility classes (e.g., java.lang.String, java.lang.Math, wrapper classes like Integer) are declared final for security and immutability guarantees.

6. Architectural Best Practices: Inheritance vs. Composition

Inheritance establishes high coupling: any modification to a superclass’s public or protected interface ripples down to all subclasses (fragile base class problem).

Apply the Liskov Substitution Principle (LSP) check:

  • Ask: “Is every Subclass strictly a Superclass in every behavioural context?”
  • If the subclass requires only a subset of features or represents a physical part of the whole, use Composition (“has-a”) instead of Inheritance (“is-a”).
Bad Design (Inheritance abuse):   Circle extends Point  (Circle is NOT a point!)
Good Design (Composition):        Circle has-a Point    (Point center is an attribute)

7. Tracing Toolkit: Constructor Chaining Execution Order

When tracing object instantiation in multi-tiered inheritance hierarchies:

  1. Step 1: Ascend the Superclass Chain
    Follow constructor delegation (super(...) or implicit super()) up the hierarchy until reaching java.lang.Object. No constructor body statements execute during ascent.
  2. Step 2: Descend with Field Initializers then Constructor Bodies
    From the topmost superclass down to the concrete subclass:
    • Run the class’s explicit field declarations and instance initializers in textual order.
    • Run the remainder of that class’s constructor body.
  3. Step 3: Watch for Overridden Methods Called from Constructors
    If a parent constructor invokes a method overridden by the child, dynamic binding dispatches to the child’s implementation immediately, before child field initializers have executed. The child method executes against uninitialized default values (0, null)!

8. Tutorial and Exam Practice

Tutorial 3 Q2: The Point-Circle-Cylinder Inheritance Anti-Pattern

Question: A student models geometric entities by creating a class Point (x, y), then creating Circle (radius) that extends Point, and finally creating Cylinder (height) that extends Circle.

Discuss whether it was a good architectural choice to use Point as the base class for Circle, and suggest a superior alternative design.

Solution:

  1. Flaws in the Inheritance Design:
    • Violation of the “is-a” Relationship: A Circle is not a specialized Point. A Point represents a discrete 0-dimensional geometric coordinate; a Circle is a 2-dimensional planar boundary enclosing an area.
    • Interface Pollution: By extending Point, Circle inherits setX() and setY() directly. Conceptual operations like moving the center coordinates become conflated with the identity of the circle itself.
    • Cylinder Distortion: Extending Cylinder from Circle further compounds the error: a 3-dimensional solid is not a 2-dimensional circle.
  2. Superior Alternative Architecture (Composition over Inheritance):
    • Model Point as an independent entity representing 2D coordinates.
    • Circle uses composition (“has-a”): a circle holds an instance variable private Point center; along with private double radius;.
    • Cylinder uses composition: a cylinder holds an instance variable private Circle base; along with private double height;.
Wooclap Check: Constructor Chaining and Illegal Invocations

Question: What occurs when attempting to compile and execute the following Java code?

class A {
    public A() {
        System.out.println("A");
    }
}

class B extends A {
    public B() {
        super();
        this(5);
    }
    public B(int x) {
        System.out.println("B: " + x);
    }
}

public class Test {
    public static void main(String[] args) {
        B b = new B();
    }
}

A. Prints: A then B: 5
B. Prints: B: 5
C. Compilation error in class A
D. Compilation error in class B

Solution:

  • In Java, constructor delegation statements (super(...) or this(...)) are strictly restricted to the very first line of a constructor body.
  • A single constructor cannot contain both super() and this(5). Calling this(5) already handles delegation to another constructor (which in turn invokes super()).
  • The compiler detects two constructor invocations in B() and emits an error: “call to this must be first statement in constructor”.

Final Answer: D (Compilation error in class B)

Wooclap Check: Implicit super() and Suppressed Default Constructor

Question: Evaluate the following code and determine the compile-time or runtime outcome:

class Parent {
    private int value;
    public Parent(int value) {
        this.value = value;
        System.out.println("Parent: " + value);
    }
}

class Child extends Parent {
    public Child() {
        System.out.println("Child no-arg");
    }
    public Child(int x) {
        super(x);
        System.out.println("Child: " + x);
    }
}

public class Test {
    public static void main(String[] args) {
        Child c = new Child();
    }
}

Solution:

  1. In Parent, an explicit parameter-bearing constructor Parent(int value) is declared. As a result, the compiler suppresses the generation of the default parameterless constructor Parent().
  2. In Child(), no explicit call to super(...) or this(...) is written on line 1. Therefore, the compiler automatically attempts to insert super();.
  3. The compiler searches Parent for a no-argument constructor Parent(). None exists.
  4. Compilation fails with: “constructor Parent in class Parent cannot be applied to given types; required: int; found: no arguments”.

Final Answer: Compilation error in class Child

Wooclap Check: Trace of Constructor Delegation and Field Initialization

Question: Determine the exact terminal output when main() executes:

class Person {
    String name;
    public Person(String name) {
        this.name = name;
        System.out.println("Person constructor: " + name);
    }
}

class Student extends Person {
    int year;
    public Student(String name, int year) {
        super(name);
        this.year = year;
        System.out.println("Student constructor: " + year);
    }
}

public class TestInheritance {
    public static void main(String[] args) {
        Student s = new Student("Alex", 2);
    }
}

Solution:

  1. new Student("Alex", 2) invokes Student(String, int).
  2. The first line of Student(String, int) executes super("Alex");, transferring control to Person(String).
  3. Person(String) sets this.name = "Alex" and prints: Person constructor: Alex.
  4. Control returns to Student(String, int). It sets this.year = 2 and prints: Student constructor: 2.

Final Output:

Person constructor: Alex
Student constructor: 2
