Multiple inheritance of state—where a class directly inherits fields from multiple concrete parents—creates severe architectural hazards, most notably the Diamond Problem (conflicting state and method implementations inherited along dual paths).

Java resolves this structural dilemma by restricting classes to single inheritance of state while providing interfaces to support multiple inheritance of type and behaviour. Interfaces establish contract-driven boundaries, allowing unrelated classes to guarantee common capabilities without being forced into an unnatural inheritance hierarchy.

1. Interfaces as Pure Behavioural Contracts

An interface defines a formal protocol: a set of method declarations that implementing classes promise to execute. It specifies what a component does, leaving how to concrete implementations.

public interface Resizable {
    // 1. Implicitly public static final constant
    double RESIZE_FACTOR = 1.5;

    // 2. Implicitly public abstract method (pre-Java 8)
    void resize(double factor);

    // 3. Default method with concrete body (Java 8+)
    default void resetSize() {
        resize(1.0);
    }

    // 4. Static utility method (Java 8+)
    static boolean isValidFactor(double factor) {
        return factor > 0;
    }
}

Compiler Invariants Inside Interfaces

  • Fields: Every field declared in an interface is implicitly public static final. Instance attributes are strictly prohibited; fields serve exclusively as immutable constants.
  • Abstract Methods: Every method declaration without a body is implicitly public abstract. Omitting the public modifier still grants public access (not package-private).
  • Constructors: An interface cannot declare constructors and cannot be directly instantiated via new Resizable().

2. Implementing Interfaces and Syntax Rules

Classes bind to interfaces using the implements keyword. A class can implement an arbitrary number of interfaces separated by commas:

public class VectorGraphic extends GraphicElement implements Resizable, Serializable, Comparable<VectorGraphic> {
    private double size;

    @Override
    public void resize(double factor) {
        if (Resizable.isValidFactor(factor)) {
            this.size *= factor;
        }
    }

    @Override
    public int compareTo(VectorGraphic other) {
        return Double.compare(this.size, other.size);
    }
}

Key Syntactic Invariants

  1. Ordering Rule: In class definitions, extends must precede implements:
    class Sub extends Super implements InterA, InterB (Legal)
    class Sub implements InterA extends Super (Compile error)
  2. Access Widening Requirement: A method declared in an interface is implicitly public. When a concrete class provides the implementation body, the method must be explicitly declared public. Omitting public (default package-private) attempts to reduce visibility, producing a compilation error.
  3. Incomplete Implementations: If a concrete class fails to provide an implementation body for even one inherited abstract method, the class must be declared abstract.

Hierarchy Coupling Matrix

Relationship Keyword Allowed Cardinality Notes
Class →\to Class extends 1 (Single) Direct inheritance of state and implementation
Class →\to Interface implements Many (Multiple) Implements behavioural contracts
Interface →\to Interface extends Many (Multiple) An interface can inherit from multiple parent interfaces
Interface →\to Class Illegal — An interface can never extend or implement a class

3. Architectural Comparison: Abstract Class vs. Interface

Choosing between an abstract class and an interface is a foundational system design decision tested extensively in exams:

Dimension Abstract Class Interface
Primary Intent Identity & partial implementation (“is-a”) Capability & contract definition (“can-do”)
State / Fields Can maintain instance state (private int x;) and constants Only constants (public static final)
Constructors Has constructors (invoked via super() chaining) No constructors
Methods abstract, concrete, protected, static, final abstract, default, static, private (Java 9)
Inheritance Model Single inheritance (extends BaseClass) Multiple realization (implements I1, I2, I3)
Evolution Impact Adding concrete methods does not break subclasses Adding abstract methods breaks all existing implementers
Selection Heuristic Use when related subclasses share common fields and code Use when unrelated classes require polymorphic capabilities

4. Modern Interface Features: Default and Static Methods

Java 8 introduced concrete method declarations inside interfaces to enable backward compatibility, allowing API designers to enrich existing interfaces (such as adding stream() to java.util.Collection) without breaking existing implementing codebases.

1. Default Methods (default)

Declared with the default keyword and a standard method block. Implementing classes inherit the default implementation automatically unless they explicitly override it.

2. Static Methods (static)

Provide utility functions directly associated with the interface contract. Unlike static methods in classes, interface static methods are not inherited by implementing classes or sub-interfaces; they must be invoked using the interface name: Resizable.isValidFactor(2.0).

5. Multiple Interface Conflict Resolution Protocol

When a class implements multiple interfaces that define identical method signatures, Java applies a deterministic 3-tier conflict resolution algorithm:

                  ┌────────────────────────────────────────┐
                  │ 1. Does a Superclass provide a body?   │
                  └──────────────────┬─────────────────────┘
                                     │
                       Yes ──────────┴────────── No
                        │                         │
                        ▼                         ▼
            [Superclass Always Wins]   ┌────────────────────────────────────────┐
            (Class implementation      │ 2. Does a Sub-interface provide a more │
             overrides all defaults)   │    specific default implementation?    │
                                       └──────────────────┬─────────────────────┘
                                                          │
                                            Yes ──────────┴────────── No
                                             │                         │
                                             ▼                         ▼
                                   [Sub-interface Wins]      [Conflict Compilation Error]
                                   (Specific overrides       (Class MUST explicitly override
                                    generalized default)      and disambiguate implementation)

Disambiguating Default Collisions

If two unrelated interfaces define conflicting default methods with identical signatures, the implementing class causes a compile-time error unless it overrides the method and explicitly selects one implementation using InterfaceName.super.method():

interface A {
    default void log() { System.out.println("Log A"); }
}

interface B {
    default void log() { System.out.println("Log B"); }
}

public class Logger implements A, B {
    @Override
    public void log() {
        A.super.log(); // Disambiguates explicitly; or provide completely custom logic
    }
}

6. Console I/O: Scanner and the Newline Buffer Pitfall

Console input in standard Java utilizes java.util.Scanner wrapping System.in:

Scanner sc = new Scanner(System.in);
System.out.print("Enter ID: ");
int id = sc.nextInt();

System.out.print("Enter Name: ");
String name = sc.nextLine(); // DANGER: Reads leftover newline!

The Newline Buffer Mechanics

Methods such as nextInt(), nextDouble(), and next() scan input tokens up to the trailing delimiter (whitespace or newline \n), but leave the \n character sitting unconsumed in the input buffer stream.

When nextLine() is subsequent called, it immediately consumes the leftover \n character and returns an empty string "" without waiting for user input!

User types:  "42\n"
             ┌────┬────┐
Buffer:      │ 42 │ \n │
             └────┴────┘
nextInt():   Consumes "42", leaving ['\n'] in the stream buffer.
nextLine():  Immediately reads and consumes ['\n'], returning "".

The Standard Remediation: Always insert an explicit, unassigned sc.nextLine(); to clear the buffer immediately following any numeric/token read:

int id = sc.nextInt();
sc.nextLine(); // Flushes the unconsumed newline character
String name = sc.nextLine(); // Correctly pauses and captures text input

7. Tracing Toolkit: Interface Hierarchy & Conflict Resolution

When analyzing interface interactions in exam problems:

  1. Verify Extension vs. Implementation Keywords:
    • Class-to-Class ⟹\implies extends
    • Class-to-Interface ⟹\implies implements
    • Interface-to-Interface ⟹\implies extends (can list multiple interfaces!)
  2. Check Access Modifiers on Overridden Methods: Ensure every method implementing an interface method is explicitly marked public.
  3. Trace Method Collisions:
    • Class implementation present? ⟹\implies Superclass wins unconditionally.
    • Distinct default methods from sibling interfaces? ⟹\implies Compilation fails unless class explicitly overrides the signature.
  4. Trace Token Reading in Scanner Snippets: Mark characters remaining in the input stream buffer after each token read. If nextLine() follows a numeric read without an intermediate flush, mark its return value as empty string "".

8. Tutorial and Exam Practice

Exam Design Problem: Abstract Class vs. Interface Selection

Question: An architect designs an enterprise fleet management system involving Truck, Sedan, Bicycle, and CargoDrone.

  1. Propose where an abstract class Vehicle should be deployed versus an interface Navigable and interface ElectricPowered.
  2. Justify why Vehicle should not be modelled purely as an interface.

Solution:

  1. Architectural Allocation:
    • abstract class Vehicle: Represents the foundational identity (“is-a”) for land-based transport entities (Truck, Sedan). Holds shared encapsulated state variables (licensePlate, odometerReading, vin) and shared implementations for concrete operations (recordTrip(), serviceHistory()).
    • interface Navigable: Represents the capability to receive GPS coordinates and execute route planning. Implemented across unrelated physical entities (CargoDrone, Truck, Sedan).
    • interface ElectricPowered: Represents battery charging protocols (recharge(), getBatteryPercentage()). Implemented by ElectricSedan, Bicycle, and CargoDrone.
  2. Justification:
    • Modeling Vehicle as an interface would disallow instance state (licensePlate, odometerReading) and common constructors. Every concrete class would be forced to duplicate the declaration and management of state fields, violating DRY (Don’t Repeat Yourself) and weakening encapsulation.
Wooclap Check: Interface Syntax and Extension Rules

Question: Which of the following statements regarding Java interfaces are TRUE? (Select all that apply)

A. An interface can implement another interface using the implements keyword.
B. An interface can extend multiple interfaces simultaneously using commas.
C. An abstract class cannot implement an interface without providing concrete bodies for all its methods.
D. Every variable declared in an interface is implicitly public static final.
E. A class can extend multiple abstract classes as long as neither declares concrete methods.

Solution:

  • A is FALSE: An interface inherits from another interface using extends, never implements.
  • B is TRUE: Java permits multiple interface inheritance: interface C extends A, B.
  • C is FALSE: An abstract class is permitted to implement an interface while leaving some or all methods unimplemented (abstract).
  • D is TRUE: All fields in an interface are immutable compile-time constants (public static final).
  • E is FALSE: Java enforces strict single class inheritance; a class can extend at most one class regardless of abstractness.

Final Answer: B and D

Exam Code Trace: The Scanner Buffer Pitfall

Question: Consider the following input stream delivered to a console application:

42
John Doe

Trace the execution of this snippet and determine the exact values stored in age and name:

Scanner sc = new Scanner(input);
int age = sc.nextInt();
String name = sc.nextLine();

Solution:

  1. sc.nextInt() scans the token characters '4', '2' and converts them to integer 42.
  2. The read pointer halts immediately before the subsequent newline character '\n'.
  3. Next, sc.nextLine() executes. It scans from the current pointer up to the next newline '\n'.
  4. It encounters the immediate '\n' left over from the first line, consumes it, and returns all characters before it (an empty string "").
  5. The string "John Doe" on the second line remains completely unread!

Resulting Values:

  • age = 42
  • name = "" (empty string)
Exam Code Trace: Interface Default Method Collision

Question: What occurs when compiling and running the following program?

interface Alpha {
    default void show() { System.out.print("Alpha "); }
}

interface Beta {
    default void show() { System.out.print("Beta "); }
}

class Implementer implements Alpha, Beta {
    // No show() method defined here
}

public class Main {
    public static void main(String[] args) {
        new Implementer().show();
    }
}

A. Prints: Alpha
B. Prints: Beta
C. Prints: Alpha Beta
D. Compilation error occurs in class Implementer

Solution:

  • Alpha and Beta both provide unrelated default implementations for show() with identical method signatures.
  • Because neither interface is a sub-interface of the other, and because Implementer does not inherit a concrete implementation from a superclass, the compiler cannot deduce precedence.
  • Java flags an ambiguity collision at compile time: “class Implementer inherits unrelated defaults for show() from types Alpha and Beta”.
  • To fix this, Implementer must override show() and resolve the ambiguity explicitly.

Final Answer: D (Compilation error)
