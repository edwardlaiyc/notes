Class diagrams model the static, structural skeleton of an object-oriented system. However, they do not depict how objects collaborate over time to fulfill use cases.

A Sequence Diagram is an interaction diagram that captures dynamic runtime behaviour. It models the sequential exchange of messages between participating objects along an explicit vertical timeline, detailing execution control, object lifecycles, and state transformations.

1. Anatomy of a Sequence Diagram

A sequence diagram visualizes an interaction along two orthogonal axes:

  • Horizontal Axis: Represents distinct participating objects / lifelines.
  • Vertical Axis: Represents the progression of time flowing downward (top to bottom).

Core Structural Elements

  1. Lifeline Box (Classifier Role):
    • Syntax: instanceName : ClassName (or : ClassName for anonymous instances).
    • Underlined to signify an active object instance.
    • The dashed vertical line extending downward represents the existence of the object over time.
  2. Actor: Depicted as a stick figure representing an external human user or boundary system initiating a workflow.
  3. Activation Bar (Focus of Control):
    • A thin vertical rectangle superimposed over the dashed lifeline.
    • Designates the period during which an object is actively executing a method or waiting for a nested method return.

2. Message Syntax and Visual Arrow Conventions

The exchange of data and invocations between objects is rendered using standardized arrow conventions:

Message Type Arrow Notation Line Style Execution Semantics Java Analogy
Synchronous Call Solid line with filled triangle head ──► Solid Caller halts execution and blocks until operation finishes result = obj.calc();
Asynchronous Call Solid line with open arrow head ──> Solid Caller dispatches message and continues executing concurrently without waiting new Thread(task).start();
Reply / Return Dashed line with open arrow head <- - - Dashed Returns control and optional return value to caller return balance;
Self-Call (Internal) U-shaped loop arrow returning to same lifeline Solid An object invokes a private or internal helper method on itself this.validate(code);

Detailed Message Specification

Message labels follow the standard UML signature format: [guardCondition] sequenceNumber : [returnVar = ] methodName(parameters)

3. Object Creation and Destruction Lifecycles

Objects are not necessarily permanent; they can be created and destroyed dynamically during interaction flows:

  • Dynamic Instantiation (<<create>>):
    • The message arrow points directly to the head of the new object’s lifeline box (not to its dashed line).
    • Java equivalent: TargetClass t = new TargetClass();.
  • Explicit Destruction:
    • Marked with a large bold X terminating the dashed lifeline at the destruction point.
    • In C++, corresponds to delete obj;. In Java, signals that all references are severed, eligible for garbage collection.

4. Combined Fragments: Modelling Conditional Logic

To represent loops, alternatives, and optional branches without drawing spaghetti flows, UML defines Combined Fragments—rectangles enclosing interactions labeled with an operator in the top-left pentagon:

High-Yield Fragment Operators

Operator Full Name Semantic Rule
alt Alternatives Exclusive branching (if-else or switch). The fragment is divided into sub-frames by a horizontal dashed line. Exactly one branch whose guard condition [condition] evaluates to true executes.
opt Option Single conditional execution (if without else). The enclosed block executes if and only if the guard condition [guard] holds true.
loop Iteration Repeated execution (for or while). Can declare bounds loop(min, max) or guard loop [hasMoreItems].
par Parallel Concurrent execution of sub-blocks across multi-threaded lifelines.
ref Reference References an entire sub-sequence diagram defined elsewhere, maintaining modularity.

5. Architectural Pattern: Boundary-Controller-Entity (BCE)

The Boundary-Controller-Entity (BCE) architectural pattern (also known as the Robustness Analysis pattern) partitions classes by responsibility to enforce separation of concerns:

The Three Archetypes

Archetype UML Stereotype Primary Role Java Examples
Boundary <<boundary>> or ─○ Mediates communication between external actors (users/APIs) and internal systems. Translates raw user input into domain requests. LoginUI, OrderScreen, RestApiController, ConsoleMenu
Controller <<controller>> or ↺ Orchestrates control flow and encapsulates core business logic. Coordinates Entities to execute use case rules. RideBookingController, PaymentManager, AuthHandler
Entity <<entity>> or ─── Encapsulates persistent domain data and foundational business rules. Typically mapped to database records. Account, Customer, FlightTicket, OrderItem

Strict BCE Communication Invariants

Exams rigorously test which direct connections are legally permitted under BCE rules:

               ┌──────────┐
               │  Actor   │
               └────┬─────┘
                    │ (Permitted)
                    ▼
               ┌──────────┐
               │ Boundary │
               └────┬─────┘
                    │ (Permitted)
                    ▼
               ┌──────────┐         (Permitted)         ┌──────────┐
               │Controller├────────────────────────────►│  Entity  │
               └────┬─────┘                             └────┬─────┘
                    │ (Permitted)                            │ (Permitted)
                    ▼                                        ▼
             ┌──────────────┐                         ┌──────────────┐
             │Other Control │                         │ Other Entity │
             └──────────────┘                         └──────────────┘
  1. Actors ↔\leftrightarrow Boundary: Actors may communicate ONLY with Boundary objects. An actor cannot touch a Controller or Entity directly.
  2. Boundary ↔\leftrightarrow Controller: Boundaries delegate user actions to Controllers.
  3. Controller ↔\leftrightarrow Entity: Controllers read and manipulate Entities.
  4. FORBIDDEN (Illegal Shortcuts):
    • Boundary →\to Entity is PROHIBITED: UI screens must not bypass controllers to mutate entity data directly.
    • Entity →\to Boundary is PROHIBITED: Domain entities must never know about or reference UI components.

6. Tracing Toolkit: Translating Sequence Diagrams to Java Code

When converting a sequence diagram into Java class definitions:

  1. Identify the Sender and Receiver:
    • The message arrow originates from the caller and terminates on the callee.
    • The receiver class must declare the method matching the message signature.
  2. Translate Lifelines into Class Fields or Local Variables:
    • If Class AA calls Class BB across multiple sequence diagrams, Class AA holds an instance variable private B b;.
    • If Class AA calls Class BB only once in a transient transaction, Class AA receives B as a method parameter or instantiates it locally.
  3. Translate Arrows into Code Invocations:
    • Synchronous call ──► ⟹\implies Direct method call b.processPayment(amount);.
    • Return arrow <-- - - ⟹\implies Method return status;.
  4. Translate Frames:
    • alt with dashed partition ⟹\implies if (...) { ... } else { ... }.
    • opt ⟹\implies if (...) { ... }.
    • loop ⟹\implies for (Item item : items) { ... } or while (...).

7. Tutorial and Exam Practice

Wooclap Check: BCE Architecture Role Classification

Question: In a ride-hailing application (e.g., Grab / TADA), a user initiates a booking. Match each software component to its appropriate BCE architectural archetype:

  1. RideBookingUI
  2. RideController
  3. Passenger and Driver
  4. PaymentGatewayScreen

Solution:

  • RideBookingUI ⟹\implies Boundary (captures user interface inputs and displays ride status).
  • PaymentGatewayScreen ⟹\implies Boundary (renders payment interface to the passenger).
  • RideController ⟹\implies Controller (manages matchmaking algorithms, coordinates pricing calculations, and orchestrates driver assignment).
  • Passenger and Driver ⟹\implies Entity (stores domain state, ratings, account records, and persistent profiles).
Wooclap Check: Boundary Class Semantic Definition

Question: In object-oriented system analysis, what is the primary responsibility of a Boundary class?

A. To execute database queries and store business entities
B. To handle the interface between the system and its external actors (users or external systems)
C. To orchestrate transactional business logic and calculations
D. To define database schema mappings

Solution:

  • A and D describe Entity persistence mechanisms.
  • C describes Controller responsibilities.
  • B is correct: A Boundary class serves as the interface between external actors and the internal system boundaries.

Final Answer: B

Tutorial 7 Q1: Code Synthesis from Sequence Diagram Interaction

Question: A sequence diagram shows a Teller actor invoking cashCheck(check) on a CashierUI boundary. CashierUI invokes verifyCheck(check) on a CheckController. CheckController calls isCleared() on the Check entity, and if cleared, calls debit(amount) on Account.

Synthesize the Java method structure for CheckController.

Solution:

public class CheckController {
    public boolean verifyAndCashCheck(Check check, Account account) {
        // 1. Verify entity state
        if (check.isCleared()) {
            double amount = check.getAmount();
            // 2. Coordinate transaction on Account entity
            account.debit(amount);
            check.markCashed();
            return true;
        }
        return false;
    }
}
  • Notice that CheckController coordinates both Check and Account entities without CashierUI needing to directly interact with Account.
Exam Check: Interpretation of Combined Fragment Guards

Question: Distinguish between the execution semantics of an alt combined fragment and an opt combined fragment in a sequence diagram.

Solution:

  • alt (Alternatives): Represents mutually exclusive branching identical to if-else or switch. Contains two or more operands separated by dashed horizontal lines. The operand whose guard condition evaluates to true executes, and the others are bypassed.
  • opt (Option): Represents an optional sequence identical to a single if statement without an else branch. Contains exactly one operand. If the guard condition evaluates to true, the enclosed sequence executes; if false, execution skips the fragment entirely and continues downward.
